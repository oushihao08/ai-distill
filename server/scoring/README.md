# 独立评分模块

## 适用范围与绑定规则

- **当前执行绑定**：以项目、题目、任务、材料包、`revision` 和附件 ID 为准。已派发任务不因正文/配置/提示词/整理结果的内容摘要或环境指纹变化而被拒绝；保留任务取消、最新任务归属、材料集合完整性、结构格式和路径边界检查。摘要字段用于历史记录、内容寻址及缓存。
- **职责范围**：逐份成功答案建立匿名评分任务，支持隔离 Agent（经 `isRegisteredAgentProvider()` 校验）和独立 API。**执行成功、评分结构有效、专业判断正确、达标通过是四种不同结论。**不以历史项目验收或测试存在推断当前运行环境已加载代码。

文件型作答由 `context.ts` 仅从本次有效答案 attempt 的 `model_answer_file` 记录读取：核对文件名、文件摘要、规范化生成源摘要、数量和总正文上限，再把可评分正文、文件格式、字节数与核验范围作为独立文件交给评分器。DOCX/XLSX证据证明受管OOXML已生成且生成源可读，不证明像素版式；API评分内联实际正文，不引用其无法访问的本地路径。工具轨迹只提供调用类型、状态和公开来源链接，不含作答模型身份、目标分数、Skill、思路或普通题标答。技术生成失败不得冒充专业零分；专业内容仍只按原Rubric评价。

## AI维护者查证顺序

判断“评分依据是什么、是否读了标答/Skill、为何这个分数有效”时必须追到最终文件投影和提交绑定：

1. `context.ts`从当前成功答案读取同版题面、附件正文、Rubric、答案正文和绑定；这里的内部`ScoreContext`包含兼容字段，不等于全部发送给模型。
2. `jobs.ts`的`enqueueScore()`逐个成功答案冻结上下文、provider、模型、步骤提示词和执行协议；同一答案已有活动评分时不重复创建。
3. `executor.ts`的`buildAnonymousInput()`做内部校验，`buildScoreFiles()`才是模型文件白名单。判断泄漏或token输入必须看后者和`buildScoreMessage()`，不能只看`ScoreContext`字段。
4. `runIndependentScore()`与`runIndependentApiScore()`分别执行Codex文件会话和API内联请求；工具可用不证明已运行，完整阅读指令不证明模型实际读完。
5. `validate.ts`只证明对应报告协议的结构/绑定要求；`jobs.ts`提交前再次比较完整上下文摘要并汇总，随后达标模块才使用有效成绩。

评分事实分层：模型调用返回文本、程序成功提取报告、报告满足绑定、专业评分正确、达到项目门槛、完成归档/交付，六者不能互相替代。

## 评分输入白名单与证据边界

| 输入类别 | 普通评分 | calibration评分 | 权威位置 |
| --- | --- | --- | --- |
| 同版题面与Rubric | 提供 | 提供 | `buildScoreFiles()` |
| 本题冻结的完整获准附件正文 | 提供 | 提供 | `context.ts` → `buildScoreFiles()` |
| 匿名完整答案 | 提供 | 提供 | `buildScoreFiles()` |
| 评分步骤提示词和冻结政策 | 提供 | 提供 | `buildScoreMessage()` |
| 作答思路 | 不提供 | 不提供 | 内部兼容字段不会进入文件白名单 |
| 标准答案 | 不提供 | 仅提供冻结校准参考 | `buildScoreFiles()`的显式政策分支 |
| 项目Skill、项目身份、作答模型身份、目标分 | 不提供 | 不提供 | 执行前清除；测试验证最终请求 |

附件用于核对题面事实和Rubric依据，但得分证据必须来自待评答案实际写出的内容。`candidate-quotes.ts`只检查候选引文字面是否存在于答案，不能证明语义正确；`arithmetic-tool.ts`只复算模型已经给出的数值，不能决定业务得分。任何工具均不得替代Rubric判断。

## 真正进入模型的输入

输入为评分步骤提示词、同版题面与Rubric、该题冻结模式对应的附件、匿名完整答案。共享库快照可为脱敏正文或提取原文；旧题保持原脱敏来源。作答系统提示词只用于答案摘要绑定，不作为评分输入；公开成果的`text_deliverables_v1`呈现约定会进入评分文件。

内部上下文兼容保留已有思路和标答；普通评分不要求这两项，只有显式标答校准模式要求非空标答。**这不表示两者都会发给模型**。实际文件由`buildScoreFiles()`白名单生成：思路与项目Skill不提供；标准答案默认不提供，只有冻结的`model_report_v1`政策明确`reference_answer=calibration`时提供校准参考。校准不得成为唯一答案键。Rubric投影排除`metadata.project_context`夹带的整题资料。作答模型身份、目标分数、项目身份及设计研究不主动提供；题面自身包含的信息不会被程序语义清洗。

新评分任务不要求当前项目Skill存在或未变化；旧规则/项目文件绑定仅按历史协议兼容，元数据不成为评分文件。若配置钩子，为冻结脚本可解析有效Skill路径，但不因此向评分模型加入Skill内容。

Codex在独立临时工作区分文件读取，实际隔离由`../agent/`与`../codex/`实施：网络、记忆、宿主项目规则/Skill、MCP等外部入口关闭，保留读文件所需工具。API将题面、Rubric、附件、匿名答案及必要计分数据完整内联到单次文字请求，不发送Python源码或脚本执行指令；Agent仍可使用原有复算和候选引文工具。API不因此获得shell或联网能力。不能从工具声明或提示词断言实际读完/执行成功。

模型文本原文、文件名/大小/SHA及执行请求随报告保留；临时输入由Codex客户端清理，详细argv及私有事件按受限诊断边界处理，不复制到普通日志。旧记录缺失请求快照时不得用当前源码补造。

## 提示词与报告契约

评分提示词来自本次冻结设置；精确命中已知旧内置默认时映射到当前默认，自定义正文保留。模型另收到实际Rubric ID清单、呈现说明以及显式model_report规则/结果格式。不能将“自定义正文保留”误写成“实际请求完全不附加其他指令”。不追加通用开发者评分指令。

新model_report任务冻结证据核对正文：先独立看候选，再用获准标答；候选引文回查答案，法源/材料引文注明来源；搜索未命中不能直接认定材料不存在。指令不自动证明模型遵守。旧无该字段任务继续空正文原协议；已有字段与当前指令不符时拒绝执行，其他绑定仍校验。

| 路径 | 程序实际检查 | 不保证什么 |
| --- | --- | --- |
| 默认legacy文本`extractTextScore()` | 读取明确最终总分及本题满分，不检查逐项合计、重复/缺失条目或整数分；不自行改分。 | 不从自由文本自动验证理由、引文准确性或法律正确性。 |
| 显式`model_report_v1`的`extractModelReport()` | 唯一结果区JSON、完整唯一ID、judgment/reason、有限数值或null、summary类型与evaluation_percent在0—100。 | **不复算raw/full、逐项合计或净分比例，不修改模型分数**；结构有效不表示算术正确。 |
| 旧结构化`validateScore()` | 绑定、有效性声明/争议、ID、分数范围/合计、指定来源包含引文、正分答案证据等。 | 文本包含关系不证明专业判断成立；不拿旧结构校验范围冒充当前文本报告保证。 |

model_report原始分可为负，否决独立记录；raw_score、full_score、evaluation_percent、veto_triggered分别保存。缺可比较指标不得猜造分数。程序不为制造达标而调分。

`计分条目.json`从Rubric原始权重投影；`复算评分.py`接受Agent已判定items，检查ID、有限值、独立否决不计分，输出实际加扣分和、正项满分及裁剪净分比例。它不验证业务得分是否合理，不覆盖报告；仅冻结规则采用该口径时使用比例。API收到脚本文字但不会运行它，Codex是否运行需另查执行事件。

## 呈现适配、队列与恢复

文字成果约定允许用答案分节内容对应文件成果，评分不能仅因缺实体文件或运行目录前缀扣分；专业内容、字段、业务格式仍按Rubric。未实际完成的外部检索/操作不冒记为完成，也不能把候选漏读已提供材料反推成出题缺陷。

模型集合全部终态且至少一个成功答案后，可评分成功答案；失败/跳过答案不生成虚假零分。每次重新派发都创建新评分，不复用已完成结果；同一答案已有等待/运行任务则拒绝重复。新派发清除达标/归档当前状态，历史保留。

评分冻结参数、同版上下文、呈现约定及执行指令摘要，提交前重读绑定；旧题/答案变更不能被迟到评分覆盖。legacy 返回明确可用最终总分才记评分成功；只有草稿链接/说明或缺失总分记评分失败并保留原文。model_report 保留执行与结构状态区别。无文本的无效旧结构报告或调用失败为失败。

worker按Codex/API分别领取，带钩子的API任务由local/all亲和队列执行；API使用独立API资源池，不占Agent槽。失联恢复只整理状态，不自动收费重试；自动达标在评分汇总终态后运行，并先提交释放评分事务连接。自动判断失败记录安全日志，不等于已归档或已上传。

before/after钩子输入仍是相同白名单；notes/data不能覆盖模型成绩。主检查点及明确续跑由[生命周期模块](../lifecycle/README.md)管理，后置待执行记录与主结果同事务登记，释放事务后同步执行。真实使用须具备对应表，不因文档描述而自动迁移。

legacy 文本评分已撤除 Python 交卷预检：新任务不冻结预检标记，实际会话不提供核验脚本或“valid=true 后才能提交”的指令。历史预检标记只用于核对旧冻结摘要，不再注入执行。评分 Agent 直接返回完整评分正文；程序仅提取明确最终总分，按项目当前门槛判断。不校验逐项算术、条目唯一性或0/1分，也不增加AI复审。没有明确合法总分仍不能编造分数。

历史已成功执行但被旧逐项规则拒绝的 legacy 报告，在达标快照读取时按当前最终总分口径投影；不改写原始评分或重跑模型。只有草稿链接、缺少完整总分或执行失败的记录不产生有效分数。

维护时保留输入隔离、来源模式、版本与契约区别。静态核对和替身测试不能证明真实模型评分准确率、当前worker已加载、外部提交或整条业务验收。


## Work新评分的候选引文核验

只对成功作者契约为`work_legal_v1`且评分为`model_report_v1`的新派发任务，入队冻结`context.candidate_quote_check=literal_v1`，随执行指令冻结提示正文和核验脚本SHA；上下文摘要包含标记。旧无标记队列、历史报告及其他项目维持原协议，不补造字段或重评。内部作者契约用于选择本次协议，不交给匿名评分模型。

每项模型结果增加`answer_quotes:string[]`；所有声称来自候选的原句按原标点/空格复制，没有可引用内容时允许`[]`，避免为缺失判断编造证据。Codex收到`核验候选引文.py`，按指令在本会话对报告JSON核验；工具只列错引条目，模型自行回读、纠正判断和成绩，再核对汇总。没有新增通用Agent重试或自动付费重评；API无文件执行能力，只要求同样的原文核对与结果格式。

两类执行器返回后，以及worker结果提交前，都对已声明引文做逐字包含核验。失败仍完整保存原文和校验问题，但不产生有效比较指标，不参与达标；程序不调整、裁剪或重算模型分数。空数组不证明内容不存在，引文字面存在不证明语义匹配或专业结论正确，reason遗漏声明的引文也不能由此自动证明可靠，仍须按试点计划审计实际报告。`validateAnswerScore()`的独立兼容校验接口不代表重放某次任务的冻结协议；真实评分有效性以对应attempt的冻结标记和worker校验为准。

本模块local队列模式的派发归属、指定ID领取、取消及恢复接入共享[执行队列](../execution-queue/README.md)；业务输入/结果契约保留，默认兼容模式不代表业务环境已切换。

## 队列代码维护导航

`jobs.ts`先冻结/领取评分，再执行独立评分，最后在事务中校验绑定并提交。`refreshScoreStep()`只汇总当前成功答案对应的最新评分；任务执行成功不等于报告有效或达标。`lifecycle/scoring.ts`的`runScoringEnhancements()`在评分事务连接释放后调用（jobs内沿用本地别名），避免嵌套占用连接；判断失败保留日志，不回滚已经完成的评分。维护时保留检查点与晚到结果校验，不重新调用模型来补数据库结算。

新派发队列只收集新增attempt ID，不设置内部复用分支；外部仍返回`reused:false`。活动评分仍409拒绝重复，已完成评分再次显式派发会创建新尝试，多模型整组登记及回滚保持。任务心跳使用`../attempt-heartbeat.ts`；执行选项在原钩子/外部调用边界内组装，提示词默认及API/Codex路由不变。

评分报告写入成功后先提交对应 artifact 与评分记录，仅在失败且确认没有已提交 artifact 时清理文件；成功路径不提前删除 `score.json`。数据库中的有效评分及版本绑定是后续达标/归档的依据，本地报告文件是可下载副本。

达标侧会兼容读取模型在草稿保存说明中明确报告的评分合计；历史逐项检查、争议及valid标记不附加为达标条件。完整原始评分记录保留，读取规则与多模型判定见[达标模块](../decisions/README.md#按模型分数直接判定)。

若评分调用成功但未提供可比较的明确分数，步骤仍可保留原报告与成功回执，达标保持waiting；页面/批量就绪判断允许用户显式重新评分。它不自动重评、不将旧报告改成成功达标，也不绕过已有活动任务及accepted保护。就绪口径复用达标入口的明确数值要求，旧validation标记本身不成为新的准入条件。

已归档题目由共享派发保护拒绝重复评分，不新增模型调用。

## 项目生命周期隔离

Work何时启用候选引文核验，由`lifecycle/projects/work.ts`注册的scoreProtocol决定；jobs通过统一策略入口选择，不再直接判断Work契约。执行器继续按冻结candidate_quote_check执行对应通用协议。旧任务绑定复核仅复用其原有标记，不给无标记历史任务增加字段或重算摘要。评分算法、指令正文、验证规则与达标门槛不随职责迁移改变。

本机明确新派发可在同一事务替代他机尚未开始的同范围待办；运行、结果未知和续作仍受保护，新派发失败则旧意图变更回滚。适用范围、共享状态兼容与验证边界见[执行队列的跨机准入](../execution-queue/README.md#他机未开始待办与本机明确派发)。

评分入队在工作流锁内先检查当前答案是否已有活动评分，再准备完整上下文；重复请求直接409，不因重复点击再次读完整材料。版本绑定与完整输入校验仍在新任务创建前执行。

评分上下文读取校验当前答案集合的answer_sha256、冻结输入摘要、题面版本、来源与成果呈现清单；发布时重新比较完整评分上下文摘要，避免旧结果覆盖新版本。绑定校验不是内容准入或作者输出格式审查。

多模型评分入队在同一工作流锁定事务内复用一次材料读取；每个答案仍分别验证输入与答案绑定。缓存为本次enqueueScore局部变量，事务结束即释放，不跨工作流/请求/执行/发布使用；worker领取与发布继续完整重读来源。

评分状态聚合在 `jobs.ts` 内声明SQL投影类型并复用共享答案摘要类型；历史单结果与模型集合分支保持原有读取和状态判断，不在这里增加格式准入。

返修准入与[返修建议模块](../revision-advice/README.md)共用：当前判定仍为`repair`时，不允许对旧题再次作答或评分，即使已有建议；须先重出题。检查位于工作流行锁内，在队列登记和结果变更之前。新题成功后按正常同版输入规则继续，原活动任务及历史尝试不由此自动取消。
