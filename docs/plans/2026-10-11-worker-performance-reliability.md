# Worker 性能与可靠性优化计划

## 目标与边界

降低 worker 对数据库连接的争用，确保任务、取消、返修和停止行为不回退。先修复会阻塞或饿死任务的控制流，再依据测量优化空闲查询；在明确做到新任务唤醒不慢于当前体验前，不增加队列轮询间隔。

不修改 CodeGraph、操作系统进程、业务数据和数据库迁移；不调整模型提示词、调用参数、判分、返修预算、业务并发上限及既有任务状态语义。代码与定向单测已完成；隔离 PostgreSQL 和真实 worker 运行验收尚未完成。

## 已确认依据

- worker 的 PostgreSQL pool 上限为 4 个连接（[db.ts](../../server/db.ts)）。
- 评分成功和失败分支会在评分事务连接释放前执行自动达标判定；达标判定会另行申请连接，多个评分并发收尾时存在连接互等风险（[scoring/jobs.ts](../../server/scoring/jobs.ts)、[decisions/jobs.ts](../../server/decisions/jobs.ts)）。
- worker Agent 执行器在申请并发名额时未传停止信号；并发槽位等待循环本身支持 AbortSignal（[worker.ts](../../server/worker.ts)、[concurrency.ts](../../server/concurrency.ts)）。
- 材料提取的任务取消没有接收 worker 停止信号；入库领取函数也没有停止信号参数（[materials/jobs.ts](../../server/materials/jobs.ts)、[intake-jobs.ts](../../server/intake-jobs.ts)）。
- Agent 队列固定按 skill、Codex 脱敏、出题、评分的顺序探测；前置队列持续有工作时，后置队列存在饥饿风险（[worker.ts](../../server/worker.ts)）。
- 本地 2026-10-10 worker 日志中，29 个日志文件、14 个实例，共有 42,165 条去重后的 `db.connection.waited`，最长 11,013 毫秒；其中 model API 20,229 条、Agent/评分通道 12,668 条、材料通道 6,528 条。该数据证明发生过明显连接等待，不单独证明每条等待的根因。
- 空队列已保持当前约 3 秒发现间隔；本次增加回归测试，防止以后将等待逐步扩展至 15 秒而增加任务启动延迟。
- 取消检查按连接池聚合，但普通任务和 skill 查询分组串行执行；过去第一组查询失败会跳过第二组，查询未设置数据库端时限，取消日志也可能继承单任务上下文。本次修复分组隔离、2 秒 `statement_timeout` 和日志上下文。
- 以上均为源码或本地日志事实；当前 worker 是否加载了这些工作区改动、真实故障是否由某一项造成，尚未验证。

## 实施顺序

### 1. 先恢复并固定调度语义

- 返修 worker 不使用新加的 15 秒空队列退避，恢复最多约 3 秒发现新返修工作的旧行为。
- 其余普通队列也暂时保留当前 3 秒派发发现上限。先改善连接领取和持有方式，不以增加用户可见任务启动延迟换取空闲省电。
- 固定 Agent 四类工作具有轮转公平性，保持现有 Agent 总并发上限和每类处理函数；任何持续就绪队列都不应长期饿死其他队列。
- 新工作仍由既有持久化队列领取，继续使用短事务、行锁和 `SKIP LOCKED`，不改变“用户派发普通步骤、worker 接续显式返修”的规则。

**验收：**模拟持续有 skill/脱敏/出题任务及评分任务同时就绪，证明每类均能获得执行机会；空队列时新派发的领取时延不高于现有约 3 秒；无重复领取、丢任务或自动推进普通工作流。

### 2. 消除连接池互等并让停止信号覆盖等待与材料任务

- 评分结果事务提交后立即释放客户端，再执行自动达标判定；评分成功/失败状态不得依赖判定调用成功，判定维持当前幂等行为。
- Agent 槽位等待接收 worker AbortSignal；停止后立即退出等待并释放本地 worker 循环。
- 把停止信号传入材料提取和入库处理，检查正在运行的本地文件操作、子进程或 provider 调用哪些能够中止；不能安全中断的部分需允许安全收尾，但不继续领取任务。
- 连接池继续使用现有上限 4，不通过扩大连接数规避连接生命周期错误。

**验收：**以 4 路评分并发压测完成与失败混合收尾，达标判定不出现连接互等；满 Agent 槽位时发送停止信号，worker 在调用自身可中止工作后退出；入库、提取停止后不再提交晚到结果，文件和数据库状态保持原有一致性。普通用户取消仍能使活动尝试停止并进入既有失败/取消处理路径。

### 3. 使批量取消有界、互不牵连且日志可归因

- 保留按 pool 合并活动尝试查询的减负目标；普通步骤与 skill 尝试任一类查询失败时，另一类仍继续检查。
- 为取消状态查询设定可验证的时间上限；失败继续重试，不因瞬时数据库错误把运行中的任务误判为已取消。
- 批量恢复/失败日志不能继承某一个任务的 AsyncLocalStorage 上下文，也不能伪造单一 attempt 归因；保留实例、查询类别和安全错误分类。
- 上游 AbortSignal 继续即时传播，数据库状态取消继续由持久化状态确认。

**验收：**覆盖两类任务同池并发、任一查询失败、慢查询、尝试消失、状态非 running、取消与 dispose 同时发生；普通及 skill 任务均能最终停止，不会因对方查询失败而永久漏检；日志不包含材料或凭证，且不把事件错误关联到某一题。

### 4. 根据现有日志优化查询，而非盲加索引或提高并发

- 按 `db.connection.waited` 和 `db.query.slow` 的时间线区分连接被事务占用、查询慢、监控采样、领取扫描及业务结果提交；基准按同一 worker 实例和时间窗计算 P50/P95/P99，不把不同实例的重复负载当作单机结论。
- 检查实际热查询及迁移已有索引，优先精简无任务时的重复扫描和非必要连接持有。任何新增索引先验证执行计划及写入代价，再单独决定是否需要迁移。
- 不先启用轮询退避、LISTEN/NOTIFY 或常驻连接等新机制。只有 3 秒轮询在修复上述问题后仍造成可测争用，且有可靠唤醒与超时回退方案时，再评估替代方式；任务首次领取延迟不得变差。
- 不修改日志保留策略，不通过删除历史日志、扩大 pool 或提高 CPU/Agent/API 并发掩盖争用。

**验收：**相同任务量与并发下，连接等待 P95 低于 250 毫秒、最长等待低于 2 秒，队列任务发现仍不超过约 3 秒；若环境噪声导致无法满足，保留测量结果，不宣称优化完成。确认 API、worker、模型和 Agent 仍遵守原并发上限。

### 5. 分层回归与实际 worker 验收

- 后端单元测试覆盖 worker 退避边界、返修活跃/空闲状态、Agent 等待取消、取消批次故障隔离、评分完成后连接释放和队列公平性。
- 用隔离 PostgreSQL 做并发和事务集成验收；测试领取去重、状态转换、取消、重启恢复和达标判定幂等，不操作真实业务题目。
- 经授权启动本地 worker 后，用合成队列做真实连接池/监控验收，再确认真实普通任务和显式返修各跑通一轮。对比同时间窗日志的等待分位数与任务发现延迟。
- 分开报告单元测试、隔离数据库、真实本地 worker 三种证据；不以类型检查或静态阅读代替运行验收。

**验收：**上述测试通过、隔离数据库无遗留活动尝试、真实 worker 无重复/丢失/饿死任务，功能状态与优化前一致，且指标达到第 4 阶段目标。没有授权或运行环境时明确标出未验收，计划不得标为完成。

## 不在本次计划内

Neon 套餐变更、迁移/远程数据库写入、CodeGraph、OCR/provider 改动、费用统计、业务 UI、日志清理、worker 多机部署，以及未被测量证实的系统级资源调参。

## 实施记录（2026-10-11）

已完成本地代码改动：

- Agent 四类队列成功消费后轮转；Agent 槽位等待传递 worker 停止信号。Agent/API 并发上限和各队列处理函数未改变。
- 空队列保持既有约 3 秒探测间隔，没有启用指数退避。
- 评分成功及失败事务均先提交并释放连接，再调用自动达标判定。
- worker 停止阻止新入库／提取任务领取；入库尚未进入材料事务时可将领取状态还原为等待，材料接收事务开始后安全收尾；提取停止或晚返回时不会发布结果，并将活动尝试重新排队。
- 取消状态按同池合并、分组查询，单组失败仍检查另一组；查询在数据库端限时 2 秒，取消日志不继承任务级关联 ID。

本地定向单测通过：`bun test server/worker-pool.test.ts server/concurrency.test.ts server/task-signal.test.ts server/scoring/jobs.test.ts server/materials/jobs.test.ts server/intake-jobs.test.ts`，55 项通过、0 项失败、136 个断言。评分测试使用临时模型目录，不依赖本机 Codex 登录状态。

`tsc --noEmit` 全仓检查未通过，当前仓库其他脚本、API、决策与评分测试等文件存在类型错误；按本次修改文件筛选没有发现对应诊断。`git diff --check` 通过。

尚未完成实际性能验收：没有连接 Neon／业务数据库，没有启动或重启 worker，没有运行真实模型或业务任务。因此连接等待 P50/P95/P99、峰值等待、真实 PostgreSQL 并发／事务行为、入库停止时的文件系统边界及真实队列无饥饿尚无运行证据；计划中的隔离 PostgreSQL 与 worker 压测仍需在安全测试环境完成。不得据此宣称连接等待目标已达成或真实业务验收通过。
