# 项目审查问题修复计划

## 目标与边界

修复复核后确认的四项缺陷，以及监控查询与中断导出的两项条件性风险。保留当前并行修改，不处理已降级的评分嵌套连接与自动判定重试。本次不改变作者 Codex 的权限、配置、工具、工作目录、提示词或模型输入，不迁移数据库、不重启服务、不调用模型。

## 实施顺序

1. 兼容契约：复用附件库 DOCX 路径校验支持逐附件及旧合并文件；旧作答缺少时长策略时按既有默认策略比较，不能匹配任意新策略。
2. 导出一致性：Excel 导出调用已有 DOCX 安全读取与指纹校验；重新出题在同一事务内使项目导出失效。
3. 异常恢复：监控数据库查询设置客户端等待上限；项目导出用专用数据库连接持有项目级 advisory lock，全部导出查询复用此连接；重置取得同一事务锁后，才把无执行者的遗留 running 导出标为失败。锁争用时拒绝重置或重复导出，不凭耗时猜测进程存活。

## 验收与风险

- 静态检查每条原始触发路径及异常收尾；查看完整本次差异与 git diff --check。
- 用户本轮未要求测试，遵守仓库规则：不创建或运行测试、lint、开发服务及真实模型任务。静态审查不能替代运行验收。
- 导出锁依赖 PostgreSQL 会话锁及同一 PoolClient 的数据库会话亲和性；直连或 session pooling 适用，transaction pooling 不属于已确认支持的运行条件，运行验收须核对连接方式。必须在 finally 解锁，解锁异常销毁连接，防止带锁连接回池。同项目同时导出返回409。
- 部署时 API 与重置逻辑必须同时加载新实现；旧进程不持有新锁，因此不能与旧版本导出并行使用新恢复逻辑。
- 文件校验只保证导出读取时的完整性，不能保证导出后用户不会移动或修改附件。
