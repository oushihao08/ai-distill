## 目标与现状

本机 CLI 向服务器 API 提交指定题目的材料处理或作答请求。材料操作由服务器完成入库、PDF 提取和 API 脱敏，CLI 查询结果并取回本机需要的管理文件；作答复用既有多模型队列，CLI 用固定请求标识查询尝试状态，答案通过共享数据库和现有结果接口读取。即使 CLI 断线，服务器仍继续已接受的任务。失败时保留明确的任务和 attempt ID，可查询；网络断开不会自动重复提交。

已有单题派发接口 `/api/workflows/:id/intake`、`/api/workflows/:id/redact` 和任务状态接口 `/api/attempts/:id`，CLI 已有 `step dispatch`、`attempt wait`。这些接口只创建持久任务，实际执行由 worker 领取。服务器与本机共享数据库时，现有领取 SQL 不区分执行机器；通用 `WORKER_MODE=api` 还会处理作答／评分队列，因此使用专用 `materials` 模式。当前 `material_root`、来源清单含本机绝对路径，而原件及部分产物在各机器自己的 `.storage` 中。因此只加一个远程 URL 无法闭环。

## 设计

1. **受限调用入口。** 服务器继续只监听回环地址，本机 CLI 通过 SSH 隧道连接。为远程材料操作增加独立 API 令牌，从两端 `.env` 读取；CLI 请求使用 `Authorization: Bearer`，服务器用固定时间比较校验。新增材料操作接口接收 `{workflow_id, mode, request_key}`，其中 `mode` 为 `intake`、`redact` 或 `intake-redact`；令牌也只供查询本次操作状态及下载本次材料管理副本。令牌不进入 URL、日志、任务快照或前端。原有本机 API 调用保持原契约。远程能力由单独的 `remote material` 命令调用，不改变其他 CLI 命令的 API 目标。
2. **任务归属。** 给材料步骤的 attempt 增加 `execution_target`，默认 `local`，旧记录按 `local` 解释；远程入口冻结为 `server`。入库完成派生的 PDF 提取任务继承同一归属，脱敏任务单独冻结同一归属。入库、提取、API 脱敏的领取、超时恢复和复用逻辑均按归属过滤，防止本机与服务器抢任务或跨机器复用同一 waiting attempt。服务器使用专用 `WORKER_MODE=materials`，只消费材料三类队列及组合操作；本机模式保持原有行为。
3. **来源路径与文件回传。** 用户已负责同步 `projects/` 到服务器。容器将同步目录挂到数据库现有绝对项目路径，派发前校验题目目录、来源文件清单及 SHA-256 与本机一致；路径无法对应时拒绝派发，不以同名文件代替。服务器入库写自己的 `.storage`，原文／脱敏文本仍走现有数据库产物。入库完成后，CLI 从服务器现有材料下载接口取回该题当前原件管理副本，按数据库中的相对 `storage_path` 原子写入本机 `.storage`，逐件核对 SHA-256；需要本机读取的其他文件型产物也按白名单取回。只同步本题产物，不同步整份 `.storage` 或凭证。
4. **服务器持久编排。** 接口把一次请求保存为材料操作记录，返回操作 ID；服务器材料 worker 根据记录派发／复用已有入库 attempt，等待包括 PDF 提取在内的可见步骤 1 成功，再派发／复用 API 脱敏 attempt，直到步骤 9 成功。每阶段记录 attempt ID、输入版本和状态；worker 重启后从持久记录恢复，同一操作重复请求返回原操作，不重复执行。步骤失败则将操作标为失败，不自动重做；来源或材料版本变化则停止并报告冲突。脱敏配置若为 Codex，远程接口拒绝，服务器不执行 Agent。
5. **CLI 查询与收尾。** CLI 发起一次请求后按操作 ID 查询；远端完成时核对当前材料版本和步骤状态，再下载并校验本机管理副本。CLI 断线不影响服务器执行；重新运行查询命令即可继续下载。下载失败只标记本机收尾未完成，不能把服务器脱敏改判为失败；本机文件齐全后才报告“可本机继续出题”。请求响应丢失时先按题目及本轮输入查询操作，不能盲目重发。

## 验收边界

- 本机普通派发仍由本机 worker 领取；服务器派发的三类材料任务只由服务器材料 worker 领取。两端同时运行时，同一 attempt 只能领取一次。
- 远端缺文件、哈希不一致、令牌错误、PDF 提取失败、脱敏失败、连接中断均停在明确阶段，不产生“已完成”假状态；后续本机出题能够读取数据库脱敏附件，本机原件预览也能读取已同步的管理副本。
- 仅在获得运行授权并完成部署后做真实 API、数据库和双 worker 验证；源码完成、静态核对和真实闭环验收分别报告。

## 远程作答扩展

本机 CLI 使用 `remote answer run|start|status --workflow <UUID> --request-key <UUID>` 调用服务器带令牌路由。服务器调用现有 `enqueueAnswer` 冻结题面、脱敏附件、模型集合和作答配置，并将 request key 保存在服务器归属的 ordinal 5 attempt；相同题目与请求标识重复请求返回相同 attempt 集合。新请求若遇到仍活动的作答，服务端拒绝，防止重复生成。服务器作答不支持项目步骤钩子；需要这类钩子的任务仍使用本机 worker。

专用 `WORKER_MODE=server` 只领取服务器归属的入库、PDF 提取、API 脱敏和无钩子作答，不处理 Agent 或评分。服务器作答附件正文写入既有 `artifacts.content`，因此本机 API 可校验和下载答案；CLI 状态接口只返回 attempt 状态与时间，不传回答案正文。Docker worker 服务已切换到该模式；实际部署须随代码发布，并应用现有 `034_remote_material_operations.sql`。

已做静态核对：`node_modules/.bin/tsc --noEmit --pretty false` 退出码为 0，`git diff --check` 通过。本轮未运行测试、迁移、模型请求或远程服务器调用，不能据此宣称线上闭环已验收。
