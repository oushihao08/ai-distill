# 第四步：出题与独立质检实施计划

目标：把当前成功的脱敏材料和冻结规则交给 Codex 起草，再由另一个独立会话质检；只有两次调用及程序校验通过，才发布第四步成功。沿用现有版本、队列、模型配置、执行器与页面，不新增调度框架。

## 实施路径

| 顺序 | 实施内容 | 验收依据 |
|---|---|---|
| 1 | 固定当前第二、三步的成功尝试、材料版本、附件指纹和完整规则快照；要求显式保存第四步模型配置 | 缺少前置条件拒绝入队；同输入／配置并发提交复用；配置和快照不随排队后编辑而改变 |
| 2 | 两个独立目录／会话依次起草、质检；起草生成题面、rubric、完整标答与能力声明 | 单元验证角色隔离、完整规则复制、错误题目阻断；真实 Codex 双调用留下会话和 usage |
| 3 | 持久化队列接入单条 Codex worker 通道；发布前复查输入、附件内容、会话及质检报告 | 无长期数据库事务；质检拒绝、取消、失联、版本变化不能发布成功；历史保留，标答私有 |
| 4 | 接入单题／批量 API、页面按钮、历史报告与下载，更新第四步迁移 | 类型检查、前端构建、隔离 PostgreSQL 集成验证；页面浏览器操作单独记录 |

## 输入与交付边界

- 输入仅为当前成功脱敏文本和当前绑定的完整冻结规则。复制全部 references/assets，不能只复制入口或跳过二进制规则附件。
- 起草者输出正式题面、当前附件引用、完整 rubric、完整标答和能力声明；不允许自报质检结论。
- 独立质检逐项检查材料依据、题目完整性、rubric 一致性、标答完整性、实际交付。任一检查不通过或有阻断问题，则第四步失败，报告保留，题目不发布。
- 公共 `authoring.json` 和工作流结果包括题面、rubric、版本、质检报告、角色会话与 usage。完整标答只保存在私有执行目录；第五步仅接收正式题面和脱敏附件。
- 当前第五步支持纯文字输入／答案、无工具。超出能力的题目明确失败，不降级执行。
- 重新出题使旧下游任务失效，但保留历史。失败可显式重新提交；自动内容返修、多模型、跨步骤自动推进不属于此次范围。

## 实施与验证状态（2026-10-08）

上述四项已接线。核心文件为 `server/authoring/executor.ts`、`server/authoring/jobs.ts`，复用 `server/authoring/validate.ts` 与 `server/codex/client.ts`。单题入口为 `POST /api/workflows/:id/author`；worker、批量第四步、工作流详情页、模型设置说明和题目报告下载已接入。`010_authoring_queue.sql` 已应用。

后端全量 572 项测试、1426 条断言、0 失败；前后端类型检查与前端构建通过。针对性测试覆盖两角色独立执行、私有标答、质检拒绝、能力不支持、入队前置条件、JSONB 指纹、材料内容变化及晚到结果保护。

真实数据库／Codex 验证脚本为 `scripts/verify-authoring-flow.ts`，结果见 [authoring-flow-results.json](../evidence/authoring-flow-results.json)。采用临时隔离 schema、合成脱敏附件及规则，通过实际 API 入队并由真实第四步 worker 执行两次 Codex 调用；第五步仅验证入队，不发起计费作答。质检拒绝和晚到结果使用注入执行，不能算真实模型失败实验。临时数据库及文件在脚本结束时清理。

未验收：真实法律卷宗的出题质量、浏览器按钮操作、完整八步自动工作流。本次结果不改变完整 MVP 尚未验收的结论。
