# Codex 工作流 CLI 与 Skill 实施计划

**状态：CLI 与 Workflow Skill 已实施，已进行定向单元测试和真实题目1只读接口核对。** 本文保留原计划边界；执行证据见 [实施验收](../evidence/2026-10-11-workflow-cli-skill.md)。真实模型完整重跑与 Codex 自主操作验收不在本次单元测试结论内。

## 目标

让 Codex 能按用户给出的项目、题目范围和目标步骤，调用现有本机 HTTP API，经持久化队列完成从材料入库到评分、判定、归档或导出的指定流程；中途按实际 attempt 和业务结果跟踪，严格在用户要求的目标处停止，不自行扩展任务。

采用 **本地 CLI + Codex Skill**，不新增 MCP。Skill 负责可调整的流程指令、范围解释、前置检查和停止规则；CLI 提供稳定、可检查的业务命令；现有 API、worker 和业务模块继续负责校验、入队、执行、版本绑定与结果持久化。

## 现状与设计依据

- 系统已有 Hono API、数据库持久化队列、独立 worker，以及 server/agent/ 的统一 Agent 调用契约。后端出题、评分等业务已使用现有 Agent 执行器；本计划不新建第二个 Agent 执行模块。
- 目前没有一个面向 Codex 的常规工作流 CLI。API 按单题或单个指定步骤批量派发；返回排队不等于执行成功，更不等于业务达标。
- 当前主流程有七个可见步骤：入库（含 PDF 内部提取）、脱敏、出题、多模型作答、逐答案评分、达标或返修、归档达标题目。Excel 项目导出是独立动作；项目级 skill 生成/采用也不是单题流程步骤。
- 稳定步骤身份是 shared/step-registry.ts 中的 key 与 ordinal；页面展示序号不能用作接口身份。PDF 提取是内部步骤，旧 ordinal 3 与独立审查 ordinal 10 不是当前流程门槛。
- 批量派发接口一次只处理一个步骤，最多 100 道题；多个模型和多个答案会产生不同 attempt。等待接口每次最长 30 秒。评分完成后系统可自动产生确定性达标判定；作答得分需逐模型与各自百分制阈值比较，所有模型都低于阈值才通过。
- 普通流程的通用自动推进已撤除。显式启动的返修链由现有 worker 接续。CLI/Skill 应让 Codex 作为外部编排者按用户授权逐步调用，而不是恢复后台自动推进。
- 项目 skill/ 是出题等业务规则；本计划新增的 workflow Skill 是“如何调用系统”的操作规则，两者不得混用。作答与评分的业务输入隔离继续由服务端执行器保证。

## 目标结构与边界

| 层 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 本机 API 与 worker | 当前状态与前置校验、任务冻结/入队、Codex 或模型调用、持久化结果及业务判定 | 不接收 CLI 自行重写的流程状态，不把所有步骤自动串联 |
| CLI | 以稳定步骤 key 调用现有 API；读取题目和尝试；标准化响应、错误、JSON 输出及等待 | 不直连数据库、不实现另一套 readiness/计分/返修规则、不重复调用 Codex |
| Workflow Skill | 将用户要求收敛为项目、题目范围、目标步骤和明确停止点；教 Codex 先查状态、再调用 CLI、核实结果 | 不固定某一期项目、不替用户更改设置或附件、不授权删除/重置 |
| Codex | 按用户本次指令读取必要信息，执行 Skill 规定的 CLI 操作，并汇报逐题/逐模型结果 | 不超出指定目标继续发布、导出或处理其他题目 |

CLI 默认只连接本机 API（默认 127.0.0.1:3100），不要求密钥或新增依赖。命令使用步骤 key，映射到 ordinal 时复用共享步骤注册表。只有真实 API 投影缺少 CLI 必要字段时，才做最小的向后兼容 API 增补；不先重做后端接口。

## 计划纳入的 CLI 能力

| 命令组 | 需要支持的操作 | 默认影响 |
| --- | --- | --- |
| 项目与题目 | 列项目、查看项目、列题目、查看单题和当前步骤；按用户明确要求创建项目或同步来源目录 | 查询只读；创建/同步必须显式 |
| 当前输入 | 查看项目规则/skill 文件指纹、项目模型集合和阈值；读取数据库中当前脱敏附件全文；查看题面、作答、评分、判定、产物和尝试历史 | 只读；默认不下载或展示原件 |
| 状态与就绪 | 查询步骤状态、就绪/阻断原因、活动 attempt 和 per-model/per-answer 任务关系 | 只读；结果依据服务端投影 |
| 步骤派发 | 显式派发入库、脱敏、出题、模型作答、评分、达标判定、归档；批量仅限明确项目和步骤范围 | 写入任务队列；一次只派发一个指定步骤 |
| 等待与结果 | 读取 attempt、按 ID 等待终态、读取产物及版本绑定 | 只读；终态不等于业务成功 |
| 返修与导出 | 显式启动/恢复返修链；对已达标题目执行归档；显式发起项目 Excel 导出并读取导出记录 | 各自单独命令；不作为评分后的默认动作 |

命令示例用于说明接口形态，最终语法在实施时按现有 Bun 项目约定收敛：

```sh
bun run ai-distill project list
bun run ai-distill question list --project <project-id>
bun run ai-distill workflow status --project <project-id> --ids <workflow-id,...>
bun run ai-distill material text --workflow <workflow-id> --redacted-only
bun run ai-distill step dispatch author_question --project <project-id> --ids <workflow-id,...>
bun run ai-distill attempt wait --ids <attempt-id,...> --timeout 1h
bun run ai-distill result show --workflow <workflow-id>
```

所有查询与派发命令提供机器可读 --json 输出；错误包含稳定错误类型、HTTP 状态和可用的 request/attempt ID。批量超过 API 单次限制时，CLI 可按 100 条分组，但不得扩大用户选定范围。

## Skill 的执行规则

Workflow Skill 作为通用的 Codex skill 存放于 skill/SKILL.md，不引用具体题目 ID、项目名称、固定模型或当期法律规则。主要指令如下：

1. 从用户指令明确目标项目、题目集合和终点；“全部”必须绑定到用户指定项目和步骤，不能默认为全部项目。
2. 先只读查看当前状态、输入版本、就绪原因、模型集合及活动任务；列出将执行的记录范围。服务端 readiness 是最终依据，CLI 不自行推导。
3. 每轮只派发本次目标中的一个步骤。按每道题、每个模型/答案保存 attempt ID；分别处理 queued、not_ready、failed、reused 等派发结果。
4. 对长期任务使用最多 1 小时的外层等待预算；每次 API 等待不超过其 30 秒契约，再轮询 attempt。到期仍运行时如实报告并停止等待，不自动取消或重复派发。只对安全的查询进行重试；写请求超时后必须先查状态，不能盲目重发。
5. 完成一个步骤后重新读取服务端状态和结果，区分请求已接受、attempt 终态、步骤执行成功和业务结论。模型答案/评分按模型与答案分别核对；达标以系统判定及当前绑定为准。
6. 只在用户目标包含后续步骤时继续。评分完成后即使系统自动生成达标判定，也只报告结果；除非目标明确要求，不继续归档、导出、返修、改设置或处理其他题目。
7. 需要改附件、重置结果、改模型/阈值/提示词、生成或采用项目 skill、删除题目时，先将其视为独立配置或破坏性动作，不从“继续流程”指令中推定授权。

简要流程卡应按当前步骤注册表说明每步输入、输出、常见阻断条件和可调用命令。Skill 不复制数据库模式、完整 API 字段清单或项目法律规则；接口事实以 CLI 帮助与当前项目 API/共享契约为准。

## 可顺手纳入的低影响改进

以下仅在实施时确认存在且与 CLI 直接相关才做，不扩大为后端重构：

- 用一个小型 HTTP 客户端统一 JSON 解析、非 JSON 错误、网络断开和状态码处理，避免 Unexpected end of JSON input 一类错误遮蔽真实 HTTP 状态。
- 对异步任务统一展示“派发结果 / attempt 状态 / 业务结果”三层状态，并按模型和答案显示 attempt ID、模型名、评分有效性、百分制分数与阈值比较结果，避免汇总状态误导。
- 在 wait 命令内部把最长 30 秒的接口等待组合成最多 1 小时的可中断轮询；读取可安全重试，写入请求不做无条件自动重试。
- 复用现有状态投影字段；若只有某个字段不足，再以最小兼容改动补齐，不把原始附件、提示词或无关模型数据塞进大响应。

这些属于提高操作可靠性和状态可读性的辅助改进，不改变题目设计、评分规则、阈值方向、worker 并发或业务判定算法。

## 验收标准

1. Codex 能根据自然语言目标，通过 Skill 与 CLI 查明指定项目/题目的当前状态，并给出将执行的精确范围；只读查询不会写入业务状态。
2. CLI 使用稳定步骤 key，调用现有 API；服务端负责 readiness 与输入冻结，CLI 保留每个批次、题目、模型/答案对应的 attempt ID。
3. 执行中刷新/重读可识别等待、运行、成功、失败、跳过及仍在运行；succeeded 不被展示为达标，评分执行成功与评分有效也不混为一项。
4. 多模型场景逐模型显示分数和各自阈值结果；“所有模型都低于各自阈值”才报告题目达标。版本或输入绑定失效时不采纳旧答案/评分。
5. 用户指定“做到评分”时，流程停在评分及其系统自动产生的判定结果，不自动归档或导出；用户指定归档/导出时才单独执行对应动作。
6. 长任务最多等待 1 小时，API 单次等待遵守 30 秒上限；等待超时不取消后台任务、不重新提交同一写请求。
7. 对命令、API 错误和部分失败均逐项汇报，不把批量中的失败隐藏在整体成功中；不得执行用户未要求的重置、删除、设置修改或额外题目处理。
8. 不增加 MCP、数据库表或迁移；CLI 与现有 Web/API/worker 共用同一业务规则。新增的 CLI 与 Skill 文档按项目目录规则说明，架构文档同步描述新增调用层。

## 明确不做

- 不恢复通用自动推进，不新增后台工作流引擎、第二套队列或重复的 Agent/Codex 调用器。
- 不新增 MCP，不直接读写业务数据库，不复制服务端 readiness、评分、阈值或版本绑定逻辑。
- 不把项目法律 skill、作答思路、标准答案或目标分数错误地传入作答/评分模型；其数据边界由现有服务端执行器保持。
- 不默认同步来源目录、上传/替换/删除附件、清空成果、改变模型与提示词、生成或采用项目 skill、发起返修、归档或导出。
- 原计划编制阶段不执行代码或运行操作；本次实施范围为 CLI/Skill、单元测试及只读接口核对，未运行真实队列/模型、写业务数据库或重启 API/worker。

## 依赖与风险

- CLI 运行要求本机 API 和 worker 可用；CLI 可以检测服务响应并报告 worker 状态，但不能替代 worker 执行或把监控心跳当作模型仍在生成的证据。
- API 默认用于本机且没有面向多用户的鉴权。本 CLI 仅作为本机工具；不得把 API 暴露公网或把本机 CLI 设计成远程多租户客户端。
- 当前工作树存在多处未提交改动。后续实施须先检查差异并保持本计划以外的用户工作；只修改必要文件。
- API 与运行中服务版本可能不一致。实现和验收要分别记录源码契约与实际进程版本，不从静态接口存在推断实时可用。

## 本计划不验收的结果

计划编制时仅产出本文件；之后已按授权实现 CLI、Skill、命令配置及定向测试。实施范围和结果以链接的验收记录为准。真实材料闭环、Codex 自主执行质量、模型答案质量和题目难度，仍须在单独授权的受控验收中判断。
