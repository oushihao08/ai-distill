# 工作流操作

通过仓库根目录的 `bun run ai-distill … --json` 操作现有 API。先读 `cli/README.md` 和 `bun run ai-distill --help`。本 Skill 规定如何执行流程；`projects/<项目>/skill/` 规定如何出题，交由现有执行器读取。

## 结构与阅读地图

- 本文件是操作入口，执行任务按下文规则进行。
- 理解分层、数据流、状态和扩展边界时，读 [架构设计](ARCHITECTURE.md)。
- 定位步骤、命令、接口或修改文件时，读 [文件与流程地图](MAP.md)。
- 参数与输出以 [CLI说明](../cli/README.md)、当前命令帮助和服务端响应为准；地图不替代当前实现，也不要求每次执行通读后端。

## 本次任务

按“用户当前要求 → 当前任务约定 → 适用配置与文档 → 默认流程”确定范围、操作和输出。API能力、实际状态及授权边界是执行约束，不能靠修改提示词绕过；无法满足时报告具体缺口，不擅自改目标。

确定项目、题目范围、起点、终点和操作类型。已有明确ID时直接查询对应对象；只有名称需要定位时才用 `project list`、`question list --project ID`。名称歧义时只询问缺失的选择。执行前简要说明选中的题目与终点；已有授权不重复确认，也不在每一步之间等待确认。只读查询不套用派发流程。

| 用户意图 | 处理方式 |
| --- | --- |
| 查询 | 读取所需对象并返回结果，不创建任务 |
| 续跑 | 跟踪已有活动任务；已完成步骤不重做，只派发授权范围内的就绪步骤 |
| 重新生成 | 先核对对应命令及服务端是否支持重做；当前CLI没有通用强制重做命令，普通批量接口拒绝已完成步骤时报告能力缺口，不冒充已重做 |
| 返修 | 仅按明确授权启动或恢复已有返修链；不把普通重新生成替换成返修 |

“全部等待出题的题做到评分”：只在指定项目读取状态，筛出服务端显示出题就绪的题目 ID；固定这组 ID，后续不会把新加入题目或其他题目带入。`--all` 仅用于用户明确授权的整个项目操作。示例不是默认范围。

## 执行

1. 派发前用 `workflow status --project ID --ids IDS` 查看 `ready`、`ready_reason`、活动尝试。涉及作答、评分或达标时按需用 `models show --project ID` 确认模型集合。需要正文才用 `question show`、`result show` 或 `material text --redacted-only`。就绪与绑定由服务端决定，不自行从 `waiting` 猜测。
2. 有活动尝试则跟踪其 ID，不重复派发。每次 API 调用只派发一个步骤：`step dispatch STEP_KEY --project ID --ids IDS`；若用户授权了连续多个步骤，Codex 应在核对当前结果后自行继续下一步，直到指定终点或遇到阻断，不把“单步派发”误解为“整次任务只做一步”。逐题读取 `dispatch` 与 `batches`，记录全部任务关联，不能只保存第一个模型。
3. 用 `attempt wait --ids IDS --timeout DURATION` 等待尝试。用户指定较短等待时采用该值，否则默认1小时；CLI单次外层等待最多1小时，接口单次等待不超过30秒。终态失败、跳过、等待到期、读取失败分别保留；到期或中断后先读取相同任务，不自动取消或重新派发。
4. 等待结束后重新读取题目状态和 `result show`。入库任务结束后 PDF 内部提取可能仍在运行，须跟踪返回状态中的提取任务。每个模型的答案和评分分别核对；失败题留在报告中，成功子集可继续到本次终点。未就绪时先读原因，不改配置绕过。
5. 评分完成后读取系统自动生成的达标结果；未生成时重读状态，确实就绪且用户目标包含判定时才显式派发判定。执行成功、评分有效、题目达标是三个不同结论。按服务端当前 `decision`、`model_scores` 汇报；所有所需模型均低于各自百分制上限才是达标，无效或缺失评分不能算通过。
6. 到达用户终点就停止。做到评分时可报告系统自动产生的判定，不继续归档、导出或返修。显式返修使用 `revision start/resume`；归档使用 `publish_export`；Excel 使用独立 `export create`。

## 任务关联与恢复

在当前对话的任务进度记录中保留：项目ID、固定题目ID集合、操作类型、目标步骤、逐题当前步骤、全部attempt ID及可取得的模型/答案关联、已完成项与阻断。派发后更新；长任务交接或上下文压缩前将这些字段写入交接摘要，不只留下“运行中”或总体成功数。

恢复时先按记录ID读取服务端当前状态。关联缺失时重新查询确认，不猜测最新任务、不重复派发。CLI本身没有持久化运行账本；对话记录或交接摘要不能替代服务端事实。

## 步骤卡

以 `step list` 为当前身份来源，不使用页面序号。

| key | 输入 → 结果 | 阻断时检查 |
| --- | --- | --- |
| receive_materials | 来源清单 → 入库与内部提取 | 目录、材料、PDF提取尝试 |
| redact_materials | 入库正文 → 脱敏正文 | 入库完成、脱敏配置和错误 |
| author_question | 脱敏附件、当前项目skill、步骤设置 → 题目包 | 附件、skill和任务错误 |
| model_answer | 题面、允许附件 → 逐模型答案 | 当前题目绑定、模型集合、凭证错误 |
| independent_score | 同版题面、rubric、脱敏附件、答案 → 逐答案评分 | 作答终态、有效答案、评分错误 |
| accept_or_revise | 有效评分、各模型阈值 → 系统判定 | 当前绑定、评分有效性、所需模型齐备 |
| publish_export | 当前达标题目 → 归档产物 | 当前判定为accepted；Excel另行导出 |

## 异常与边界

- 写请求网络失败或响应异常可能已经入队。保留返回批次、题目和任务 ID，先查状态；不得盲重发。只读查询可有限重试；业务失败不自动重跑。
- 退出码2意味着部分失败/未就绪，3意味着等待到期；退出码0也不表示达标。具体状态看 JSON，不能将整体成功覆盖单项失败。
- 继续流程不隐含授权同步来源目录、改附件、改模型/阈值/提示词、重置、删除、生成或采用项目skill。用户明确要求时才单独操作；CLI 不提供的操作先报告，不能直接写数据库。
- 流程执行授权不隐含启动/重启服务、迁移、安装依赖或修改代码；这些是单独任务，按用户明确授权及项目规则处理。API/worker不可用时报告实际阻断；监控心跳不能证明供应商仍在生成。

## 按任务汇报

- 查询：返回用户所查内容及必要的不确定项，不附加无关模型评测。
- 执行：逐题列出已完成步骤、失败/未就绪原因、仍活动的attempt ID及是否到达目标。
- 评分/达标：在执行结果上补充逐模型得分、满分、百分制、阈值、评分有效性和系统判定；缺失项明确标出。
- 下载/导出：报告生成记录、文件路径及实际结果，不以命令成功代替文件已交付。

按用户要求控制详细程度，只披露任务必要内容，不把部分成功汇总成全部完成。
