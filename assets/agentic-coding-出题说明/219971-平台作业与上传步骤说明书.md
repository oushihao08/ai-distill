## 一、进入平台之前：在本地把题做成可评测的题包

1. **确认任务类型与材料资格。**先读当次项目说明、作业规则和数据脱敏指南；确认材料有权使用、已按要求脱敏。不要把“已经脱敏”当成“来源可提交”，也不要把另一项目的公开裁判文书口径直接搬到本项目。第二期说明禁止搬运开源数据集、模板化题目和全过程 AI 撰写；领域判断与平台介绍须由专家本人实质核对。
2. **确定真正的编程目标。**写出业务输入、程序要改变的行为、可观察输出，以及哪一个专业判断必须影响代码结果。第二期在线说明描述了先做正确实现、再引入专业语义错误的制作流程；若采用从空入口开发的形式，应先确认当次任务类别接受该形式，不能仅凭可运行就推定符合制作流程。
3. **建立题包根目录。**根目录直接放 `task.toml` 和 `instruction.md`；`environment/` 放 Dockerfile、供作答者使用的初始代码和可用材料；`solution/solve.sh` 放评审用参考修复；`tests/test.sh` 放评审用评分入口。需要其他文件时按实际任务增补。不要把测试期望、参考解或评分记录复制到候选人可读的环境中。
4. **写清给被测模型的题面。**`instruction.md` 写目标、入口、输入、输出和必须遵守的约束。作答必须知道、且决定唯一正确行为的日期算法、金额规则、状态含义、异常行为，不能只藏在测试里。`solution/` 和 `tests/` 可以实现标准与评分，但不能补写题面遗漏的必要条件。
5. **核对配置与运行边界。**`task.toml` 至少满足当次 schema 和必需字段。219971 实际被 `schema_version` 缺失、`[task].name` 缺失拦截过；后者要求“组织/题目标识”格式。本题还因整个作答环境断网、Docker 默认用户及候选用户主目录配置出错而失败。把平台模型调用、候选程序和评审进程分别看待，不照抄旧题的联网、身份、时限和资源值。
6. **在允许的范围内验证同版题包。**核对 Docker 能构建、初始状态得低分、参考解满分；错误解应在对应业务点失分，合法等价解不应误扣；崩溃、坏输入和挂起能正确退出或收尾。记录使用的版本、命令、输入与结果。这里是本地验证，不能替代平台 R1、Oracle、T1、R2。

可先用下列只读命令检查题包结构，路径换成自己当前题目的目录：

```sh
find '/你的题包目录' -maxdepth 3 -type f -print
```

本地 ZIP 适合作备份或按页面支持的方式传输。**219971 最终参与评测的是 Web IDE 仓库已推送的文件，不是本地 ZIP 本身。**

## 二、领取题目并进入作业页

1. 打开 [TalentsAI 专家工作台](https://www.talents-ai.com/expert/dashboard)，登录自己的账号。
2. 从“我的项目”进入“【Code】Agentic Coding x 交叉领域”，选择“去出题”或当前页面显示的“开始作业”。先核对项目名称和题号，再进入对应作业页；不要在旧题或其他项目页操作。
3. 阅读“项目说明”页的作业方式、资格、题包要求和提交期限。既有说明提示领取后 72 小时未提交会清理；以当次页面显示的期限为准。
4. 如出现“开启工作模式”“授权录屏并开始”，按平台提示由作业人完成浏览器和系统录屏授权，确认页面出现正常的 REC/计时状态。离开作业时按平台功能暂停或结束。该步骤是平台的工作记录要求，不是检测按钮，也不应绕过。
5. 进入左侧“作业区”。检查必填的领域与题目标签；219971 当时选择了“民事”和“A.1 代码开发（Coding）”。标签要与题目真实工作类型一致，不能用改标签来回避题包要求。作业页右侧与底部可能有自动保存提示，但实际保存状态仍应由页面确认。

## 三、把题包放进 Web IDE，并使远端真正收到

1. 在作业区打开本题的 **Web IDE**。先核对 IDE 顶部的仓库/题号和工作目录，219971 的仓库工作区是 `/home/workspace/project`。不要把文件写进另一题的 IDE。
2. 通过 IDE 提供的文件管理器上传文件或目录；如果页面只接受文件，可在目标目录逐项上传，再恢复题包结构。上传 ZIP 只是传输一步：若使用 ZIP，必须在 IDE 工作区解包并确认根目录下存在实际的 `task.toml` 等文件，不能只留下压缩包。遇浏览器权限拒绝，按浏览器/平台正常授权或 IDE 支持的方式处理；也可直接在 IDE 中创建、编辑相应文件，不把反复点击当作已上传。**219971 曾尝试文件管理器上传但遇浏览器权限拒绝，最终成功路径是 IDE 内文件同步并推送 Git；不能把该次上传尝试写成上传成功。**
3. 在 IDE 文件树逐项打开核对：`task.toml`、`instruction.md`、`environment/Dockerfile`、初始代码/材料、`solution/solve.sh`、`tests/test.sh`。特别检查材料是否进入正确目录，评审文件没有进入作答镜像；忽略本机 `.DS_Store`、临时输出、敏感凭证。
4. 在 IDE 终端确认当前 Git 仓库状态。先看已有改动，避免覆盖他人或用户正在编辑的文件。按当次仓库分支提交并推送；219971 使用 `main`，新题不能盲用。可用命令如下，提交说明与分支名按当前题目替换：

```sh
pwd
git status --short
git branch --show-current
git add task.toml instruction.md environment solution tests
git commit -m 'Add agentic coding task package'
git push origin main
git status --short
git rev-parse HEAD
git rev-parse origin/main
```

5. **核对推送真的完成。**`git rev-parse HEAD` 与 `git rev-parse origin/main` 应一致；`git status --short` 无漏提交的本次题包文件。若平台页面或执行记录显示所测提交 SHA，再与本次 SHA 核对。只看到“文件已上传”或 IDE 里有改动，不能说明远端版本已更新。若本地还保留 ZIP，同步更新 ZIP，但它不能代替 `git push`。

## 四、填写作业页的题目构建介绍

返回“作业区”，依次打开左侧四项。219971 页面对应 **Prompt、环境思路、测试思路、参考解思路**；这些都是向质检专家说明题目构建的文字，和 `instruction.md` 的全文用途不同。写完每项查看字数提示及保存状态，四项都要与**刚推送的同一版本**一致。

| 栏位 | 应说明的内容 | 不应填入 |
| --- | --- | --- |
| Prompt | 工作场景、核心编程任务、输入输出和专业难点。219971 当时此栏要求至少 100 字；以当页提示为准。 | 题号、单字占位、整份 `instruction.md` 机械粘贴、参考答案。 |
| 环境思路 | 基础环境、初始代码、材料所在位置、运行依赖与环境边界。 | 把本地 ZIP 路径说成平台已收到，或把“程序离线”写成整个模型环境断网。 |
| 测试思路 | 评分维度、权重理由、正常/错误/异常路径，如何识别专业语义错误。 | 泄露隐藏期望值、宣称未运行的测试 PASS。 |
| 参考解思路 | 参考修复的关键判断和实现路径，以及如何证明它与题面一致。 | 将完整参考解放进模型可见的题面，或把本地满分说成官方 Oracle 已通过。 |

平台要求专家本人用自然语言介绍构建；AI 辅助草稿须按项目规则进行实质专业核对和修改，不能通过改变粘贴方式冒充本人原创。字段缺少时即使 IDE 题包完整，也会使正式提交资料不完整。

## 五、在评测区发起一次检测

1. 打开“评测区”，先核对题号、剩余检测次数、当前是否在冷却期、远端提交 SHA 和本次介绍文本。219971 页面总次数为 10；一次失败也占一次。不要因别的题的通过线相同就认定本题无须检查。
2. 点击一次“**保存并检测**”。页面会出现确认框，提示 IDE 修改需先提交并 `git push`；确认后以新出现的执行记录和 Transaction ID 证明真正发起。按钮禁用、加载中或已出现同轮 Transaction ID 时不要再点。
3. 依次看四阶段：**R1 → Oracle → T1 → R2**。R1检查结构、题面/环境/评分/参考解等；Oracle检验空白状态和标准解；T1看被测模型是否正常完成及得分；R2做深入质检。后一阶段通常要等前一阶段通过。每一阶段分别记开始/结束时间、结论、得分、报告和所测版本。
4. 219971 最终轮的页面门槛是 R1、R2 各 ≥80/100，Oracle 初始 NOP ≤0.100、参考解 1.000，两名 T1 模型得分各 ≤0.700。**这是该题该轮观察值，不是新任务必然相同。**T1 未检测到作答、零 token、安装异常或超时都不是有效的“低分通过”。
5. 正在运行时只能读取当前轮状态。219971 曾出现通用提示仍写“点击保存并检测”，而按钮实际上禁用、T1 已有 Transaction ID；应以阶段状态、按钮状态和执行记录判断。等待很久也不自动等于卡住，不因刷新/重连 IDE 就重开评测。

## 六、失败后怎样返修并重测

1. 读**本轮**完整报告，先定位是 R1 配置、Oracle、T1 作答环境/模型表现，还是 R2 的专业与工程质量；记录版本和实际报错，不用旧轮报告推断新版。
2. 只修报告证实的问题及其直接关联。例：`invalid_schema_version` 修 `task.toml`；模型安装报 `/nonexistent` 权限错误，修 candidate 主目录；R2 指出验证器无法拒绝无关引用，要改评分语义，而不是增加任意难度门槛。
3. 修改后先检查题面、初始环境、参考解、测试、四项介绍是否仍同版；做与改动风险相称的本地验证，再在 Web IDE 提交和 `git push`，核对远端 SHA。**一轮正在评测时不要改它的待测版本。**
4. 若页面要求失败后等待 30 分钟，从该轮**实际失败完成时**起算；冷却结束且按钮开放、修复已推送后才启动下一次。别用反复点击试探冷却。剩余次数少时先完成报告复核和同版检查。
5. 大改的判断看核心任务、关键输入和评估能力是否改变。第二期说明要求大改另领题号；配置补齐或直接修复原问题不因文件多就自动算大改。

## 七、四步通过后的正式提交与后续状态

1. 评测区出现“四步通过”后，回作业区再核对标签、四项介绍、远端提交、附件资格和脱敏状态；查看“执行记录”保存最后一轮分数及报告。四步通过说明**自动检测达标**，不等于人工质检或结算完成。
2. 页面底部“保存”和“提交”是不同动作。“保存并检测”也不是正式“提交”。正式提交前，作业人须读懂页面当前的数据协议与事实声明，**只在内容真实时自行勾选**；材料使用权、个人信息授权或不存在受限数据等声明不能由程序或助手代替判断。
3. 确认正式提交后，核对页面是否从“标注／进行中”变为后续环节，并保存题号、页面链接、最终仓库 SHA、四阶段结果和提交后的状态。219971 的现场结果为四步通过后显示“**质检／待领取**”，这只证明已进入后续质检队列；人工质检结论、费用结算须等平台后续记录。
4. 若平台显示提交失败或仍在编辑环节，按页面实际错误处理，不能凭按钮点击或本地文件推断提交成功。
