## 三、题目为什么具有领域价值

这题的实际工作目标是整理申请执行材料，让程序输出可复核的候选申请与风险，而不是生成一篇法律意见。程序要从 DOCX 原文提取当事人、主文、利息、费用、送达和公告信息，并把每个确定事实指回原文段落。

难点来自**多步法律判断改变程序行为**：起诉请求、庭审陈述、裁判认定、主文各有不同证明作用；借款交付对象和借条署名不能直接替换主文义务人；约定利率不能冒充裁判支持的利率；代收不能写成本人签收；有公告日数计算也不能推定判决生效。`unresolved`、`same_basis`、`separate` 三种条件改变提交决策，但不能改写每卷已知权利。双卷冲突、单卷、改名、重复文件、日期变化和无效输入共同检查这些判断是否稳定。

可复用的设计链条是：**材料原文 → 事实与法律性质 → 程序分支/计算 → 可追溯输出 → 对应断言**。每个高价值判断要有具体错误行为和可核对后果。单纯增加附件数量、隐藏必要规则、堆字段或让模型超时，不能证明专业难度。

本题以固定两份材料和给定变化条件为范围。R2 对可迁移性有折减；新题若确实要处理新案件，需要另行设计输入和验证，不能把本题的文本锚点直接视作通用法律解析器。

## 四、题包、环境与评分的实际要求

完整题包至少要形成可运行的 `task.toml`、`instruction.md`、`environment/Dockerfile` 与初始代码、`solution/solve.sh`、`tests/test.sh`。平台四个介绍栏是写给质检专家的构建说明；`instruction.md` 是给被测 Agent 的题面。两者必须同版，不能互相替代。作答镜像只放候选入口和可用材料；参考解、测试、预期结果及验证记录留在评审侧。

本题最终配置的关键关系：平台环境 `network_mode="public"` 保障初始化与模型工具；交付程序要求离线，评分器在低权限候选进程及其子进程上拒绝创建 socket。Dockerfile 最终 `USER root` 供平台启动，`agent.user=candidate` 且 candidate 有可写 `/home/candidate` 和 `/app/main.py`，`verifier.user=root`。评审目录须 root 私有，候选不能读测试/参考解、改材料或 reward；仅写“禁止访问”不构成权限隔离。**这是本题在该平台的适配结果，不是所有任务的通用 Docker 配方。**

验证器要以实际执行结果计分：初始空实现为 0，参考解为 1；15 组权重合计 1，核心业务约占 0.70。正常的局部错误只丢对应权重。应检查类型、范围、单位、金额、日期端点、来源引用语义、单卷与多卷的完整字段，以及不允许出现的无依据事项。允许合理的额外字段或诊断输出时，评分器不能因其存在误扣。`True == 1` 之类的语言比较陷阱会让错误布尔类型蒙混过关，须显式检查类型。非零退出、错误类别、旧报告撤销、缺失/损坏输入及候选挂起，都要有可观察的失败路径。

参考解满分只证明标准路径可通过。还要用有针对性的错误实现验证“该错应失分”，并检查合法等价表达不会被误扣。评估题目难度必须看**模型正常完成后的官方得分与轨迹**；零 token、安装失败和超时不能当作低分样本。第九轮两模型得分虽低，R2 也观察到它们的自建检查声称通过而正式业务断言未通过，提示内部自验覆盖不足，但没有据此证明评分器没有任何缺陷。

## 五、一次检测前的最短核对顺序

1. **资格与材料**：核对原始材料来源、可用范围与脱敏；真实案卷复印件不自动等于可公开提交资料。项目禁止搬运开源数据集及全过程 AI 撰写；介绍栏需要专家本人实质核对和撰写。不要借另一项目的材料资格结论。
2. **同版契约**：逐项对齐题面、TOML、Docker、初始代码、参考解、测试和四栏介绍。特别核对谁可以联网、谁运行候选、谁写 reward、哪些日期/金额未知、`null` 与状态字段的含义。
3. **有限的实际验证**：按本题需要确认 Docker 能构建，独立干净容器中 NOP=0、参考解=1，崩溃/挂起可收尾，权限边界可观察；只针对具体风险检查错误解和合法等价解。记录真实命令、退出码、reward、输入及文件哈希。不要把静态审查写成已执行测试。
4. **远端冻结**：只同步本次改动，逐文件哈希核对，确认 Git `HEAD=origin/main` 且工作区没有漏提交；保存提交 SHA 和输入摘要。平台检测只读取已推送版本，本地 ZIP 更新不能替代远端同步。
5. **单次发起并跟踪**：核对题号、剩余次数、冷却和按钮，再点击一次“保存并检测”；以新 Transaction ID/执行记录确认真正开始。R1、Oracle、T1、R2 各自记分和结论；尚在执行时只读取状态。最终正式提交与数据/法律声明属于独立步骤，不能把四步自动通过当成人工质检或资格声明已完成。

## 六、常见失败写法与修正原则

| 不好的做法 | 会导致什么 | 修正原则 |
| --- | --- | --- |
| 看到“离线运行”就把整个容器断网 | R1 阻断平台模型调用 | 先区分平台联网与交付程序联网，按实际运行对象做隔离。 |
| 只设置 Docker `USER candidate` | 可能使平台安装或启动失败 | 核对平台门禁、`agent.user`、实际进程 UID、主目录和写权限。 |
| 只检查 Docker 构建及 Oracle 1 分 | R2 的隔离、异常与范围漏洞仍存在 | 追踪候选进程、评审文件和奖励的真实权限及失败路径。 |
| 给候选程序加很短的时限，或把 T1 超时视作低分 | 误杀合法实现、误判难度 | 分清作答与评分时限，依据实际流程设必要看护并记录原因。 |
| 只检查必须出现的正确事项 | 无依据的额外义务人、财产或冲突也可能得分 | 同时校验允许集与禁止集；引用必须支持对应事实性质。 |
| 单卷只检查记录数，不检查完整字段 | 跨卷事实污染难以发现 | 单卷重跑关键身份、主文、利息、费用、送达、来源和申请状态。 |
| 把 `0644` 当成所有人只读，或把只读挂载当作不可读 | 参考解可能无法写入口，测试也可能泄露 | 结合所有者、目录权限、挂载语义和实际 UID 验证。 |
| 本地修复后直接检测 | 远端仍测旧版，消耗次数 | 核对每个文件哈希、提交 SHA、推送状态及当前轮引用的仓库版本。 |
| 根据等待时间推断 T1 卡死或重按检测 | 混淆排队、执行与失败，浪费次数 | 看执行记录、trial/Transaction ID 和明确结束原因。 |
| 给质检报告填“通过”或预估分数冒充实测 | 无法追溯 | 分别标注静态发现、本地运行、外部模型审查和官方结果。 |
