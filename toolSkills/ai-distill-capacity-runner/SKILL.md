# 本机满载调度

目标：只处理用户指定的主项目、期次与材料/题目，在当前实际并发内持续补位，优先占满 **Agent** 槽位，独立补齐 API 作答。任务结束后关闭本次定时任务。

## 入口与范围

1. 先读仓库根 `AGENTS.md`、[操作Skill](../../skill/SKILL.md)、[流程地图](../../skill/MAP.md)和[CLI说明](../../cli/README.md)。命令参数以当前 `cli/commands.ts` 为准，不复制旧命令。项目内容规则另读该项目的规则与Skill。
2. 从用户要求解析主项目、期次、范围和终点，通过API确认 `project_group_id`、期次 `project_id`、`phase_no`，禁止只用显示名称派发。名称有歧义时只询问缺失选择。
3. 默认终点是完成评分并读取已有系统判定；入库、提取、脱敏和建题是授权材料范围内的必要前置。只处理用户指定材料或该期明确授权的已加载范围，不从全局库随意挑新材料。生成题目的场景、角色、方向等按项目现有规则；缺失关键要求则记录缺项，不编造。
4. 只写Skill不等于启动任务。用户指定执行目标后才创建调度。默认直接调用本机HTTP API；CLI是参考和可选客户端，仅在用户明确要求命令行时使用。不得直连数据库或手工代替程序执行脱敏、出题、作答、评分。

## 建立5分钟定时任务

- 使用应用的 `automation_update`，创建当前会话的 heartbeat，每5分钟唤醒；不用系统cron或后台死循环代替。先检查同一主项目、期次、执行机的现有调度，接续匹配记录，不重复创建消费者。
- 创建前在 `.storage/automation-runs/<本轮ID>/state.json` 保存：目标身份、API地址与本机 `executor_id`、授权材料/题目范围、终点、优先级、已知job/attempt/request-key、阻断和调度ID。创建响应后立即写回真实调度ID。凭证、材料正文、答案不写入此记录。
- 定时任务提示词必须写明本文件的**绝对路径**、state文件绝对路径和真实项目/期次ID；要求每次先读取它们再核对API。不能只写“继续之前的任务”。配置周期时遵循工具当前契约，不向用户输出原始调度表达式。
- 创建后立即执行第一轮，不先空等5分钟。状态无变化保持静默；仅报告实际完成、影响推进的新增故障、需用户决定或全部完成。

## 每轮：先核容量，再补位

### 读取真实状态

合并独立只读请求：

- `GET /api/system/concurrency-settings`：用 `active.agent` / `active.llmApi`，不把已保存但未生效的 `settings` 或安全上限 `limits` 当成现有容量。
- `GET /api/system/execution-queue` 与 `GET /api/monitor`：确认本机执行器、worker健康、内存派发状态，以及本机队列 `items` 的 `lane/state`；只计算该机实际消费者可领取的任务。
- 目标期次的状态、已加载材料、job和attempt：通过流程地图定位当前API，按明确ID批量读取下一步 `ready`、当前绑定和活动尝试。新库题不机械执行旧ordinal1/9；材料任务走library入口。

Agent、API分别核算，模型池有空闲不必等另一个池。分类依据冻结配置和队列lane：出题通常Agent，作答/评分仍核对实际provider；提取及内部任务不一律算作API模型请求。全局PG计数、`snapshot.tasks`循环数量、仅标记running的步骤都不能单独证明本机模型占槽。监控心跳过期不能证明任务已停止；受影响池容量未知时不猜剩余名额，其他已知健康池仍可推进。

### 补满Agent并预排下一轮

对每个池，以当前活动并发为 `C`、本机可执行运行任务为 `R`、已确认可消费的排队任务为 `Q`：

- 有就绪任务就立即派发，不等待其他题或整个阶段结束；首要消除Agent空闲。评分与出题竞争Agent时，结合用户优先级、任务等待时间及能否尽快释放下游安排，不能只做容易派发的一类。
- 预排**最多一轮额外就绪任务**：本轮新增数不超过 `max(0, 2*C - R - Q)`，并受实际就绪数量限制。它是排队水位，不是提高运行并发；worker仍通过程序共享槽位领取。已有排队足够时不再堆积。
- 这样任务结束后worker能立即接续，避免只在5分钟检查点补一题。若预排任务不能被当前worker范围领取，不把它算作可补位队列，并报告范围不匹配。
- 出题完成即安排该题作答；答案满足服务端评分前置即安排对应评分，不等其他题完成。多模型作答/评分可能一次生成多个attempt，必须按预计新增调用数留预算；无法准确拆分时仅提交一个可核算的最小批次，再回读队列。
- 按同一步合并明确workflow ID的批量请求，不用无条件 `--all` 扫全库。每次派发保存全部返回ID并回读；某池满载时继续处理另一池、必要材料准备或只读核验，不反复轮询同一任务。

队列排满不等于Agent实际满载。离开本轮前核对实际运行/排队；Agent未达到 `C` 时记录具体原因：无ready题、前置API未结束、材料/配置缺项、worker未消费、内存暂停或状态未知。不能把“已派发”写成“已完成/满载”。5分钟轮询和依赖等待无法保证每秒都满载，不能为凑满制造任务。

## 正确推进与恢复

- 模式读取数据库：`aliases`走程序Agent化名，`original`跳过脱敏，使用完整成功提取；不新建mask任务，不更改模式以便推进。建题后出题、作答、评分使用同一冻结来源。Work一包一道；其他项目按各自规则。
- 同题同一步有活动attempt或同版本library job即跟踪原任务；已成功且绑定有效不重做。请求响应未知先用原ID/request-key查证，不更换key盲重发。恢复时服务端状态为准，本地state只帮助定位。
- `draft`、未达标、校验失败、`needs_review`分别记录原因。未达标不等于程序失败，不自动重出；失败重试/返修仅在用户明确授权的对象和次数内执行，不把取消伪装成失败结算。
- 本轮是用户授权的外层调度，不恢复服务端通用自动链。不能调整并发、模型、推理强度、提示词、阈值、来源和规则以填槽；不自行新增worker、重启服务、迁移或安装。低内存暂停尊重程序；服务不可用时保留任务ID并报告，不反复排队。
- 每轮结束更新state：逐题阶段与活动ID、两池运行/排队、缺口及原因、已到终点数量、上次核实时间。不得把运行中题记为失败或跳过后另起重复题。

## 停止条件

- 授权范围全部达到终点且没有本轮活动/未知请求：回读确认，删除或停用本次heartbeat，汇报完成与未达标数。默认不继续归档、上传或登记，除非用户另有授权。
- 尚有能推进或正在运行的任务：继续5分钟调度。全部剩余项都需人工处理且无在途任务时，保存具体阻断，暂停本次调度并通知；不能无限空转，也不能宣称完成。
- 用户要求停止：关闭本次heartbeat；后台任务是否取消由用户另行决定，默认保留在途任务。只操作本次调度ID。
