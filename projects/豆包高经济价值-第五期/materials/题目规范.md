# 题目规范

出题先读 `出题问题.md`，按那里的标题和字段交稿。成稿里给人看的文字按本文写。评分只按 `官方评分标准.md`。本文和那份评分标准不一致时，以 `官方评分标准.md` 为准。培训稿里的四分制、权重、一票否决不用。

## 给人看的部分要像承办人写的

作答思路和标准答案是承办人自己的说明。质检要能当一份意见读下去，不要读成模型的检查单。

这两部分不用表格。难点、采信、对照、待核实，都写成连贯的话：材料怎么读、哪一句为准、写错了会变成什么结论。题面如果要求模型交一张表，标答里同一内容仍按文书叙述，不再铺一张同样的表。

不要写「模型只能看到 prompt」「本条得 0」「内部难点清单」这种出题备注。思路里直接说自己怎么看卷宗。标答按交给合伙人的意见来写，不要按考点序号往下填，也不要每段都用同一句式，例如通篇「须写出」「不得」「不能」。

题面像给同事布置一件要签字的活：谁来做、交什么、拿去拍什么板。不要把对照项写进题面，例如当事人、借款日、主文是几个人、利率、送达有没有完成。这些留在附件里，由考点去查。题面一点破，这条考点就废了。

考点可以写得紧。官方要的就是怎样算通过、哪种写法这条是 0。这段给判分用，不必改成散文。不要把考点的句式抄进思路和标答。

## 评分

难度和判分只按 `豆包高经/官方评分标准.md`，不另起一套。出题时按那份执行，下面只留不能记错的几条。

条目 15 到 20 条。一条只查一件事，并列的结果拆开。每条 0 或 1，等权，总分是得 1 的条数除以条数。每条先写通过标准，再写何种写法这条得 0。不设权重、倒扣、一票否决。

格式、结构、常识不能占到接近一半。每个难点至少有一条考点去查。题面已经点破的难点，这条不算。

能唯一确定的结论写死。半开放的写必须写到哪些点、不能出现哪些错，不要把标答一种写法当成唯一解。等价说法给 1。判的是产物里有没有那句话、有没有踩零分条件，不看文采。上游写错带下来的下游，每条仍查不同的事，标答里说明连带，避免同一句话扣两次。

模型只收 prompt 和附件。思路、标答、考点不给做题模型。官方分数以机标为准。自己拿模型跑只是估难度，不能在成稿里写成已经过线。合格线仍是得分不高于 50，并且执行不少于 50 步或运行超过 40 分钟，满足一项即可。

自测按 `官方评分标准.md` 第 4 节：先审考点，再盲评，逐条留下原文。不看标答打分，不按「这题应该压到 50 分以下」去改某一条的 0 和 1。

## 难度验证与返修

难度不能由题面观感或一轮人工评分单独判定。记录题目版本、rubric 版本、受测模型及版本、逐项评分证据，以及执行步数或运行时长；人工分是估测，官方机分才是官方成绩。缺少对应证据时标为「未验证」，不写成已达标。

试跑后逐项复盘失分：区分模型漏判、任务流程没有迫使它处理该点、材料不足以支持唯一判定、rubric 标准含糊或过窄、交付格式遗漏。只有证据表明题目本身没有有效测到目标能力时才改题；不得仅为压低分数收紧 rubric、把一种标答措辞设成唯一正确答案，或把同一错误重复计分。修订后更新版本并重新盲测，保留旧轮次及对应 rubric，不把不同版本分数直接横比。

难点需同时满足三点：附件或题设中有可定位的依据；任务流程要求模型处理该依据；产物中有可核对的判断或结果。若模型绕过该点仍能完成核心决策，应调整任务依赖或交付物之间的对数关系，而不是增加格式分或硬性步骤数。结构完整、文件拆分等必要交付项可以评分，但应单独标为交付质量，不把它当作核心推理难度的证据。

## 材料来源

本规范不要求题目必须使用真实业务材料。可以采用合成案例、合成数据和合成附件，也可以混合真实与合成材料。合成内容应明确标为模拟，不得包装成真实案件、客户或企业记录；事实关系、版本、数字和裁决依据仍须完整一致，不能靠材料缺失或无根据猜测制造难度。

若题目要提交给外部项目、平台或竞赛，应另行核对其现行材料来源规则。本地规范允许合成材料，不代表合成材料符合任何外部项目的提交资格。

## 和出题问题怎么分工

标题顺序、任务类型、行业、领题和交题，仍按目标任务的交付要求处理。材料来源按本文件「材料来源」和目标项目的现行规则核对；外部项目的强制要求优先。本文同时规定给人看的文字写法、评分和难度验证方式。

## 每次必须交的成稿格式

只交一个 markdown，一级标题是题目 ID（没有就写「待领题」）。按这个顺序、用这些二级标题，不要多加章节：

```
# {题目ID}

## 表头
## 任务名称
## 任务类型
## prompt
## 考点rubric
## 作答思路
## 标准答案-文本
```

表头用列表写清：题目 ID、一级行业、二级行业、任务形式（本期只能单轮）、输入附件的绝对路径、建议的 L1 职业簇和 L2 职业。

不要在成稿里写：飞书账号、领取状态、质检、AI 率、GSB、模型回复、自测分数。那些由专家自己填或自测。

## 各字段要求

- **任务名称**：具体工作名，一句话，不写抽象能力标签；采用合成情境时，不暗示它是真实工作记录。
- **任务类型**：从六类里选最主要一类，整段照抄：经营与投资决策／数据、财务与业务运营／法务、合规与交易支持／客户与专业项目交付／持续运营与团队协作／工程、产品与专业研究。不自拟，不写「单轮」。
- **prompt**：模型只看 prompt 和附件。说清谁、要交付什么、拿去拍什么板。有效信息必须已在 prompt 或附件里。不要写怎么做，不要罗列每份附件内容，不要点破难点，不要规定必须跑多少轮，不要写压分目标和模型名单。单轮。可执行，禁止只让模型「分析一下」。
- **考点rubric**：计分只按 `官方评分标准.md`。15–20 条，一条一事，等权，每条 0 或 1。不设权重、倒扣、一票否决。每条先写正向通过标准，再写何种写法本条得 0。每个难点至少一条。格式、结构、常识合计不能接近一半。有唯一结论的写死；半开放的写必须写到哪些点、不能出现哪些错。金额脱敏的，不考点具体元，改查主体、口径、程序。字节会按 prompt、附件和本考点做机标。
- **作答思路**：给质检看，不进模型。用连贯的话写材料怎么分层、冲突以谁为准、难点在哪份附件、做错会怎样。不用表格，不附对照清单。口吻见 `题目规范.md`。
- **标准答案-文本**：独立可执行的结论，和考点能对上。用连贯的话写，不把采信或结论再铺成表。prompt 若还要求单独的文件产物，另在出题目录放标准答案附件。

## 难度与材料

合格线：SOTA 得分不高于 50；执行轮数不少于 50 步或运行时间超过 40 分钟，满足一项即可。

附件可用真实材料、合成材料或二者混合，不以真实材料为前提。格式限 Office 三件套、PNG、MD、HTML。保留各来源的原始结构；合成材料应标明模拟身份，且能够从题设和附件重新得出结论。多份附件打架时必须有依据确定采信口径，否则题不可判；矛盾须能裁决，难点埋在附件里。若目标提交项目另有限制，按该项目现行规则执行。

同一专家多道题：任务目标、工作流程、任务类型、最终产物中至少两项实质不同。最多 8 道新题，同时在手不超过 2 道。本期第一道题的一级行业锁死后续题。

## 一、分数、轮数和时长分别靠什么

| 指标 | 要求 | 靠什么 |
| --- | --- | --- |
| Sota模型得分率 | 不高于 50 分，必须达到 | Prompt 里埋难点，考点把难点查出来 |
| Sota模型执行轮数 | 不少于 50 步，和运行时间满足一项即可 | Prompt 安排的工作量 |
| Sota模型运行时间 | 超过 40 分钟，和执行轮数满足一项即可 | Prompt 安排的计算量 |

轮数和时长好理解，模型要干的活多，轮数自然就上去了。十几份文件要一份份打开，几千行记录要一条条处理，排程要真求解，代码要真跑测试，七八份交付物要一份份写，写完还得回头对数，这些都是实打实的步数。这部分主要靠 Prompt 来设计。

分数要复杂一些。模型答错了，考点却没查那个地方，分数照拿；考点写得再细，材料里没有会让它出错的东西，它也能拿满。分数得靠 Prompt 和考点配合：Prompt 里放进容易做错的地方，考点专门去查这些地方。

**核心原则：** 以上两件事要同时设计在一道题目中。只堆工作量的题，模型老老实实干了六十轮，每一步都没错，分数还是很高；只埋难点的短题，分数压住了，二十几轮就交卷了。比较好的做法是把难点藏在模型必须一条条处理的明细里，活不干完就碰不到难点，碰到了还得认得出来。

**选题判断：** 模型替你把这件事做完，你愿不愿意为结果付费。值得付费的任务，背后一般都有一个人要在某个时间前拍板，比如这批备件订多少，这份合同能不能签，这个版本能不能上线。围绕这个决定出题，题目就有了方向，考点也有了对错。

## 二、用 Prompt 把轮数和时长做上去

思路很简单：让模型必须一步步地做，而且步与步之间有先后，没法合并。

### （一）好的做法

1. **附件给原始的，别给整理好的。** 真实工作里的材料是散的：系统导出一份 CSV，财务给一张 Excel，邮件里一个说法，会议纪要里又一个说法，最后还有一份盖章的正式文件。把它们按原样分开给，格式也保留原样，模型每换一种文件就得换一种读法。你要是先替它汇总成一张干净的表，它三五轮就读完了，里面的矛盾也看不到。
2. **要求每条记录都有结果。** 让模型逐笔、逐户、逐个 SKU 给结论，没有需求的行也要留着，汇总数要能对回明细。明细的量控制在人工一条条看不完、写脚本又得先把规则弄懂的程度，几百行到几千行都可以。
3. **要求真的跑起来。** 排程要真求解，代码要真跑测试，结果要能从空文件夹重新生成，并留下命令和输出。没跑的就写没跑。这一类要求最能拉长运行时间。
4. **交付物分成几份，数字要对得上。** 给审批人的报告、给执行岗位的清单、给财务的底表、给后续跟进的待确认事项表，各写各的，内容不能互相抄，数字必须一致。题面里可以直接写出哪些数必须相等，比如需求减库存等于缺口，缺口加安全量等于下单量。
5. **前后有依赖，情景要重算。** 先定口径，再算明细，再出方案，最后做压力情景和执行安排，前一步的结果就是后一步的输入。压力情景要求重新算一遍，不许把主方案按比例打个折了事。
6. **最后留一步自查。** 要求模型换一种算法把核心数字再算一遍，或者做一张跨文件的对数表，对不上就回源头去改，不许在结果页上直接改数。

### （二）大致算一笔账

按一般的作答路径粗算：15 份左右不同格式的附件，读下来要十几二十轮；清洗、关联、处理异常十轮上下；核心计算十轮上下；三个压力情景各重算一次，六轮左右；七八份交付物，一份一两轮；最后对数返修再来五到十轮。加起来五六十轮。因此，如果题目附件只有两三份、只交一份报告的题，内容再难也很难到 50 轮。

### （三）不好的做法

1. **靠硬性规定凑轮数。** 规定必须按固定步数逐步输出，每一步都要重新打开同一个文件，每做完一步单独发一条进度消息，要求派子代理分头做，要求把全部资料调研一遍或者写够上百页。消息条数确实多了，题却没有变难，分数压不下来。项目说明里写了，靠扩大范围做长的任务不收，质检很可能判成凑量。
2. **把几件不相干的小活拼在一起。** 每件都要做，轮数也上去了，但它们之间没有共同的目标，也谈不上谁依赖谁，不符合真实工作场景，而且这些小事彼此独立，难以有效压低分数。

## 三、用 Prompt 和考点把分数压下来

### （一）先估一下送分的比例

写考点之前先估一下：格式对不对、结构全不全、常规的加减乘除、常识性的结论，这些 Sota 模型基本都能拿到。你可以把 SOTA 模型想象为一个刚 985 毕业的实习生，常规、理论性的考点都难不倒他。如果它们的内容加起来接近总考点的一半，难点埋得再好也压不到 50 分以下，这类考点要少放。

### （二）在 Prompt 里放进容易做错的地方

真实工作里让人出错的地方，模型一样会错。

1. **材料之间打架。** 同一张订单有草稿和正式版，同一个客户在两个系统里编码不一样，群里有人凭印象报了个数。光放矛盾还不够，还要给一个判断依据，告诉模型以谁为准，比如签发的优先于草稿，合同优先于会议纪要，截止日前批的优先于事后补签的。没有依据，这道题就成了开放题，考点判不了对错。
2. **同一个数，口径不一样。** 含税和不含税，原币和人民币，下单金额和实付金额，月报数和年报数。模型最常见的错法是拿来直接相加。
3. **表面上的指标会骗人。** 平台后台的 ROI、供应商报备的产能、全月总工时，看着够用，拆到每周、每个班次，或者换成实际利润一算，就不够了。比如报备产能只是单班日产，乘上工作日、开班数和良率之后，才是真正的月供应能力。
4. **顺手的做法走不通。** 预算、产能、比例上限、起订量几条限制同时卡着，按单价排序、先到先得、按比例分摊这些顺手的办法，总会违反其中一条。压力情景也一样，可用额度砍掉一半，方案就得重新选，按原方案打五折是错的。
5. **时间和状态分不清。** 题面写清楚截止到哪一天，之后才到的更正只能用来解释偏差，不能拿来改当时的结论。待审批不等于批了，开了票不等于钱到了，测试没跑不能写通过。模型为了让方案看起来完整，很喜欢把没定的事写成定了的。
6. **有人提了错误的要求。** 老板要求所有客户一律打八折，前任的结论有一部分已经被推翻，业务方坚持报表亏损就关店。题目要求模型逐条回应、用数说话，它就得在顺着说和拿数反驳之间做选择。
7. **看着有问题，其实没问题。** 某个监测字段按规定本来就不填值，某条专用条款写的是按通用条款执行，这些都正常。模型很容易什么都标成风险，放一两处这样的地方，就能把“全部不通过”式的答卷筛出来。

### （三）埋难点时要注意

1. **难点要藏在原始明细里，题面上别点破。** 题面一写“附件3第12行是重复记录”，模型照着改就行，这个点就废了。
2. **题面上写“不得直接相加”“不能简单平均”这类提醒**，基本不增加难度，模型会照做。真正起作用的，是材料里确实有会让它犯错的东西。
3. **公式、参数、换算关系不要直接给**，只给业务规则和正式文件，让模型自己推。

材料写完，自己先用最顺手的办法做一遍。顺手的办法就能得出正确答案，说明这道题的判断部分没有难度，还得再加限制或再埋点。

### （四）考点要把难点查出来

考点写得粗，难点就白埋了！！！拿口径那一处来说，考点写成“考虑了含税与不含税的差异”，模型提一句就能拿分；写成具体的数，它算错了就拿不到。下表里的数字只是举例。

| 难点 | 容易被糊弄过去的写法 | 能查出错的写法 |
| --- | --- | --- |
| 口径不一样 | 考虑了含税与不含税的差异 | 三季度不含税收入为 1284.6 万元，误差不超过 0.1 万元；直接用含税数 1451.6 万元的不得分 |
| 情景要重算 | 对压力情景做了分析 | 额度减半后入选的是 A、C、F，不含 B；按原方案等比例缩减的不得分 |
| 状态分不清 | 区分了事实和计划 | 三项待会签的采购在执行清单里标为“待确认”；标成“已批准”的不得分 |
| 看着有问题其实没问题 | 识别出了材料中的异常 | 第 17 条“按通用条款执行”判为没有改变默认安排；标成风险条款的不得分 |
| 执行安排 | 给出了执行建议 | 停产切换写明负责岗位、完成时间和回滚条件；缺一项不得分 |

写考点时还有这些讲究：

1. 一条考点只查一件事。几个并列的计算结果分开写，别合成一条。
2. 每个难点至少对应一条考点，考点重心往这些考点上倾斜。
3. 对常犯的错设不得分条件，比如把没确认的写成已完成，什么都判成不通过，替决策人拍了本该由他拍的板。
4. 上游错一处会连带下游好几条考点丢分时，确认每条查的是不同的东西，并在标答里写清楚连带关系，方便质检判断是不是重复扣分。
5. 能唯一确定的结果，尽量设计成唯一，打平时怎么取舍也写进题面。开放一些的部分，用“必须写到哪些点、不能出现哪些错”来判。
6. 文件名、字段、单位、小数位、允许的误差都写进题面。要求定死了，考点才好判，模型也没法靠格式上的自由发挥拿分。

### （五）标答和作答思路

标答最好自己独立核一遍。作答思路里把每个难点交代清楚：在哪一步发现，怎么处理，做错了会得出什么数。质检主要靠这部分判断考点有没有道理。

## 四、出题顺序和试跑后的调整

1. **选一个真实的决定。** 找你岗位上经常发生、做错了会有损失的一件事，比如备件该订多少、合同能不能签、这批贷款要不要调分类。把前面的数据整理、口径确认和后面的方案比较、执行交接一起放进来，别只做中间一小段。
2. **把交付要求定死。** 要交哪几份文件，每份叫什么名字，有哪些字段，保留几位小数，结论只能从哪几个选项里选。
3. **列一张只给自己看的难点清单。** 每一行写清楚：难点埋在哪份附件的哪几条记录，正确做法是什么，模型可能怎么错，错了会影响后面哪些数。一道题一般列 8 到 15 个，尽量覆盖上面说的不同类型。
4. **照着清单丰富材料。** 按来源系统分文件，把难点放进明细，给出以谁为准的依据。
5. **自己用顺手的办法做一遍，确认真的会踩坑。**
6. **写考点、标答和作答思路，考点和难点清单逐条对上。**
7. **跑一遍 Sota，看分数、轮数和时长，没达标就对照下表改。**

| 跑出来的情况 | 一般是什么原因 | 怎么改 |
| --- | --- | --- |
| 得分超过 50 分 | 题面点破了难点，材料太干净，送分考点太多，考点写得太粗 | 把提示从题面拿掉，难点放回明细；多放几处版本冲突和口径差异；压低格式分；考点改成具体数值 |
| 模型错了却没扣分 | 考点没查到这个地方 | 对照难点清单补考点 |
| 轮数够了，分数还高 | 活很多，但难点不在模型必须处理的地方 | 把难点挪进要逐条处理的明细，让汇总表和明细对不上 |
| 轮数不到 50 步 | 附件少或者已经汇总好，只交一份报告，不用真跑，情景能按比例缩 | 换成各系统的原始导出；拆分交付物并要求对数；加入必须运行的求解或测试；要求情景重算 |
| 时长不到 40 分钟 | 计算量小，要逐条判断的对象少 | 扩大逐条判断的范围，加入需要枚举或求解的环节 |
| 分数很低，但模型根本没法做 | 材料不够，缺判断依据 | 补材料和判断依据 |

改的时候动材料和结构，别去加凑轮数的硬性规定。

## 五、不要出的题

1. 按章节填空的报告。题面列好一二三，材料很干净，模型照着填就是高分。
2. 拼盘题。几件不相干的小事凑在一起。
3. 离不开外部条件的题。要登录真实平台、用真实账户或者抓实时数据，光靠给的材料开不了工。
4. 换壳题。同一个题面结构换个公司名、换个行业就算一道新题，项目会查重。参考素材可以学思路，结构和写法要自己来。

直接影响与损失：v15 采购订单的 title 字段为必填且不渲染，每笔新单标题必然写入字面量 {supplier_name}，脏标题进入长期业务数据并跨版本保存，而旧维护线没有任何自动修复手段；若错误放行，所有升级客户的采购/销售/子承包单据会持续产生脏标题，只能事后人工回填。
做错导致的损失：只修新数据不修历史数据，历史脏行永远留在库里；错误回移或迁移会破坏已正确的数据，或让已升级客户的问题依旧；反向错误阻断则让本该发布的修复无法按期上线。
任务收益：同类“跨版本数据迁移/回移完整性”问题在企业 ERP 维护中会重复出现，每次缺陷族关闭、维护版本发布或回移前都需要同规格复核；单次专业投入约 16 小时+（2 个工作日），完成本题即替代该环节的人工复核，结论与产物可复用
