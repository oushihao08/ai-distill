# 真实委托双口吻、防剧透与去模板表达（对齐官方 3.1 规范）

**用途：**在完成全卷穿透求解、脚本复算与 ≥30 项 Rubric 设计后，严格按照钉钉《数据集构建规则》第 3.1 节与 11-17 退回红线编写 `task_metadata.instruction`、`deliverables` 与 `task_name`——还原真实委托情境、交代清楚脱敏主体关系、混入合理口语干扰与待纠偏诉求，同时严守**零出题痕迹、零剧透、零模板同构**。

---

## 一、官方双口吻规范与信息边界（`instruction` 核心要求）

根据本题设定的真实委托方身份，在以下两类口吻中择一执行（不得混搭成“AI 出题说明书”）：

### 1. 普通委托人口吻（不懂法的自然人／企业经营者／业务部门负责人）

- **第一人称口述为主体**：当事人只讲自己亲历的来龙去脉、眼下痛点、主观感受和想要的结果；**允许口语化、允许啰嗦、允许时间顺序颠倒、允许夹带情绪表达或单方偏差信息**（真实的委托人不会按编年史替律师整理好事实摘要）。
- **允许并鼓励包含不专业、不可行或越界的诉求**：在 `requests` 中自然带入 1–2 项符合当事人利己心理但依法不成立、超权限、程序走不通或有合规风险的诉求，专门检验模型能否独立判断、不被当事人带偏。
- **不越位替律师思考**：普通委托人**不介绍证据的三性性质、不评价法律关系定性、不规定专业法律文书体例**；交付物要求停留在委托人能说出口的程度（如“帮我把回绝他们的答辩材料、要交上去的证据单子、还有给我看的说法说明弄出来”，具体精确文件名在 `deliverables` 锁定）。

### 2. 法律专业人士委托口吻（合伙人转交办、法务总监派活、法官交办、检察官阅卷指令、监管问询）

- **行内正式交办风格**：直奔程序节点、退件障碍、待审合同底稿、交易交割死线或阅卷审查重点；可以使用准确的专业术语、文种要求与汇报体例，但**同样严禁提示考点、严禁喂给解题路线或提前点破底层证据矛盾**。

### 3. 脱敏主体清晰交代 vs 不替候选归纳卷宗（把握黄金分寸）

- **必须交代清楚的（防 11-17 匿名化失明退回）**：本次服务的是哪一方主体、委托方与相对方在交易／程序中的基本对应关系（尤其当脱敏卷宗存在简称或代称时，必须确保模型能明确识别谁是我方、谁是相对方）、完成委托不可或缺但卷内未载明的现实触发背景、`baseline_date` 基准日及不可退让的 `hard_constraints`。
- **绝不在题面重复喂给的（保住 ≤55% 难度）**：凡能从 `input_files` 发现、提取、比对或推导的具体时间线、多笔收付明细、补充协议变更条款、送达签收日期差异和证据矛盾点，**一律不写进 `background` 替模型做摘要归纳**。

## 二、零出题痕迹与防剧透五禁令

### 1. 严禁出现的出题、模拟与容器黑话

`task_name`、`instruction` 各字段与 `deliverables` 中**严禁出现**：
- 出题与评测词：`本题`、`考察`、`请注意`、`重点是`、`评分将检查`、任务类型编号（`F1–F5`）、维度名称（`Q1–Q7`）；
- 虚假模拟词：`模拟律师`、`模拟场景`、`本题模拟`、`办理演练`、`假定截至某日无新增清偿`、`题设前提`、`虚拟双窗口`；
- 容器、测试脚本与内部预处理词：不在 `instruction` 自然语言字段手写 `/app/input_files`、`/app/output`（Harbor 转换器会自动拼接路径表，手写会污染 Siriser `instruction.json` 业务语境），不写“在聊天回复中分节列出即可”或“转换页面图像／重算读回”等测试指令；`hard_constraints` 数组元素不自带 `1. ` 编号前缀，严禁把内部不脱敏指令（如“保留原姓名、不改写原件／附件”）抄进题面；对外文书与元数据中严禁出现“提取文本／提取原文／页标／未另行读取扫描PDF／历史题包”等内部 OCR 流水线措辞。

### 2. 防剧透五禁令（把发现矛盾与法律判断留给被测模型）

| 禁令 | 严禁在 `instruction` 或文件名中泄露的内容 | 合规的真实委托写法 |
| --- | --- | --- |
| **① 禁文件名泄底** | 救济路径、案由或请求权基础本身待判断时（如应走代位析产、撤销权、执行异议之诉还是追加被执行人），不得在 `deliverables[].path` 或 `task_name` 直接点名胜出路径 | 用中性业务用途命名（如 `权利救济路径方案.docx`、`拟提交法院的主请求文书.docx`）；仅当程序阶段已固定（如二审上诉、收到处罚告知后陈述申辩）才直接命名既定文种 |
| **② 禁喂法律定性与备选路径** | 严禁提示“注意区分名租实贷”“审查表见代理或越权担保”“适用减资前置规则”或列“第一步先核……第二步再算……”的解题大纲 | 只讲委托方想要什么结果、担心的商业后果或卡住的审批节点 |
| **③ 禁提示跨时际修法与顺延** | 严禁提示“跨越 2024 新公司法修订”“适用时间效力司法解释第 X 条”“注意某年法定节假日顺延” | 仅明确 `baseline_date`（交付物出具日／评估基准日），要求依法核定适用规范、期限届满日与权利义务 |
| **④ 禁点破在卷旧稿／模板错点** | 交办审查在卷旧起诉状、对方合同模板或结算表时，严禁直接点破“管辖违反专属管辖”“漏扣某笔款” | 按委托人口吻表达直观诉求或顾虑（或交代旧稿拟用于何处，请把关修订定稿），把隐蔽法律漏洞留给模型自己查出 |
| **⑤ 禁预告账据重复与时间线异常** | 严禁提示“微信转发回单与银行流水重复”“某笔款当日已退回”“面积单价写反” | 仅要求把双方往来账目和手头凭据彻底核清，算出截至基准日站得住脚的准确金额 |

## 三、文书引用、案号核验与去模板排版

1. **分层文书引用规范**
   - **`input_files`**：`attachment_id` 与 `name` 原样复制自 `delivery.json.input_files`，`description` 如实写明该附件所含文书与字段口径。
   - **`instruction`**：按委托人自然知情方式提及手头核心文件（如“对方发来的那份推广合同模板”“法院刚寄来的处罚告知书”），不按卷宗目录机械报菜名罗列全部边缘回执；附件原文已有的真实／脱敏案号按在卷字面准确引用，不自行凭空新造星号占位符，也不把完整在卷文书误称“文字摘录”。
   - **`reference_outputs` 与 `rubric`**：精确引用具体原始文书名称、日期、主体与条款号；引用公开类案案号前必须上网核验真实存在且裁判要旨一致，**严禁编造虚假案号**；严禁把内部映射名 `附件1` 或哈希文件名直接当作正式法律文书名写进对外正稿。
2. **打破全批同构模板**
   - `task_name`：用一句自然交办短语点明业务事项与核心产出（参见 [书面表达与交办组件库](../assets/书面表达与交办组件库.md)），禁套“`XX案的A、B与C`”三段标签拼串，禁加“专项／全量／闭环”包装词。
   - `instruction`：根据委托人角色灵活切入（当事人倒苦水提诉求、商务催审对方霸王模板、合伙人交办庭前急件、收到行政告知卡死线等），拒绝千篇一律的“我方作为XX，现以XX年XX月XX日为基准日……”开场白。
   - `reference_outputs`：诉状、答辩状、陈述申辩书、修订合同、法律意见书各自严格遵循真实实务文种体例（含完整首部、正文说理、此致机关、落款署名日期），不使用装饰性 `【】` 堆砌大纲，严禁夹带代码块或脚本。

## 四、成稿前四步终检

1. **角色口吻与主体清晰度检查**：通读 `instruction`——普通委托人是否像真当事人在说话（含合理干扰与待纠偏诉求、无专业法言法语指导）？专业委托方是否像行内真实派活？脱敏后的我方与相对方关系是否交代清楚、无空白失明？
2. **漏交办与防剧透双查**：单读公开 `question`（由 `instruction`＋`deliverables` 合成）——Rubric 中每一条 `Explicit` 要求在题面是否都有明确出处？每项 `hard_constraints` 是否均有 Rubric 覆盖？是否零泄露待求路径、修法线索与底层账据异常？
3. **五件套与 Harbor 六处路径对齐**：核对 `deliverables` 包含 ≥3 份实质业务成果 ＋ `法规案例检索轨迹.xlsx`，全部文件名无动态成分、≤200 字节，且与 `reference_outputs`、`rubric[].metadata.evaluated_files` 逐字节完全一致。
4. **零退回瑕疵扫描**：全量扫描 `task_name`、`instruction`、`reference_outputs`（含 `sheets` 单元格）与 `rubric`——确认零编造源外事实、零虚假案号、零法条原文错漏、零模板占位符、零内部自相矛盾、零 AI／工具／评分残留、零“待专家确认”未清理字段。
