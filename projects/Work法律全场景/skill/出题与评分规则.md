# Work法律全场景：出题与评分规则

## 材料包与题目的固定关系

本项目按 **一个材料包只对应一个题目身份** 执行。出题前先确认材料包身份及其已有题目；读取包内全部附件，将它们作为同一道题的共同来源。不得按附件、文书、文件版本或案件子环节拆出多道题。对既有题目的返修、重出、重评沿用原题身份和尝试历史，不新建第二题。若发现历史上一个包已关联多道题，暂停该包的新建并报告重复关系，不擅自删除历史；核清后沿用确定的既有题目身份继续。

本文规定任务描述、源文件、标准成果、评分方案及题目信息。各文件的用途与读取条件见[入口](SKILL.md#文件用途与阅读顺序)。

方向、律师／法务单方代理、单场景或关联多场景及配套文书按[材料方向场景与交付设计](材料方向场景与交付设计.md)执行；正式场景分类按登记填写，不把多场景工作另拆成第二题。

## 一、任务描述

### 委托要素与口吻

用途：把真实委托事项完整交给模型，明确背景、诉求、交付物和不可退让的条件。

| 要素 | 原文要求 | 作用／结果 |
|---|---|---|
| 业务／案件背景 | 交代交易或纠纷经过、各方关系、已发生事实；允许冗余、矛盾和干扰信息 | 让模型自行梳理事实、识别法律关系，判断哪些信息可信或相关 |
| 委托方诉求或办案要求 | 逐项说明委托方想要什么；允许包含不专业、不可行、越界的诉求 | 检查模型能否识别不合理诉求并正确处理 |
| 交付物要求 | 明确交什么材料、每份大致包含什么；普通委托人口吻不直接规定文书体例 | 确定最终产物及其必要内容 |
| 基准时间点 | 写明交付物出具日、尽调基准日或评估基准日 | 确定适用法规版本、时效及信息截止范围 |
| 硬约束 | 提交期限、金额上限、必须保留条款、不得披露事项等；独立编号单列 | 评分时逐项检查遵守情况 |

口吻及内容要求：

- 以委托人第一人称口述为主体，只讲亲历事实、感受和期望结果；不预先解释证据性质、法律关系或指导文书如何写。
- 可以口语化、啰嗦、顺序颠倒、带情绪。
- 委托方为律师、法官、检察官、监管部门等专业人士时，使用对应专业行文，可以提出专业术语和体例要求，但不能提示考点。
- 不出现“本题”“考察”“请注意”“重点是”、任务类型编号、评测维度名称等出题痕迹。
- 各场景办理时点及当时可取得的信息同时约束题面、标准成果和评分使用的事实范围。单场景按其基准日判断；多场景分别明确各自时点，不能让整体交付日把后续材料倒灌到较早场景。回溯复核确需使用后续材料时，明确区分原决策时点与本次复核时点及各自可用材料。

### 题面：只给基础委托

- 能从获准附件发现、提取、关联或合理推导的信息，不在题面重复归纳、强调或解释。只给角色、基本诉求、必要基准时点、成果用途及真实硬约束；附件无法提供但完成委托不可缺少的背景才补充。
- 文件清单、精确交付要求和理解委托必需的事实不能省略。

- 人物关系、关键数值、时间线、矛盾点、证据性质和法律线索交给候选自行识别。
- 不要把作者求解所得的争点、正确算式、适用法条、法律定性、行动分支写成提示；不在题面列“先核对……再分析……”的解题路线或暗示评分点。
- 保留委托确已提出的真实问题，不将正确结论伪装成客户已知事实；不删改原始附件或隐藏无法推导的必要信息。

### 作者：形成必要的判断依赖

- 先满足适用标准、指定场景和真实委托；仅在现有材料支持进一步判断时加难。
- 找出会改变请求、抗辩、风险或后续动作的证据、规范前提及核算口径，完整求解其影响；材料支持竞争解释时比较最强反对意见、采信理由和结论改变条件，不补造竞争路径。
- 跨成果确需依赖同一判断时保持一致。允许材料支持的关联场景组合，但不强行把复盘、整理等任务改成无依据的其他场景；连续办理、条件触发及互斥备选按场景设计规范分别安排，不要求同时实施互斥路径。

- 委托已固定时，在其范围内深化；尚未固定的工作重点，先比较同一材料与指定场景能够支持的真实任务，优先选择必须综合文书、评价证据或适用规范才能完成的办理目标。
- 材料多、成果多或判据多不能替代这一步。
- 对拟采用的关键判断，先求解“材料依据（含实际存在的冲突） → 成立前提与可接受解释 → 请求、金额、风险或动作的实际变化”；只有影响本次成果可用性的结果才落实为任务与判据，不把链条公开为解题提示。

- 没有真实加难空间时保留实际任务和难度；仍不满足正式等级或难度门槛时如实记录，不降低门槛或用虚构障碍凑合。
- 不固定难点个数，不要求每题覆盖全部机制；多案仅在实际共同决策时联动。
- 期限、预算、权限、保密及程序约束须来自委托或材料；不增加无来源限制、无关成果、人为操作，不以强制耗时、输出字数或公开内部思维过程制造压力。
- 质量核验、独立计分及准确状态始终按标准执行，其修正不单独算作难度提升。

方法对照例（仅教作者设计，不是本题事实、候选题面或固定任务模板）：

| 项目 | 对照 |
| --- | --- |
| 适用前提 | 获准材料确有可核对对应关系的合同、付款记录和对账材料，且当前场景与委托允许评价其证明范围；不得为套例子新增事实 |
| 基础设计 | 按真实委托汇总记录和余额；符合规定任务时可保留，不能仅因包含摘录就拒绝给分 |
| 有空间时深化 | 材料确有影响结论的付款归属或证明范围问题时，让阅卷、质证或核算成果依赖该判断，并影响余额、证据意见或后续动作；不把判断链条直接交给候选，无此问题不强套 |
| 作者内部求解 | 比较材料支持的付款解释，核验各自前提和计算，说明何种证据改变结论；不预设某类记录当然有效或无效 |
| 评分落点 | 各独立业务结果有明确判据，不能只列争点就得分；合法替代可满足，不能因多处复用同一金额重复奖励 |

### 保存前核对

#### 专业判断与实际难度

- 完整求解后，对照仅准确摘录、列出问题和通用建议的基础答案，与完成材料支持的关键判断的答案，检查核心判据是否真正区分两者。
- 基础答案已经满足真实委托的部分正常给分；若它无需关键判断就能完成主要成果，回查任务选择是否遗漏了材料支持的必要工作，有则在委托范围内重设计，无则如实保留实际难度。
- 不能仅因基础答案能答对就压低其合理分值，或增加无来源义务制造区分度。

#### 成果、判据与公开输入

- 对照第三节核验成果，再按第四节核对必设维度、F锚点、权重和幻觉阈值。
- 核心条目代入“一对一错”“合法替代”“实际违规”和“仅缺非决定性细节”的回答，确认独立判断、正确给分、同一缺失不重复处罚。
- 核对候选实际收到的题面、成果文件名及说明、input_files描述：必要背景、约束和交付标准均公开，不额外泄露争点、结论或解题路线。
- 程序选择本身属于待判断事项、委托又未指定文书类型时，成果名不预选正确程序；真实委托已指定的名称保留。
- 题目信息与实际任务相符。不新增自审文件，草稿状态不免除已能完成的规则。

#### 结构化输出

- 本次schema包含`task_metadata.instruction`时，用`background`写委托已知的必要背景，`requests`写本次诉求，`baseline_date`填适用的YYYY-MM-DD，无适用时点才填null，`hard_constraints`只填真实限制。
- 成果名称、说明及必交属性只维护`deliverables`。
- 公开`question`由程序生成，不能另维护第二份题面。
- 时点的日内范围及材料截止口径写入实际约束；不以开庭日、文书日期或法条年份猜填基准日。
- 多场景时，`baseline_date`仍按本次整体交付或复核基准填写；各场景的办理时点和可知信息在既有背景、诉求或约束中说明，不新增字段，也不让单一字段取消逐场景信息边界。
- 本次代表的一方及接受委托所必需的代理身份、权限应在背景明确；其余交易主体身份及关系可从附件可靠识别时交给候选分析。无法从附件推导的必要信息须明确或保留真实缺口，不补造关系。

#### 自检对照

在既有作者自检中逐项完成，不新增流程节点或自审附件：

| 对照对象 | 检查和处理 |
| --- | --- |
| 任务与逐份成果 | 名称、必交数量、用途、时点及约束一致；逐份有本案可用的实质正文，摘要、空标题或未来计划不能冒充成稿 |
| 成果与检索轨迹 | 金额、身份、日期、法条范围与版本一致；每个实际采用的援引有对应核验，检索词无无关残留；发现差异回源修正，不自动删去可能有效的条文 |
| 全部Rubric逐对 | 同一行为若会同时损失正分并触发负分，核对负项是否确有额外错误；可一对一错且有独立业务后果才拆条，共同成立同一结论的必要条件不机械拆开 |
| 每条判据 | 写明全部/任一命中条件、事实或法规实质及合法替代；负项直接描述有害行为；计算说明舍入及有依据的接受范围，不一律增加1元容差 |
| 等级与输入形态 | 独立文书定位、人时与必要工作如实记录，未核实或不匹配保留疑点；扫描属性依据实际交付文件判断，无法确认时保留未知；视觉依赖按完成任务是否需要识读图像信息判断，不由扫描属性直接推出。适用平台另有明确填写口径时按该口径填写并注明依据 |

#### 文件形式及对应关系

| 阶段／字段 | 要求及作用 |
|---|---|
| 专家初稿 | `任务说明.docx` |
| 构建规则中的名称 | `instruction.json` |
| Harbor实际交付 | `instruction.md`，仅接受此文件名，≤1 MiB，作为模型的任务提示词 |
| 源文件说明 | 逐个列出 `/app/input_files/` 下的文件及相关字段、口径说明 |
| 交付路径 | 明确写入 `/app/output/`，逐个列出精确文件名 |
| 对齐要求 | 显式评分要求应在任务书中有出处；任务书硬性要求应有评分项覆盖 |
| 保密边界 | 不泄露评分条目、标准答案内容或“评分将检查……”式提示 |

## 二、源文件

### 材料资格与完整性

用途：提供完成任务所需的真实材料，包括合同、证据、卷宗、尽调底稿和模板等。

| 项目 | 原文要求 | 作用／结果 |
|---|---|---|
| 数量 | L2≥3份；L3≥10份；L4≥50份；L5≥100份 | 满足对应任务长程性所需的材料规模 |
| L5材料构成 | 多项目、跨不同时期的不同材料 | 支撑跨项目、跨时期的综合任务 |
| 真实性 | 真实实务材料脱敏改写；不得由模型批量生成凑数 | 保持真实工作场景和有效难度 |
| 完整内容 | 不能用摘录、概要或节选冒充完整文件 | 让模型实际读取、筛选和交叉核验 |
| 格式与体例 | 行文结构、格式、表述细节应符合该类真实文件 | 避免简单模板或仿真材料失真 |
| 完备性 | 正确结论所必需的材料齐备 | 避免缺材料造成结论不唯一 |
| 可设置的缺口 | 只允许真实场景中确会缺失、且正确处理是明示缺口并列补充清单的情况 | 考察补充材料意识，不能以信息缺失制造无解题 |
| 文件形式 | 可含PDF、Word、Excel、扫描件、PNG等 | 对应识读、OCR、计算和核验能力 |

### 等级依据与逐份清点

等级同时按成熟法律实务人员完成业务的必要工作核对，不计算设计题包、AI等待或人为增加的操作成本：

| 等级 | 专家业务人时 | 最短必要步骤 |
| --- | --- | --- |
| L2 | 0.5–2小时 | 10–30 |
| L3 | 2–8小时 | 30–100 |
| L4 | 8–40小时 | 100–500 |
| L5 | 40小时以上 | 500+ |

- 本系统的`level_basis.documents`按材料内可辨识、真实完整且相关的独立文书逐份登记，并填写附件和页段位置。
- 一个合订附件不直接等于只有一份文书；也不能把分页、PDF分片、重复件或仅被提及但未提供的文书计为新增材料。
- 未清点或完整性不足时如实说明，不以附件数量直接断定等级。
- 实际人时与指定等级不符时保留真实工作及估算，说明等级未成立，不改数字或删除难点凑级。

- 多份文书的分组目录可以辅助阅读，但不能用文书组条数冒充逐份清点结果。
- 目标标签、模型得分和专业内容完整性均不能单独证明等级；等级尚未证明不自动使可完成的专业成果变成草稿。

- `level_basis`记录作者对材料与工作量的依据，不要求候选复述等级、估计专家人时或证明出题资格。
- 材料资格由用户审定；已确认的清点结果保留来源，尚未核实的数量或等级差异如实记录，不擅自改标签或用虚增步骤凑级。
- 同一材料可用于不同业务任务，但换标题、扩写成果或增加评分项不等于独立材料及必要工作增加。

### 存放与可见范围

- 专家初稿放在 `input_files/`，目录名不能改成“源文件”。
- Harbor题包放在 `environment/input_files/`。
- 模型看到的路径是 `/app/input_files/`，只读，不得修改。
- 每份材料应在任务描述中列明；不能通过隐藏说明补足必要语境。

## 三、标准交付物

### 成果类型与必需内容

用途：由法律专家亲自撰写，提供可在真实实务中使用的标准答案，并作为评分细则的拆解来源。

以下组合是参考，不是固定全集或数量豁免。按场景设计规范形成整体任务至少三份有实际用途和实质内容的配套文书；具体成果按单场景或关联组合确定，不重复拆分凑数。

| 任务类型 | 标准交付物组合 |
|---|---|
| F1 咨询研究 | 法律研究报告／法律意见书／检索报告；法规案例检索轨迹 |
| F2 审查审核 | 审查意见书或尽调报告；风险清单；修订留痕版或300–500字审查意见邮件，覆盖全部高风险项；检索轨迹 |
| F3 文书起草 | 可直接提交、报送或对外出具的文书正稿；证据或附随材料清单；委托诉求处理说明；检索轨迹 |
| F4 方案设计 | 方案或预案正文；法定动作清单；支撑依据分析，含替代路径及成本／风险比较；检索轨迹 |
| F5 数据核算 | 结构化台账或测算表；口径说明；分析结论与预警清单；检索轨迹 |

其中明确要求的内容字段：

| 内容 | 字段／要素 | 作用／结果 |
|---|---|---|
| 风险清单 | 风险等级、风险描述、判定依据、修改或整改方案、是否必须修改 | 按风险从高到低排序，支持处置决策 |
| 证据／附随材料清单 | 编号、名称、形式、证明内容、证明目的 | 按证明对象或请求权路径分组，形成证据对应关系 |
| 法定动作清单 | 动作、执行主体、时限、所需材料 | 形成可以执行的步骤 |
| 测算口径说明 | 基数口径、计算公式、数据来源、假设条件 | 让公式和结果可复算 |
| 法律分析 | 事实、规范、适用 | 每项结论可追溯到源文件及核验过的法律依据 |

### 成稿质量与求解核验

- **按用途成稿**：申请书、意见书、报告分别使用真实业务体例，写出本次已能完成的具体结果，不以提纲或未来核查清单替代已有材料可完成的判断、核算及建议。对外正稿不夹给起草人的填写、删除、改写指令；报告中的调查方法、证据缺口及条件意见是业务内容，保留在适当位置。缺少不可替代输入时如实标明草稿及提交条件，不编造事实、授权、签章或已办理事项。
- **正式格式**：本轮Work业务叙述类成果使用DOCX，结构化工作表使用XLSX，检索成果按内容使用DOCX报告或XLSX轨迹表；逐份写入reference_outputs，不能只改扩展名。内部JSON、提示词及执行记录沿用原格式。
- **结论明确**：每项问题有结论；确有不确定性时，写明原因、可能结果及条件、针对本案的建议倾向。
- **说理完整**：事实来自源文件，规范来自已核验的法规或类案。
- **立场一致**：律师／法务保持所代表一方的立场，分析对方观点不等于替对方交付成果。
- **口径统一**：不同交付物在同一场景、时点和口径下的金额、日期、比例、主体名称一致；跨阶段身份、余额或结论发生变化时说明依据，不强行写成相同结果或混用时点。

- 先逐份完成并交叉核验reference_outputs，再据此写Rubric：关键事实必须回到源文书及其上下文，不能用标答的另一处重复陈述作为证明。
- 同名／脱敏主体通过可验证的身份和程序关系区分；无法可靠区分时说明限度，不猜填。
- 法律路径核实全部成立前提、适用版本和合法替代，不把后来规则倒用于历史时点，不把有条件成立的办法写成当然可行。
- 数值用计算工具按来源、单位、公式和取舍规则复算；标答与判据冲突时修正后再交付。

### 内容状态与执行能力

`content_status`按本次明确委托判定，不按真实案件是否已办结判定：

| 本次委托与材料 | 内容状态 |
| --- | --- |
| 要求基于现卷评价证据、提出条件性意见及补证计划，已有材料足以完成这些成果 | `complete`；原件待核和未来补证写入成果，不另作草稿理由 |
| 必交成果要求确定性结论或实际操作，缺少不可替代输入使该部分无法合法完成 | `draft`；issues指明具体必交成果、无法完成的部分及必要缺口，不能只写“需专业复核” |
| 仅外部登记、等级依据或后续办理状态待确认 | 单独如实记录，不据此改变专业内容状态 |

- `task_requirements`如实列候选本次必须实际执行的操作，未来核验计划不当成本次访问未提供图像或法院系统的要求。
- 保留真实业务所需检索、核算和文件成果，区分文本可判断结果与必须操作才可验证的部分。
- 作者工具不等于候选工具；文字成果不等于实体文件，检索计划不等于已检索。
- 当前能力不足时如实记录，不自动删项或免分，不以操作失分独自证明推理难度，不冒称正式文件／工具评测通过。

### 法源与真实检索

#### 引用格式

| 类型 | 必须包含 |
|---|---|
| 法律、行政法规 | 全称＋中文数字条次，款、项及“之一”“之二”不能省略 |
| 原文标为“部门规章”的一行 | 全称＋发布机关令号 |
| 司法解释 | 全称＋法释文号 |
| 修订版本 | 修订年份写在书名号外 |
| 案例 | 案号＋裁判要点＋来源 |
| 域外法 | 原文名称＋编号＋条次，首次附中文译名 |

**不能只写条号，必须给出条文原文或规定摘要**，便于裁判判断该规定是否支撑分析。

#### 检索轨迹与来源

检索轨迹为所有任务类型的必交项，必须是专家办理过程中的真实记录，不能由模型生成或事后补写。

| 检索轨迹字段 | 要求／作用 |
|---|---|
| 检索词 | 记录实际检索入口 |
| 命中要点 | 法条原文或裁判要旨摘录 |
| 来源URL | 能定位到法规或裁判正文 |
| 版本核验记录 | 材料引用旧版、基准日应适用新版时，写明新旧条号对照 |

轨迹必须覆盖主交付物与评分细则中的每一条援引；没有轨迹的援引视为未核验。允许作为依据的是官方正文来源、国家法律法规数据库、法院正式案例来源、北大法宝／威科正文页、域外官方数据库。行业解读仅辅助理解；公众号、律所推文、百科、问答社区、聚合资讯不得作为依据，出现时按负向条目扣分。

### 文件清单与路径

| 字段 | 要求 | 作用／结果 |
|---|---|---|
| `path` | 相对 `/app/output/` 的文件名；必交文件必须精确命名 | 定位交付物 |
| `required` | `true`必交，`false`可选 | 必交文件缺失即未完成交付 |
| `desc` | 一句话说明 | 说明文件用途 |
| `artifacts` | 必交文件路径加 `/app/output/` 前缀展开 | 登记产物路径 |

- 任务书、清单、`artifacts`、两份标准答案、评分描述引用的路径须逐字节一致。
- 文件名不得含动态日期、时间戳或版本号；单个文件名≤200字节。

- 标准答案位于 `solution/golden_output/`，评分侧副本位于 `tests/__golden_output/`，两份内容一致、均不能为空。
- 应满足全部正分项且不触发扣分项。

## 四、评分方案

用途：把专业人员对交付物实际可用性的判断，拆成裁判可以独立判断的具体评分点。

### 判据设计

#### 设项与数量

- 从已核验的完整标准成果提取独立业务结果。本轮Work按项目方反馈，完整题包至少30项（正项、负项、独立否决合计），草稿如实保留已完成部分。
- 先去重，再拆可独立判断的业务结果，不能拆句、重复文件或增加无关形式项凑数；不足时继续完成真实工作或说明具体缺口。
- 数量不证明难度。覆盖核心内容，修改成果时同步修改判据。
- 作者整题设计、材料清点、等级／人时估算留在题目信息或`level_basis`；裁判方法只用于解释判据，不另立得分项。
- 候选自己的办理计划可按主体、顺序、依赖及期限评价。

#### 独立结果与去重

- 代入“甲正确、乙错误”：各有独立业务意义则拆条，共同决定同一结果的必要条件可整体判断。
- 同次计算的基数、公式和结果不机械拆开；不同金额、证据或法源不因同主题而捆绑。
- 按实际业务后果定权，核心判断分不能由表格齐备、重复列数或复述基准日替代；不因非决定性细节遗漏将独立核心结果整项归零，不把拆出的小项机械设为高分。
- 逐对比较条目实际奖励的结果，不看维度名称：同一组数字的复算及算术差异只在Q5主项计分，不能换成“事实冲突”“推理核验”再次奖励。
- 证明范围、法律门槛或行动确有独立结果才另设项；必要复用同一金额不自动新增得分。
- 负项命中额外实际错误，不将正项的反面换名再扣；独立否决单列。

#### 自包含条件与判定方式

- 正向写正确完成的结果及必要依据，负向写实际错误行为。
- 每项自包含，写全判定事实、正确值、法规内容、命中条件及合法接受范围；标题或能力名不能代替判据，不能写“详见参考答案”“参照上条”“等”等省略表达。
- 主观项不超过总条数的10%。
- 精确核算与量级示例区分，写明必要精度、舍入方式及有依据的接受范围，不设统一容差或任意宽免。默认二元；确有质量分档意义才按既有Likert五档写完整锚点。

### 严格判断，满足即给分

#### 判分条件事先固定

- 把高标准写入本题`statement`，交付前固定，不要求评分者临场“更苛刻”。
- 要求来自真实委托或必要专业标准；要求分析、核算或执行方案的条目，明确可核对的依据、适用前提及业务结果，不能仅凭提到关键词、堆法条或空泛建议给分。
- 只要求结论的条目不得临时增加过程义务；需要依据的条目，猜中结论而前提错误不算满足。

#### 专业判断与条件结论

- 要求完成判断的条目，写清候选须解决的具体关系及结果：列出双方说法不等于评价证明范围，罗列请求权不等于论证本案成立条件，写“若成立则支持、否则不支持”不等于依据现卷作出有理由的判断。
- 确因材料缺失只能给条件结论时，接受明确缺失前提、不同结果及相应动作的答案；现卷已能判断的部分不能全部推给未来核验。
- 这些要求须来自本次业务，不能套用于仅要求整理或摘录的条目。

#### 命中、给分与负向触发

- 按候选实际内容及本条条件判断：缺失、前提错误或论证不成立严格依规则处理；内容满足条件必须给分，不因表达、顺序或合法路径不同于标答拒绝认可，也不额外要求复述作者思路。
- 二元按完整条件判断，Likert按已写锚点判断。
- 负分及否决须有实际触发证据，不能因正项未满足就自动触发。
- 不预设低分、不为达标调宽严；判据有误或歧义应明示，不在看到答案后添加要求。

#### 检索完成状态与编造的区别

- 检索及援引的负项区分“实际核验未完成”“未核依据被当作确定支持”和“编造来源或虚称已完成检索”。
- 明确标注为拟检索入口、待核来源或后续核验计划，不因尚未访问就认定编造；若据未核依据作确定结论，评价其实际的依据或论证错误。
- 必须真实检索的正项仍按实际履行判断，诚实披露不等于完成该项。

#### 类案与合法替代路径

类案标准评价真实裁判规则、可比事实和适用边界，接受同等有效且可定位的依据。只有业务确需指定的案例／文件才要求唯一对象，并在题面明示；作者检索到的某一案号不能自动变成候选必须猜中的隐藏答案键。公开业务要求不等于公开正确结论或评分清单。

评分边界示例（仅演示判断方法，不继承案件内容、成果组合或权重）：

| 边界 | 应调整 | 可保留 |
| --- | --- | --- |
| 独立结果 | “正确计算欠款金额，并判断上诉是否可行”应拆；两项可一对一错，影响不同业务决策 | 同一次计算的基数、公式和结果可合并；同一法律结论成立的必要要素不机械拆开 |
| 重复计分 | Q5奖励欠款算式正确，维度4又奖励同一算式正确，应保留一个主计分位置 | Q1评价凭证证明范围，Q6评价取得缺失凭证的行动，使用同份材料仍可分别计分；负项须命中实际错误，不能只因正项未满足就触发 |
| 主维度 | “指出缺少付款凭证及其证明缺口”归Q1；“明确谁向谁取得凭证、何时完成”归Q6 | 评价跨文件核验的方法可归维度4，但不再次奖励Q5已计分的计算结果；具体空话替代分析的行为可归维度7，不因涉及建议就一律归Q6 |

### 原始字段与单条否决

| 字段 | 定义及要求 | 作用／结果 |
|---|---|---|
| `id` | 正向`R{维度}-P{序号}`；负向`R{维度}-N{序号}`；否决示例`R0-V01` | 唯一标识、追溯评分项 |
| `statement` | 完整判定标准；包含正确值或错误情形、全部／任一条件、等效表达范围 | 直接决定是否命中 |
| `criterion_type` | `Objective`可验证；`Subjective`需结合语境 | 标识判断性质，控制主观比例 |
| `criterion_necessity` | `Explicit`任务明文要求；`Implicit`由职业常识或语境必然推导 | 标识要求来源 |
| `dimension` | 使用本次schema提供的完整维度名称；内容质量只填一个主Q | 汇总维度表现 |
| `evaluated_files` | 字符串数组，填写标准答案文件名；跨全部文件写`all` | 按文件功能找到对应被测输出 |
| `knowledge_points` | `法律域::具体知识点`；无对应知识点填空 | 按知识点定位短板 |
| `atomic_capabilities` | 每条0–3个；首项主导，其余兼考 | 命中率及失分归主导能力，兼考只统计覆盖 |
| `priority` | 与六档分数或`Veto`一一对应 | 标识重要性／危害性 |
| `score` | `10、7、3、-3、-7、-10`；否决为`null` | 确定加减分 |
| `type` | `binary`默认；或`likert` | 二元判定或分档判定 |
| `points` | Likert固定5；Binary及否决为`null` | 确定五档标度 |
| `trigger_count` | 可累计扣分规则；一次性扣分和正向为`null` | 确定按处数累计还是只计一次 |

#### 累计条件与独立否决

- 负向项先确定仅计一次还是按处累计；`statement`与`trigger_count`保持同一口径，不能同时出现两种算法。
- 仅计一次时`trigger_count = null`；累计时填写每处定义、分值与封顶口径。
- 不能因为是编造类就自动改成无封顶累计。

- 当前内容契约用一条`R0-V01`承载独立否决。
- 条内分开写本题有事实依据的具体违规、职业立场及三类编造触发条件；同一对象反复提及去重，三类分别计数，超过3处的门槛不变。
- 不要因外部建议自行增加R0条数、降低门槛或把普通错误当编造。
- 条目排序与方向前缀不替代正确条件，也不新增为所有题的实质扣分要求。

#### 权重与分析字段的职责

- `statement`写业务判定标准、合法替代、必要的likert档位或累计条件；数值权重以`score`为唯一来源，不在每条正文另写“计+7，否则0”等重复分值，以免与字段冲突。
- 本系统的`criterion/rule`由原始字段派生，不由作者另维护一套。

`evaluated_files`、`knowledge_points`、`atomic_capabilities`是分析型元数据，不进入判定正文、不直接参与计分、不改变净得分率或否决结果。

| F5 | Q1＋Q5 |

### 分值与否决触发

| `priority` | 分值 | 含义 |
|---|---:|---|
| Critically Important | +10 | 缺失会使整体结论方向错误、需要重做 |
| Important | +7 | 需明显补充核查或修改才能使用 |
| Slightly Important | +3 | 细节完善，可由复核人员补齐 |
| Slightly Detrimental | −3 | 易发现、修改成本低的小错 |
| Detrimental | −7 | 需回查材料或法源的重要错误 |
| Critically Detrimental | −10 | 违法建议、立场倒置、编造或核心定性错误 |
| Veto | 不计分 | 判定实务不可用，单独统计 |

#### 否决条件与普通扣分

- 一票否决包括具体违法／舞弊建议、职业立场红线，以及编造法规或裁判依据、事实证据、URL或检索轨迹分别累计**超过3处**的情形。
- 普通遗漏、说理不足、体例缺陷不应直接否决。
- 三类编造分开计数，不将不同类别合计凑到阈值。
- 负项引用某否决条时，该否决条须实际写全被引用的触发条件，不能只在负项中提及或留给裁判推断。
- 否决不使分数归零，对应负向仍正常扣分。

### Harbor字段与聚合

| 字段 | 要求／结果 |
|---|---|
| `criterion.id` | 与原始评分项编号一致 |
| `criterion.name` | 必填且等于`id` |
| `criterion.description` | 完整标准＋`output/具体文件名`；Likert附五档锚点 |
| `criterion.type` | `binary`或`likert` |
| `criterion.points` | Likert固定5 |
| `criterion.weight` | 只允许正数`3.0、7.0、10.0` |
| `criterion.negate` | 负向设`true`，不能使用负权重 |
| `judge.mode` | `individual`，逐条独立会话、串行评分 |
| `judge.prompt_template` | `prompt.md`，保留`{criteria}`占位符 |
| `scoring.aggregation` | `weighted_mean`；最终主分按固定聚合脚本计算 |

#### 计分结果定义


- Binary：命中／未命中。
- Likert：输出1–5整数，归一化为`(raw−1)/4`。
- 满分：所有正向分值之和，负向不进分母。
- 净分：正向得分减去负向扣分。
- Harbor主分：`clip(净分÷满分, 0, 1)`。
- 可用率：未触发否决的题目数÷总题数，独立统计。
- `reward.json`、`reward.txt`：主分；`reward-details.json`：逐项明细；评分不可用时另写错误结果。

## 五、题目信息

用途：记录题目的归属、任务类型、能力、长程性、材料来源及完成任务所需资源。

### 命名与分类

任务名称：在题面和标准成果完成后，根据材料正文和实际工作，用一句真实交办工作的话写清业务方向、具体场景和交付成果。使用明确动作，不把工作标签直接串成标题；自然表达，不套固定句式，不靠换人名或同义词制造差异，不提前给出待求结论，不从文件名补造事实。

对照示例：标签式“民间借贷三案分期和解中的恢复执行审查、单案核算与局部结清回复”；交办式“核清三案和解的履行情况，拟定恢复执行申请和单案结清回复”。成果表述须与标准成果对应。示例只说明表达差异，不限定题目方向、动作或成果组合。按本次输出结构填写名称，不自行新增字段。

交付前按本节命名要求和下表分类，核对名称与最终题面、标准成果一致；不符合时在本次出题内改写，不改变题目工作或分类体系。
