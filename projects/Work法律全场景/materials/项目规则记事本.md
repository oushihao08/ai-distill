# Work法律全场景项目规则记事本

整理日期：2026-10-13。此文件是规则摘要与冲突记录，不是项目方原文，也不取代项目方最新通知。来源链接和访问限制见本项目 [README](../README.md)。

## 一、项目目标与适用范围

项目评估大语言模型在真实法律工作中的产物能否被从业者实际使用，重点包括法律角色与立场、合规判断及处置、事实和证据梳理、法律分析、跨文件核验、检索及可执行交付。题目应来自真实法律工作流程，经适当脱敏，提供完成任务所必需的案件材料、交易文件或工作底稿；页面举例覆盖 PDF、Word、Excel、扫描图片等。

项目总体计划为 150 道新题。六类执业角色为诉讼律师、非诉律师、企业法务合规、法官/法院辅助、检察官/检察辅助、法规政策研究员；总体场景口径为 24 个二级分类、51 个三级场景。每个三级场景至少两题，同场景题目须更换案由、合同类型或业务情境，不能只改数字或名称。场景及任务类型的正式枚举须按项目登记资料填写。

业务覆盖公司与资本市场、知识产权、数据合规、劳动用工、私募基金、跨境贸易等，法域包含中国法、美国法等。任务类型包括咨询研究（F1）、审查审核（F2）、文书起草（F3）、方案设计（F4）、数据核算（F5）；按主交付物确定主类型，可以自然包含相邻能力。

## 二、任务长程性、题量及难度

- L1 不采用；L2、L3、L4、L5 均须覆盖。用户本次要求同样明确为 L2–L5。
- 项目总量计划按 L2:L3:L4:L5 = 50:50:30:20，即 150 题中的 50、50、30、20 题分布。这是项目总体配额，不等于已经分配给本专家的数量。
- 长程性按成熟法律专家完成真实任务所需时间、最短必要步骤、材料范围、工具使用、状态传递和一致性约束评定，不以堆文件、重复动作或篇幅制造难度。分级表中的“默认时程”参考值为 L2 0.5–2 小时、L3 2–8 小时、L4 8–40 小时、L5 40 小时以上；材料/步骤/调用量参考值依次为：L2 3–5 份材料、10–30 步、10–50 次工具调用；L3 10 份以上、30–100 步、50–200 次；L4 50 份以上、100–500 步、200–2000 次；L5 多项目或跨期材料、500 步以上、1000 次以上。工具种类参考为 L2 2–3 类、L3 3–4 类、L4/L5 4 类。它们只作佐证，不替代真实任务复杂度；超长程任务轮次不低于 15 次。
- 分级表另列“专家人时”参考数 L2 10–30、L3 30–100、L4 100–500、L5 500+；而题目信息要求按 3 年以上执业经验人员的实际任务耗时、以小时填写。该栏与“默认时程”看起来不是同一口径，原文未说明两者如何换算；填写专家耗时和定级时须向项目方确认，不把默认时程直接当作专家人时。最终级别由项目负责人确认。
- 用户通知要求：从 Claude Code 框架下所列模型中选三个测试：Claude Opus 5、GLM 5.3、Kimi-K3、Qwen 3.8-max0902；三模型平均得分不超过 55%。交付规范附录的口径是三分数算术平均严格低于 55%，并要求参考答案得分高于 90%。执行上建议以严格的“低于 55%”为目标，且保留每个模型分数和平均值，不把平均值误写成每个模型各自都必须低于 55%。
- 页面还要求参考答案通过 Oracle 预检；golden 主分 >0.90，否则整题退回修改。模型测试需检查完整性、源文件不一致和答案质量；人工检查题面、参考答案、评分项及 hack 行为。

## 三、项目总体配额与场景分布

项目规则中的总体量为 150 题；另规定 L4+L5 合计 50 题，分布于 22 个三级场景，相关场景通常至少 3 题；每个主要类别至少有一题 L5。按任务类型的总体参考数为 F1 15、F2 50、F3 50、F4 28、F5 7。角色参考量为诉讼 35、非诉 30、企业法务合规 45、法院 17、检察 14、法规政策 9。部分场景配额及批次比例是登记规划参考，应以可访问的最新认领表和负责人分配为准。

## 四、唯一性与来源文件

这是硬性结算条件：题目及数据包必须由专家新做，不得复用或迁移任何过往已提交的数据；在 Work360 法律、Work0-1、C 项目等其他法律项目提交过的题目均不得在本项目重复提交，发现重复不予结算。新题不能通过换名、改金额、改格式或局部改写旧题来规避。

因此新题须另行确认可用的新来源，独立构造任务背景、事实链、业务目的、问题和参考答案。不得复制或改编旧项目的案件文件、题面/提示词、事实组合、计算过程、参考答案、评分项、检索轨迹或其他已提交数据。对现有「豆包高经济价值」项目的具体相似风险见[项目情况与相似度分析](../项目情况与相似度分析.md)。

主规则还列出 Work360 法律项目约 65 个既有题目/场景作为避重范围，涉及借贷、买卖与建设工程、股东争议和公司退出、医疗/交通、跨境投资与 IPO 尽调、MCN/SaaS/主播、私募基金、采购和合规等方向。选题时除核对本专家自己的历史提交外，还要对照项目方完整的既有场景清单；这里列举的是风险类别，不代替逐题查重。

规则对输入材料数量给出参考下限：L2 至少 3 份，L3 至少 10 份，L4 至少 50 份，L5 至少 100 份；L5 还强调跨项目/跨期且来源独立。材料应完整、真实、适度脱敏，并与任务直接相关，不能用无关附件、空壳文件、重复副本或人为拆分凑数。必要信息缺失时，应让真实工作者能够识别缺口并提出补充要求，不能令题目无从判断。

题面要复现委托人的真实口吻和必要背景、目标、约束、基准日期及交付要求，可包含真实场景中的冗余或矛盾信息，但不要把答案、考点、法条结论、应使用的工具或目标陷阱直接泄露给模型。矛盾事实必须有材料依据可裁决，不能靠猜测。

## 五、参考答案与法律检索轨迹

参考答案由法律专家亲自完成，须达到真实可提交/可使用质量，结论明确，事实、法律规则和适用分析相连，角色立场一致，主体、金额、日期和不同交付物之间保持一致；计算口径可复核。按任务实际要求提供法律研究报告、风险清单、诉讼文书、合同/方案或核算表等。

参考答案须配套专家真实完成过程中的法条、案例检索轨迹，不能事后虚构。每项核心引用至少记录检索词、命中内容/摘要、官方或一手来源链接，并覆盖答案中的全部重要法律依据；必要时核对行为时点和法规版本。中国法应写法律全称、条号及相关内容，规范性文件写名称/文号；案例写案号、裁判要旨与来源。外国法需保留原文名称/编号/条文并给中文译文。只列法条号或只贴链接不够；引用应来自官方、法院或可靠的一手法律数据库，低等级来源不能单独支撑核心结论。

## 六、题目信息与登记

按项目分类表及认领登记信息填写：题目编号（页面示例格式为“法律-三级场景-提交日期-专家”）、法律角色/场景、F1–F5 主任务类型、能力点、L2–L5 级别、是否涉及视觉材料、来源及真实性说明、专家亲自完成标准答案所用工时、需要的工具和专业知识。项目负责人最终确认长程等级；不要把题包制作时间误填为专业任务工时。目录名、任务 ID、task.toml 字段及交付件之间应一致。

## 七、Rubrics 设计

Rubric 评估的是交付物的实务可用性，不是与参考答案逐字相似。评分项必须从最终 golden_output 拆出：答案核心内容须覆盖，答案没有的要求不得凭空加进 rubric；改答案时同步复核 rubric。裁判只看被测产物及评分标准，因此每条标准要自包含，写出判定所需的事实、正确数值/日期、具体法源内容、标准答案条件、等价答案范围及扣分触发方式。

### 七维度与否决

1. 指令遵循与任务理解（必设）。
2. 交付物内容质量（必设，含 Q1–Q7）。
3. 体例规范与可读性。
4. 推理与规划/过程。
5. 安全合规（必设；可主要设负向项）。
6. 协作体验与可编辑性。
7. 反偷懒与反模板。

每题还须从维度 3、4、6、7 中至少选两项。Q1–Q7 中至少选择三项，并包含任务类型指定的两个锚点；锚点正向分值须占全部正向分值至少 30%。任务类型锚点：F1=Q3+Q4，F2=Q2+Q3，F3=Q1+Q4，F4=Q4+Q6，F5=Q1+Q5。Q7 默认只设负向一致性标准。

正向标准要完整覆盖 golden 核心点；负向标准写具体错误输出，不以“没有做到”重复扣分。评分项保持原子、客观、完整、自包含、允许合法等价路径。同一错误原则上只在一处扣分。Subjective 条目不超过 10%。每题至少两条 +10 的关键项；-10 仅用于重大法律错误、造假、违法建议、业务安全或合规风险，不滥用。

Rubrics 设计文档给出的评分档为正向 +3/+7/+10、负向 -3/-7/-10；高低按造成的法律/业务后果、返工及纠错成本判断。总体分数为命中正向分与负向扣分之和除以全部正向满分。一票否决为独立的可用性统计，不计入净分，也不把整题自动归零；每题一条 R0-V01，针对具体违法/执业红线、角色立场红线或重大编造。通常采用 binary；确需 Likert 时须给五档的明确锚点。

### Harbor 评分器映射

Rubrics 设计文件说明评分逻辑/JSON；题包交付规范另规定 Harbor 的 `rubrics.toml`。不得把设计文件的负数原样写为 Harbor weight：Harbor weight 只用 3.0/7.0/10.0，负向项使用 `negate = true` 和正 weight。criterion 的 id 唯一，name 必须与 id 完全相同；description 须可独立判定并列明 `output/<文件名>` 路径。type 仅 binary/likert；likert 显式写 `points = 5` 并列 5/4/3/2/1 档位。prompt.md 保留 `{criteria}`、公平性说明、材料地图和参考答案使用政策；模板 + 全部 description 小于 100 KB。具体固定模板必须按交付规范附录 A 逐字复制，不能凭摘要重写。

## 八、Harbor 题包与运行环境

概念上的五部分是任务描述、源文件、专家参考答案及检索轨迹、Rubric、metadata。最终每题须按交付规范转为 Harbor 目录，示意如下：

```text
<TASK_ID>/
├── instruction.md
├── task.toml
├── rubrics.json
├── environment/
│   ├── Dockerfile
│   ├── requirements.txt
│   └── input_files/
├── solution/
│   ├── solve.sh
│   └── golden_output/
└── tests/
    ├── test.sh
    ├── finalize.py
    ├── rubrics.toml
    ├── prompt.md
    └── __golden_output/
```

其中 task.toml 保存运行配置/元数据；源文件映射到只读 `/app/input_files`；模型交付仅写 `/app/output`；参考答案位于 Oracle/测试挂载区域，模型不得读取。metadata.deliverables 中的路径必须与 instruction、artifacts、两份 golden、rubric 所列输出文件逐处逐字节一致；文件名大小写敏感、不得使用通配符或版本日期后缀。必须保留空的 requirements.txt（无依赖时）。

交付规范还约束：题目 ID/目录名/任务名一致；network_mode 固定 public；input 文件和最终包体积遵守上限；不含真实 key/token/凭证；不带 .git、缓存、虚拟环境、系统杂项和本地评分残留。Dockerfile 使用规定的基础环境和官方包源，安装指定 Claude Code CLI、RewardKit 和解析库；容器自检确认运行时、工具及写入路径。参考资源上限为 2 CPU、8192 MB 内存、30720 MB 磁盘；模型时限默认 72000 秒，verifier 18000 秒，单次 judge 7200 秒且 verifier 超时须更长。输出不超过 2 GB，整包不超过 20 GB。细节和附录脚本以交付规范原文为准。

## 九、制作、验收、提交与返修

主流程为认领场景 → 准备新源文件、题面、专家答案/检索轨迹、rubric、metadata并按要求提交 → 质检和返修 → 转 Harbor 并初测难度 → 补充修改 → 最终完整性及答案质量验收 → 项目方确认等级和结算。项目主规则中的专家初稿五项为 `任务说明.docx`、`题目信息表.docx`、`评分要点.xlsx`、`input_files/`、`golden_output/`；确认稿改为 `instruction.json`、`metadata.json`、`rubric.json`、`input_files/`、`golden_output/`，再按题包交付规范转换成 Harbor。模型测试未达难度线时应调整任务和评分设计，再重新验证；不得为达到阈值而改评分规则或伪造运行证据。

常见退回原因包括：题面泄漏答案/考点或缺基准日；材料矛盾无法裁决、脱敏后主体关系不清、缺签署/关键材料、合成材料冒充真实或摘录凑数；golden 编造事实/法源/案号、结论不确定或缺检索轨迹；Rubric 漏点、重复扣分、权重/否决标准不清；题目信息、长程等级、材料格式或实际交付不一致。

用户本次提供的通知明确：认领后 5 天内上传任务包；收到质检意见后 2 天内完成返修，无法及时完成时提前向项目方说明。项目主规则另写有收到工作流反馈后 1 个自然日内逐条响应，否则视为放弃、不予结算。此处可能是“先回复”与“完成返修”的不同要求，也可能存在冲突，须在认领时向项目方核实；当前执行按用户本次提供的 5 天/2 天通知记录。

主规则还写有批次安排：第一批 60 题截至 2026-09-30，第二批 90 题截至 2026-10-16；本记录日期为 2026-10-13，第一批日期已过。该总体批次表不能替代本次用户提供的认领后 5 天规则，实际批次和专家份额待确认。文档提及单题试做/测试期为 2 天。

返修需逐条回应质检意见。Harbor 重交时 task.version 补丁号递增，只提交修订题目目录；批次目录和 zip 名增加 `_fix<N>`，随批次附交付说明及环境变量表。按规范完成 Oracle golden 预检并保留真实模型/裁判分数。
