# Work 法律全场景交付规范

核对日期：2026-10-14。本文覆盖内容稿、确认稿、出题平台流转和最终 Harbor 包，重点列明评分器必须遵守的约束、运行成功／失败产物、验收和常见问题。出题、专家答案及原始 Rubric 的详细内容要求见[出题规范](出题规范.md)。

> **【本轮截止】**认领后 5 天内在出题平台提交；收到质检意见后 2 天内返修，无法按时须提前联系项目方协调。此为本轮项目通知，区别于 D 原文中的试标与通用反馈时限。**【验收分数】**待测模型从 Claude Opus 5、GLM 5.3、Kimi K3、Qwen 3.8 Max 0902 中选 3 个；本轮通知写均分 ≤55%，H 写严格 <55%，稳妥目标按 **<55%** 控制。Golden 的 Oracle 必须 >0.90 且 `verifier_error=0`。

**标记含义：** **【提交红线】**缺失可能导致拒收／返工／不结算；**【正向分】**命中有效正向 criterion 才加分；**【扣分】**仅按本题明确负向 criterion 扣分；**【否决】**独立影响可用率，不并入数值分；**【提质】**提高实务可用性，不代表额外奖励分。

## 2. 内容稿、确认稿与 Harbor 转换（D 第2节、第3.6节；H 第1节）

### 2.1 专家内容包

D 的初稿根目录名为 `法律-{三级场景编号}-{提交日期}-{专家姓名}`，固定五项如下：

```text
├── 题目信息表.docx
├── 评分要点.xlsx
├── input_files/

```

D 的确认稿改为以下五项；`input_files` 和 `golden_output` 必须为英文小写加下划线，不翻译、不改名：

```text
法律-IC14-20260910-张某/
├── instruction.json
├── metadata.json
```

内容包返修在文件夹名后加版本如 `-v2`，增加 `返修说明.docx`，逐项回应质检意见。不能以“评分要点”摘要代替完整标准交付物，也不能用 Harbor 的 solve.sh 复制逻辑替代专家答案的实际制作与核定。

### 2.2 官方内容流程、平台提交与时限

D 列明的实际环节为：登记认领及主交付物 → 提交任务、材料、专家答案、检索轨迹和 metadata → 书面内容质检及返修 → 项目组仅作格式转换、内容不变地转 Harbor 并初测 → 最终模型测试、缺陷返修和负责人验收／结算。

- 认领格式为“三级场景编号-专家姓名-行业-案由／合同类型／业务领域”，并登记本题实际主交付物。
- **【本轮执行时限】**按当前项目通知：自认领任务之日起 **5 天内**在出题平台提交任务包；收到质检意见后 **2 天内**完成返修。预计无法按时，提前说明并与项目方确认安排。逾期可能导致任务释放、重新认领或影响后续验收结算。
- D 原文另有“正式任务前每人试标一题、认领后两天内交试标包”和“每步反馈后一个自然日内回应”的通用流程。它与本轮 5 天／2 天通知不是同一阶段口径；当前题目按本轮项目通知执行，试标或其他批次要求以负责人最新明确安排为准，不能把旧时限套到当前任务。
- 对质检有疑义，在返修意见中逐项注明并随返修同步；修改任务要求、材料、答案或评分项时，关联内容一并修订。
- D 的计划日期为第一批 60 题 2026-09-30、第二批 90 题 2026-10-16；每批独立覆盖 51 个三级场景。日期为本次读取值，新认领、补交、延期须核对项目方最新安排。
- D 开头称流程“六步”，但当前正文列出的标题只有第一至第五步；不能自行补造第六步。

D 写项目组负责转换，开头又要求供应商按 H 交 Harbor 包。应按当前对接分工明确由谁构建／自测／提交最终包；不因分工待确认而减掉最终包的必交要求。

**【平台操作必经】**完成平台五件套并通过“脚本实时质检”后，导出“五件套 ZIP”并上传“出题认领平台”；上传后点“全部执行”，确认“1 浏览执行”成功，再等待质检及书面反馈。上传成功或脚本实时质检通过不等于质检通过。需要返修时，用“导入五件套”载入原包，在平台修改后重新质检、导出和上传；返修 ZIP 文件夹名增加 `-v2` 等版本，并附 `返修说明.docx` 逐项回应意见。平台五件套是专家内容包阶段，Harbor 六件套是后续转换交付，不能互相替代。

## 4. 任务书、命名和 task.toml（H 第2–3节）

### 4.1 六处命名一致性

必交文件使用固定精确路径，不用 glob、通配、“或等价命名”；glob 仅允许可选过程产物。业务上确需日期时把日期写为固定字符串，不能让 Agent 自行生成时间戳或版本名。

以下六处对每份必交物逐字节一致，包含大小写、全／半角、空格、下划线与连字符：

1. instruction.md 的交付清单；
2. `[[metadata.deliverables]].path`；
3. artifacts 中的输出绝对路径；
4. solution/golden_output/ 的相对文件路径；
5. tests/__golden_output/ 的相对文件路径；
6. criterion description 的待查文件清单。

`deliverables.path` 相对 `/app/output/`，需要子目录时明确写出并使用 `/` 分隔；`required=true` 表示缺失即未完成，`desc` 为说明。artifacts 按每个 required=true 的 path 加 `/app/output/` 机械展开，不增不减。可选项不能无故成为必交评分条件。

description 按模板明确列出 `Deliverables to inspect: output/文件名` 等可定位的文件路径；评分工作目录是 /app，故该相对路径对应 /app/output。不能只给目录、只写中文功能名，或靠 evaluated_files 推测要查哪个文件。

任务书自包含，逐一说明 input 文件及字段／口径；不依赖隐藏语境，不泄露 Rubric 或 golden。完成业务所需的检索任务和网络能力须与题包真实环境一致，不能把自包含误解成所有法律任务都不得检索。

### 4.2 配置字段和固定值

`schema_version`、`artifacts` 写在文件最前的根级位置；先定义 `[metadata]` 再定义其 deliverables 等表，避免 TOML 表作用域将根级字段吞入前一表。不把原文中的自然语言、全角标点或 JSON 示例直接粘成 TOML。

| 字段 | 要求 |
| --- | --- |
| `schema_version` | 固定 `"1.4"` |
| `artifacts` | 仅由必交 deliverables 路径展开，见上文；不复制示例额外日志路径 |
| `[task].name` | 原文示例 `work/LAW-001`；org 与实际供应商代号的一致性要求有差异，见第 12 节 |
| `[task].version` | 首版 `"1.0.0"`，返修递增补丁号 |
| `[task].description` | 一句话任务描述，可用任务书标题 |
| `[task].keywords` | `["LAW", "office", "L2–L5中的实际等级"]`，不是将这段范围文字作为字面值 |
| `[metadata].task_id` | `LAW-序号`，如 LAW-001；与题目目录及 task.name 的题号部分归一化后一致 |
| `domain`／`domain_l2` | 法律／当前登记表对应二级场景标签，不自行归类 |
| `capabilities` | 本题真实可评测的具体专业能力，必填 |
| `vl_dependency` | “是／否”，必填；扫描、图片、图表及 PDF 范围差异见第 12 节 |
| `source_note` | 为何选题、真实来源如何保障、实务交付物是什么，必填 |
| `tools` | 必要办公工具／数据库，必填 |
| `domain_knowledge` | 所需专门知识，选填 |
| `task_complexity` | L2–L5，必填；按真实材料、人时和必要步骤 |
| `tool_set` | 环境实际提供给模型的工具集合，必填 |
| `skill_set` | 选填，与 environment/skills/ 下目录逐一对应，可含发现型干扰项 |
| `expected_tool_dependencies` | 选填，tool_set 子集，只有不依赖就无法完成任务的工具 |
| `expected_skill_dependencies` | 选填，skill_set 子集，可为空；不能把“安装了”当“必须使用” |
| `expected_pass_rate` | 选填，0–1 的预估，不是通过验收的证明 |
| `[[metadata.deliverables]]` | 必填，逐件 path／required／desc，不漏实际必交产物 |
| `[agent].timeout_sec` | 必填，默认 72000 秒；L4／L5 按实际需要上调 |
| `[verifier].timeout_sec` | 原文值 18000.0 秒，必须大于单 judge 会话超时 |
| `[verifier].user` | `"root"` |
| `[verifier.env]` | judge 凭据、模型／协议入口使用 JUDGE_ 前缀；其他基线变量按完整官方模板；真实凭据由运行环境注入，可选项有默认值 |
| `[environment].network_mode` | 必填，固定 `"public"`；不能自行改 no-network，否则 Claude Code setup 可能超时 |
| `[environment]` 其他资源 | os／build_timeout_sec 等按当前完整官方示例；CPU 2、内存 8192 MB、存储 30720 MB，确需上调在交付说明写原因 |

`[environment]` 仅允许：`os`、`network_mode`、`allowed_hosts`、`build_timeout_sec`、`docker_image`、`cpus`、`memory_mb`、`storage_mb`、`env`、`healthcheck`。不增加 `workdir`；工作目录在 Dockerfile 用 `WORKDIR /app` 设置。

`[environment].env` 只放候选完成任务必需变量；不得出现真实凭据、JUDGE_* 或评分信息。断网语义题先确认平台适配方案，不能把基线直接改断网。

## 5. 环境镜像与必须预装的依赖（H 第4节）

每题一个 Dockerfile；公共依赖直接写全，执行侧依赖由 requirements.txt 安装；全部走官方 Debian、registry.npmjs.org、pypi.org 等源，禁止 npmmirror、阿里云 PyPI、Docker registry mirror 等国内镜像源。

| 检查对象 | 本次原文要求 |
| --- | --- |
| Python | ≥3.12，提供 python3；参考基础镜像 python:3.12-slim |
| shell 与基础工具 | bash；参考镜像安装 ca-certificates、curl、git、jq、ripgrep、unzip 等所需工具 |
| Node.js／npm | Claude CLI 运行依赖，必须可用 |
| Claude Code | verifier 不由平台代装，必须预装并满足原文固定版本 `2.1.114`；不能仅检查命令存在 |
| Reward Kit | 固定 `harbor-rewardkit[all]==0.1.7`，root 的 PATH 可执行 rewardkit |
| 文档读取库 | markitdown、openpyxl、pandas、python-docx、pypdf、python-pptx、PyYAML、chardet、matplotlib 等模板依赖；本题额外格式库写齐 |
| 中文文档支持 | 模板含 LibreOffice Writer／Calc、fonts-noto-cjk，供文档读取、渲染与核验 |
| 用户及输出 | 存在 agent 用户（参考 UID 1000），/app/output 可写；/app/input_files 为 root 管理且取消写权限 |
| 工作目录 | Dockerfile 明确 WORKDIR /app；COPY 的源均来自 environment 构建上下文 |
| 额外执行依赖 | requirements.txt 预装；没有依赖也要提交空文件，不能指望模型运行时临时安装 |

Claude 模板“仅缺失时安装”的分支不能证明预装旧版本合格，最终仍以实际版本自检为准。上列版本是本次原文硬要求，不能用“可能更新”自行放宽；项目方发布新版本后按新要求整体核对。

官方镜像自检需核对 Python、bash、node、Claude 精确版本、Reward Kit、markitdown、文档库 import、pip check、agent 用户及输出写权限，末行打印 OK 才算该自检通过。H 第4.2节 参考命令：

```sh
docker build -t LAW-001 environment/
docker run --rm --network none LAW-001 bash -lc '
  python3 -V && bash --version | head -1 && node -v &&
  claude --version | grep -q 2.1.114 &&
  rewardkit --help >/dev/null && markitdown --help >/dev/null &&
  python3 -c "import openpyxl, docx, pptx, pypdf" &&
  pip show harbor-rewardkit | grep ^Version: && pip check &&
  id agent && su agent -c "touch /app/output/.w && rm /app/output/.w" && echo OK'
```

这条离线镜像自检不等于把正式 task.toml 的 network_mode 改为断网，也不证明真实 judge API 或法律题目已通过。

## 6. Oracle 与两份参考答案（H 第5节、第6.8节）

solve.sh 的职责是把已由专家形成的 golden 文件复制到唯一交付目录，不是在 Oracle 阶段临时让模型生成标准答案：

```sh
#!/bin/bash
set -euo pipefail
mkdir -p /app/output
cp -R /solution/golden_output/. /app/output/
```

必须核对：

- 两份 golden 目录均不为空，文件名、格式、数量、目录结构、内容一致，并匹配任务书及 deliverables。
- golden 满足所有正向 Rubric，不命中任何 negate 扣分项；不能仅因总分 >0.90 就放过已知答案遗漏或违法建议。
- 标准答案和真实检索轨迹按出题规范完成；不能将参考答案作为候选可见输入。
- 正向 Oracle 自测命令为 `harbor run -p <题目目录> -a oracle`；主分须 >0.90，且 verifier_error=0。
- 未命中项逐条核对：标准要求确有问题则修 Rubric，标准答案确有遗漏则修答案并同步 Rubric；不能无依据删除正确要求来抬高 golden 分数。

## 7. 评分器转换与计分（H 第6节；R 第1节、第4–5节）

### 7.1 TOML 字段不可省略或乱改

| 字段 | 必须遵守 |
| --- | --- |
| `[judge].judge` | 固定 `"claude-code"` |
| `prompt_template` | 固定 `"prompt.md"`，同目录 |
| `model` | 本次原文 `"GPT-5.5"`；合法 LiteLLM 模型串，无运行注入时兜底；运行时可由规定变量覆盖 |
| `timeout` | 显式 7200 秒；不留默认 300 秒 |
| `mode` | 显式 `"individual"`，每条 criterion 单独会话、逐条串行 |
| `[judge].weight` | 固定 1.0；只影响 Reward Kit 审计值，不作为主分权重 |
| `[scoring].aggregation` | 固定 `"weighted_mean"`；最终主分由固定 finalize.py 池化 |
| `[[criterion]].id` | 必填、题内唯一，与原始 Rubric 对应 |
| `name` | 必填且恒等于 id；不能依 description 自动生成中文 slug |
| `description` | 单条完整判据＋待查交付物具体路径；likert 包含五档锚点 |
| `type` | 只用小写 binary／likert |
| `points` | likert 必须显式为 5；判官输出整数 1–5 |
| `weight` | 只用正 3.0／7.0／10.0 |
| `negate` | 负向为 true，正向不翻转；不要将原始负分写为负 weight |

每条判据仍须满足出题规范：原子、自包含、客观、无歧义、不重复、允许等效有效方案，不能要求裁判补找正确值。原始分析元数据按原始文件保留；不要因 TOML 没有同名字段，就把知识点／能力标签混入评分条件。

必须覆盖维度 1、2、5，并从 3、4、6、7 至少再选两个；Q1–Q7 至少三个且含本题两个锚点；锚点正分合计 ≥全部正分 30%，至少两条 +10。Subjective ≤总条数 10%，Q7 默认只负向；−10 仅用于真正重大专业、幻觉、安全及合规问题，不恶意压分。

### 7.2 原始正负分与 TOML 的转换

| 原始条目 | TOML |
| --- | --- |
| +3／+7／+10 | weight = 3.0／7.0／10.0 |
| −3／−7／−10 | 相同绝对值的正 weight ＋ negate=true |
| Veto、score=null | 独立可用性信息；H 未明确专用转换／输出 schema，不能自行赋分加入主分 |

likert 必须逐档写 5／4／3／2／1 的可核验条件。正向按满足程度：5 完全满足、1 不满足；负向按违规程度：5 完全违规、1 无违规，Reward Kit 会翻转，不要再手工反转一次。

负向优先 binary。原始 `trigger_count` 中“每处 −7，可累计”的条目转 TOML 仍是一条 criterion，不拆成若干重复 binary；确需按次数／程度区分时，用一个 negate likert 写清五档和本题所有可命中情形，超出次数取最重档。**这会把原始可能无封顶的累计扣分限制到单项 weight，不能宣称数值完全等价；需要确认项目当前采用的转换口径。**

### 7.3 主分公式和否决边界

```text
S_max = 全部正向 criterion 的 weight 之和
分子  = Σ(正向 weight × value) − Σ(负向 weight × (1 − value))
reward = clip(分子 / S_max, 0, 1)
```

binary value 为 0／1；likert 原始整数 raw 按 `(raw−1)/4` 归一化；负向 value 已由 Reward Kit 翻转为“未违规程度”。例如 weight=7 的负向 raw=5／4／3／2／1，对主分分子的扣减是 7／5.25／3.5／1.75／0。

负项不进入分母；没有正向条目时主分无定义。原始净分率可能为负，Harbor 主分裁剪到 0–1，不能混用来计算或比较难度。Reward Kit 的 soft_score 仅为审计参考，不能替代 finalize.py 的主分。

一票否决只影响独立可用性统计，不再次扣数值分，不自动变成 reward=0；其 Harbor 存储／输出方式需要项目方明确。不得因为尚无专用字段而丢掉否决规则，或私加有权重的 veto criterion 改变主分。

## 8. Judge 提示词：评分重点与禁止事项（H 第6.2节）

prompt.md 必须保留完整平台政策，不能只留工具说明：

| 必须保留 | 含义与不能做的事 |
| --- | --- |
| `{criteria}` | Reward Kit 注入评分项的占位符；删除后 judge 收不到 criteria |
| Material map | /app/output 是唯一评分对象；/app/input_files 只用于真实性核验；/tests/__golden_output 是校准参考，不能混淆三区用途 |
| Fairness anchor | 保留官方公平性段；不增加“严格／宽松／尽量给分／目标低分”等表述改变宽严 |
| Reference-solution policy | 不能因参考答案有某内容就给候选分；不能因候选与参考答案措辞、顺序或同等有效结果不同就扣分 |
| criterion 权威 | 参考答案用于结构、字段名、数值量级校准，不是逐行／逐格／逐值的答案键；参考与 criterion 不同时，以 criterion 判据为准，并回查题包是否错误 |
| 技术工具提示 | 可用 Bash、Python、markitdown、openpyxl／python-docx／python-pptx／pypdf 等方式，工具提示不等于强制唯一路径；尝试实际已装库，不先假定不能读二进制文件 |
| 无法打开产物 | 确实无法用可用手段打开时，在理由明确说明；不能静默当成缺失、内容不满足或真实 0 分 |
| 环境限制说明 | 按真实评分环境说明原模板的无网络、无 Task／Explore 子代理等限制；这属于 judge 场景，不是关闭作者工具或把 task 环境基线改成 no-network |

prompt.md 模板 UTF-8 内容与所有 description 总量必须 <100 KB；不是单文件各 <100 KB。criterion 路径、五档和正确值都不能为压缩长度而省略；超限需按真实任务和原子性审查内容及平台方案，不能简单删掉判据。

## 9. 评分运行、环境变量和失败产物（H 第6.1节、第8.4节、附录 A）

### 9.1 固定链路与模板完整性

运行链为 harness → `bash /tests/test.sh` → Reward Kit 各 criterion 的独立 judge → `finalize.py` → AP 评分结果。供应商编写原始 Rubric、rubrics.toml 和 prompt.md；test.sh、finalize.py 必须复制完整固定模板，注释也保留，不改聚合或错误处理。

**当前页面转录已包含可见的 `tests/test.sh` 与 `tests/finalize.py` 代码块；页面“下载到本地”不可用，Markdown 转录仍不是可证明字节一致的原始文件。**实际交付前须将固定脚本与项目方提供的正式文件逐字节核验，并确认版本、首尾、占位符和权限；仅从转录复制、不能核验字节一致时，不得宣称固定模板已验收。`task.toml`、`prompt.md` 的示例是配置／提示模板，不替代每题按字段表完整编制的文件。本文表格与自检命令不是固定脚本的替代实现。

### 9.2 环境变量与覆盖关系

| 变量 | 必选／默认 | 作用与联动 |
| --- | --- | --- |
| JUDGE_API_KEY | 必选，运行环境注入 | judge 网关密钥；test.sh 派生 ANTHROPIC_AUTH_TOKEN／ANTHROPIC_API_KEY／OPENAI_API_KEY |
| JUDGE_BASE_URL | 必选，运行环境注入 | 网关地址；Anthropic 派生地址处理 /v1 后缀，OpenAI 对应地址由模板派生 |
| JUDGE_MODEL | 可选，GPT-5.5 | 经 REWARDKIT_MODEL 覆盖 TOML model；openai 协议降级时也决定模型串 |
| JUDGE_PROVIDER | 可选，anthropic；枚举 anthropic／openai | 原文为信息声明，本身不改变行为 |
| JUDGE_API_PROTOCOL | 可选，anthropic；枚举 anthropic／openai | anthropic 走 claude-code agent judge；openai 由模板设置 REWARDKIT_JUDGE，降级为 OpenAI 协议 LLM judge，工具提示不再代表其具备工具能力 |
| EVAL_API_KEY／EVAL_API_BASE | 可选，空 | 旧环境兜底；JUDGE 对应值已注入时优先使用 JUDGE |
| LITELLM_DROP_PARAMS | 可选，true；bool 字符串 | 网关兼容开关，按模板 |
| REWARDKIT_MODEL／REWARDKIT_JUDGE | 固定脚本识别的运行覆盖入口 | 不等同题目候选模型配置；若实际部署使用覆盖值，交付说明列出影响和优先级 |

TOML 的 `[verifier.env]` 中 judge 入口变量统一 JUDGE_ 声明；LITELLM_DROP_PARAMS 等其他基线变量按完整官方模板，不能把“judge 变量统一前缀”误解为禁止所有非 JUDGE_ 的基线变量。JUDGE_API_KEY 和 JUDGE_BASE_URL 用运行注入，不能写真实值。JUDGE_MODEL 等可选项按 `${VAR:-默认值}` 写明默认值。不在 TOML 另配 ANTHROPIC*／OPENAI*，由固定 test.sh 从 JUDGE_（旧 EVAL_API_* 兜底）推导。评分变量禁止进入 `[environment].env`。

单 judge 7200 秒和 verifier 总超时 18000 秒不通过环境变量覆盖；需修改 TOML 并重新交付，交付说明须写清。由于 individual 逐条串行，总执行可能跨多个会话；除满足“总超时大于单会话”外，还要在真实自测确认整体完成时间，不能凭这一个不等式认定所有评分项都能跑完。需要变更时按平台允许方式说明，不改固定脚本。

### 9.3 成功、真实零分和评分不可用

| 产物／状态 | 核对要求 |
| --- | --- |
| `/logs/verifier/reward.json` | 主分及有效性记录；检查 reward、verifier_error、criteria_counted 等实际结果，不能只看文件存在 |
| `/logs/verifier/reward.txt` | 单一 int／float，与 reward.json 的 reward 一致 |
| `graded/reward-details.json` 和 `/logs/verifier/reward-details.json` | 本地完整自检要求两份存在且一致；根目录明细副本为审计便利件，H 说明其缺失不改变已有效计算的主分 |
| 成功 | verifier_error=0、有效条目存在，且没有 reward_exit_message.json |
| 真实零分 | 评分有效且候选确实得 0；不能仅凭 reward=0 就下该结论 |
| 评分不可用 | verifier_error=1，并产生 reward_exit_message.json，含 exit_code、exit_reason 及模板规定的诊断字段；这不是候选答错 |
| 评分进程异常 | 非零 Reward Kit 返回、缺有效条目、带 error、非法权重、NaN／inf 等需按模板处理，不挑剩余正常项拼一个可验收主分 |

AP 错误码族为 `judge:timeout`、`judge:api_error`、`judge:parse_error`、`judge:scorer_error`、`judge:invalid_output`、`judge:unknown`，可有更细子级。按实际模板分类，不自行把所有失败都记为 0 分或 timeout。

固定脚本采用失败时的保护产物，成功后移除失败占位；finalize 自身正常退出也不证明评分可用，须看 verifier_error。正常候选缺失产物与判官无法读取格式、API 失败、超时、解析错误必须区分；不能利用评分失败制造低模型均分。

H 提交自检还要求人为制造一次失败（如临时不给测试环境 JUDGE_API_KEY），确认失败文件及分类正确；只在隔离自测环境执行，不修改业务凭据，也不把真实密钥写进题包。本文列出要求，不授权自动运行这些命令或真实模型调用。

## 10. 验收标准：同时满足，不互相替代（D 第1–2节；H 第6.8–7节）

| 验收项 | 本次原文要求 |

Oracle 通过不代表模型难度符合；三模型低分不证明材料准确；本地归档不证明平台正式验收。任务、材料或评分依据变动后，按关联影响更新答案、Rubric、配置及自测，不继承失效成绩。

项目专用入口为 `projects/Work法律全场景/batch-package.ts`，使用 Bun 执行。它从显式 manifest 读取批次名、交付文档、官方固定脚本和已制作完成的 `LAW-*` 题目目录；逐题检查必交路径、空目录、文件名、符号链接、脚本可执行位与 LF、两份 golden 的相对路径和 SHA-256、固定脚本原件字节一致，再生成“批次目录 → 题目目录 → 六件套”和一个 ZIP。目标已存在时拒绝覆盖；所有题目通过预检后才创建临时产物，出错清理临时目录。

## 13. 含 Skill 题目的额外要求（H 第3节、附录 B）

- **Discovery**：环境提供多个 Skill，由候选判断是否需要及选择哪个；expected_skill_dependencies 可为空，不能因为安装了干扰项就评分强制使用。
- **Dependency**：Skill 内特殊知识、业务冲突处理、审批 SOP、阈值／映射／优先级／fallback 规则实际决定结果；没有遵循会走错分支。任务书明确指定所需 Skill，不能只是泛泛知识与任务无关。
- **Generation／Editing**：可设计创建、修改、从 SOP 抽取、迁移和修复 Skill 包等任务；仍需真实工作价值、实际可检查产物及对应 Rubric。
- 文件按 `environment/skills/<name>/` 提供完整 SKILL.md、脚本及 references；由 Dockerfile 实际安装到约定位置（附录例为 /skills/），同时安装其声明依赖。skill_set 与目录一一对应，expected_skill_dependencies 是必要子集。
- SKILL.md 使用相应平台格式的 name／description／compatibility 及正文 SOP；要求原生修订、批注等特殊行为时，使规则影响最终产物，并设置可核验判据，不能只查回答声称“用了 Skill”。
