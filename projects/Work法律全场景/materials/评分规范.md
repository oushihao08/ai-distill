# Work 法律全场景评分规范

核对日期：2026-10-14。

> **【正向分】**只对有真实实务价值、由最终 golden 支持的具体内容给 +10／+7／+3；至少两条 +10，两个领域锚点的正分合计至少占全部正分 30%。**【扣分】**只对本题具体可观察的错误给 −3／−7／−10；不得为压低模型得分任意加重。**【一票否决】**独立影响交付物可用率，不进入数值分、不等于再扣一次分。**【验收红线】**题目与 Rubric 不一致、评分器报错、分数缺失或模型数不足，都不能当成有效低分通过。

**本轮模型口径：**从 Claude Opus 5、GLM 5.3、Kimi K3、Qwen 3.8 Max 0902 中选 3 个；项目通知写三模型均分 ≤55%，交付规范 H 写严格 <55%。按更严的 **<55%** 控制，正好 55% 不作为稳妥通过值。认领后 5 天提交、收到质检意见后 2 天返修属于本轮进度要求，不是 Rubric 分值。

## 评分对象与输入边界

- Rubric 是对候选交付物的可判定标准，不是对抽象模型能力的泛泛评价。
- 裁判模型以候选交付物和 Rubric 为评分依据；每条 `statement`／`description` 都要自包含，不能依赖裁判另看 golden、源文件或外部材料才知道正确值。
- 评分提示词可把输入文件作为真实性核验材料，并把 `tests/__golden_output/` 作为结构、字段和数量级的校准参考；不得因参考答案满足某条就给候选加分，也不得仅因候选与参考答案不同就扣分。Rubric criterion 才是计分依据。
- 只评价候选放在 `/app/output/` 的交付物；每条 Harbor criterion 的描述中列出要检查的完整输出路径。

## 维度要求

Rubrics 设计文档定义七个一级维度和独立的一票否决：

1. 指令遵循与任务理解（必设）
2. 交付物内容质量（必设，下设 Q1–Q7）
3. 交付物体例规范与可读性
4. 推理与规划
5. 安全合规（必设；通常集中设负向项）
6. 协作体验（可编辑性）
7. 反偷懒与反模板
0. R0-V01 全局一票否决（单独统计交付物可用率，不计入分数）

每题需覆盖一级维度 1、2、5；维度 3、4、6、7 中至少再选择两个。交付规范第 6.7 节另要求：Q1–Q7 至少选三个，并必须包括题目类型对应的两个领域锚点。若两份文档或后续规则有变更，以项目方现行原文为准。

| 任务类型 | 必选领域锚点 |
| --- | --- |
| F1 咨询研究 | Q3 法源定位与援引准确性、Q4 法律适用与涵摄定性准确性 |
| F2 审查审核 | Q2 风险与问题识别完备性、Q3 法源定位与援引准确性 |
| F3 文书起草 | Q1 事实与证据梳理准确性、Q4 法律适用与涵摄定性准确性 |
| F4 方案设计 | Q4 法律适用与涵摄定性准确性、Q6 结论确定性与方案可执行性 |
| F5 数据核算 | Q1 事实与证据梳理准确性、Q5 量化计算与门槛判断准确性 |

领域锚点对应的正向分值须占全部正向分值至少 30%；每题至少两条 `Critically Important`（+10）评分项。任务主类型决定锚点，但不是排他的硬边界，可以有相邻能力项。

### Q1–Q7 的考察范围

- **Q1 事实与证据梳理准确性**：事实完整、材料冲突采信、证据判断和材料缺口。
- **Q2 风险与问题识别完备性**：风险是否覆盖、风险等级及判断依据；实质障碍 +10，整改可解决的监管／程序不利 +7，补材料或确认即可解决 +3。
- **Q3 法源定位与援引准确性**：核心规范、条号和内容、时间效力、可比案例。
- **Q4 法律适用与涵摄定性准确性**：要件对应、定性结论、例外和抗辩。
- **Q5 量化计算与门槛判断准确性**：金额、比例、期间、基数、计算口径和法律门槛。
- **Q6 结论确定性与方案可执行性**：结论、动作主体、期限、材料、路径和替代方案。
- **Q7 内部逻辑一致性**：只设负向项，逐项列举具体矛盾；单一事实错误归 Q1，只有前后矛盾才归 Q7。

## 单条 Rubric 的编写

五项准则：

1. **原子性**：一条只判一件事；独立要点拆条。完整事实簇或必须同时满足的法定动作要素，可在有明确整体判定理由时合并。
2. **客观性**：判据写在条目内，将“专业、充分、准确”等抽象词转成可观察事实。
3. **完整性**：正向覆盖 golden 的核心内容；负向覆盖题目埋点和具体典型错误。
4. **自包含**：写明准确的法条内容、事实、值、日期、结论、比较基数、命中全部还是任一条件、计数方式及可接受等效表达。
5. **鲁棒性**：不同表述、章节顺序或同等有效方案不应改变判断；可接受范围须在条目中说明。

正向项应以终稿 golden 为唯一内容来源，逐项拆解而非凭经验扩写。负向项写“做了什么错事”，逐项列出具体场景；编造法规、事实、证据或检索来源按对象分类。多个可行法规、整改措施或定性方式要列出可接受范围；只给法律结论、没有可追溯依据的，不视为满足要求。

**【避免分数失真】**同一要点不得既作为正向漏项再以反面扣一次。指令遵循只检查动作、格式和硬约束；专业实质判断归内容质量。安全项的扣分和否决可以对应同一行为，因为否决不进入分数，只用于可用性统计。

## 维度细化与反偷懒

- 指令遵循按交付物齐备、硬约束、角色立场、基准时间四类设项；每类不超过一条。交付物齐备按二元判定，少一件即不通过；角色立场只设负向项。
- Q2 正向分值依不处置后果分档；Q3 只列核心法源，写明条文或要旨和对应问题；Q5 写正确值、容差和基数；Q6 按动作、主体、时限、材料判断。
- 体例维度优先检查法定或惯例要素；通用编号、层级、长表格等格式要求可合并，不应拆成大量低价值项。
- 推理维度看工作流顺序和必要交叉核验；交叉核验项写明具体材料及正确结论。
- 协作维度看是否能供下一环节直接使用，是否明确需要委托人确认的事项；不得替委托人默默作决定。
- 反偷懒维度至少一条负向项，结合题目检查回避结论、无关模板、只有标题、以“略／同上”替代要求内容、复制底稿冒充分析等，并写可核验阈值。
- -10 仅用于重大专业错误、幻觉、业务安全和合规风险。

## 分值、一票否决与聚合

**【正向加分】**只用 +10、+7、+3；**【负向扣分】**只用 −3、−7、−10。分别对应：

| 重要性 | 原始 Rubric 分值 | Harbor TOML 写法 |
| --- | ---: | --- |
| Critically Important | +10 | `weight = 10.0` |
| Important | +7 | `weight = 7.0` |
| Slightly Important | +3 | `weight = 3.0` |
| Slightly Detrimental | −3 | `weight = 3.0`、`negate = true` |
| Detrimental | −7 | `weight = 7.0`、`negate = true` |
| Critically Detrimental | −10 | `weight = 10.0`、`negate = true` |

原始 Rubric 的正负分值与 Harbor 计分权重是两种表示。TOML 只用正 `weight`，负向用 `negate = true`，不得写负 weight。

- 默认使用 binary（命中／未命中）。只有程度差异可量化且有质量意义时才用 likert；固定 `points = 5`，按 5/4/3/2/1 写完整、可核验锚点。原始 Rubric 负向可累计的条目，在 TOML 保持一条 criterion；按次数/程度设计 likert 档位或明确二元判定，不能拆成多个扣分项来重复计分。
- 原始 Rubric 满分为正向分值之和，净得分为命中正向分值加命中负向分值；R0-V01 未触发比例独立统计。
- Harbor `finalize.py` 按全题池化：主分为 `clip((正向 weight × value − 负向 weight × (1−value)) / 全部正向 weight, 0, 1)`。binary 的 value 为 0/1；likert 的 1–5 归一化为 `(raw−1)/4`；`negate = true` 自动翻转。不要由供应商另行聚合。
- **【Veto 不计分】**每题按原文总则设全题独立 `R0-V01`，`dimension = 0-一票否决`、`priority = Veto`、`score = null`。仅用于本题中足以使交付物不可用的效力／安全红线、角色／立场红线或明确幻觉红线；一般遗漏、普通专业错误、说理不足和体例问题不得判否决。
- 违规建议可按具体行为设 −10、可累计；编造法规、事实／证据、检索来源按对象分别设 −7 或 −10、可累计，且计入幻觉否决阈值。R 原文的幻觉否决阈值是“各类编造累计**超过 3 处**”，不得改成“达到 3 处”或“一次即否决”。负向分仍可正常命中；Veto 本身不再扣分、不自动把 Harbor 主分改为 0。R 的 Veto 条目数量／示例有冲突，且 H 没有专用输出字段；实际 schema 和项目方口径未确认时，不得把它转成带权重的普通 criterion。
- **安全维度不设“没有违法行为”普遍正向加分。**无违规是底线；不发生违规不应让所有输出平白增加分值。

## 字段与 TOML 评分器

原始 Rubric 至少按源文档字段表提供：`id`、`statement`、`criterion_type`、`criterion_necessity`、`dimension`、`evaluated_files`、`knowledge_points`、`atomic_capabilities`、`priority`、`score`、`type`、`points`、`trigger_count`。三个分析元数据字段仅用于监测和弱点定位，不进入 statement 或计分；`evaluated_files` 写 golden 文件名，不确定或跨文件写 `all`；`knowledge_points` 使用“法律域::具体知识点”；`atomic_capabilities` 最多 3 项，首项为主导能力。

TOML 评分器按交付规范设置：

- `[judge]` 固定 `judge = "claude-code"`、`prompt_template = "prompt.md"`、`mode = "individual"`、`weight = 1.0`；文档示例 `model = "GPT-5.5"`、`timeout = 7200` 秒。
- `[scoring].aggregation = "weighted_mean"`。
- `[[criterion]]` 的 `id` 须唯一并与原始 Rubric 对应；`name` 必填且等于 `id`；`description` 是独立判据并包含输出路径；`type` 只用 `binary` 或 `likert`。likert 必须写 `points = 5` 及五档锚点。
- `weight` 仅 3.0、7.0、10.0；负向用正权重加 `negate = true`。
- `prompt.md` 必须保留 `{criteria}`、material map、fairness anchor、reference-solution policy 与技术工具提示；参考答案只校准结构等，不得作为答案键。prompt 与所有 criterion description 总量小于 100 KB。
- 裁判超时 `7200` 秒；任务 verifier 总超时示例为 `18000` 秒，并大于单次 judge 超时。

Rubrics 文档 5.3 对原始 `type` 的枚举大小写写作 `Binary/Likert`，但字段示例使用小写，题包规范对 TOML 明确要求小写 `binary/likert`。迁移时按当前 schema/模板核对原始 JSON 的枚举大小写，不能将该处原文差异自行当成已消除。

## 评分验收

- **【Golden 门槛】**执行 `solve.sh` 后主分须严格大于 0.90 且 `verifier_error=0`；未达到应检查 Rubric 是否写偏并修订。不得删去正确标准或把已知错误当成合格答案来抬分。
- 提交验收还要求 verifier 无错误，Rubric 至少两条 +10、锚点正分占比至少 30%、维度覆盖满足上述要求，并且人工检查打分项、参考答案和 hack 行为。
- **【内容准确性】**任务描述、源文件、标准交付物和评分方案均须达到 99%。D 写 golden 得分率 ≥90%、三模型均分 ≤55%；H 对应项目门槛写成严格 >90%、<55%。本轮通知写 ≤55%，为同时满足两份口径，实际按 **golden >90%、三模型均分 <55%** 控制。三模型须从当前指定的四款候选中选择三个；分数必须来自真实框架的有效评分，不能补 0、用失败调用冒充低分或用单模型分数替代三模型均分。
- 数据集规则同时把任务真实性、源材料完整性、无存量题目重复、项目负责人验收列为验收条件。Rubric 应能暴露材料与答案不一致、虚构事实或案例、错误法律适用、交付物内部矛盾等本题具体风险；不能仅用抽象“准确、专业”替代可判定标准。

## 原文存在的口径边界

原始 Rubric 的“净得分率”与 Harbor 主分的“归一化并裁剪到 0–1”不是同一展示口径；保留两层定义，不混用。Rubric 源文档对 Veto 条目数量与示例存在冲突，见[出题规范第 11 节](出题规范.md#11-原文差异未决事项与使用边界)；没有明确答案前不能用自己的实现填补。评分维度和内容质量的更多要求由《Work法律全场景评测数据集构建规则》补充；模型版本和验收流程按当前项目通知核对。
