# 饱满去模板与防剧透表达

**用途：**在全部业务求解、实算验证与 Rubric 定稿之后，将内部设计转化为真实律所／法务高强度办案语言，消除说明书腔、四段同构骨架、剧透与 AI 痕迹——**绝不因去 AI 化而压缩业务信息量、删除实体文件要求或软化判据强度**。

---

## 一、零模拟与防剧透五禁令（`instruction` 与 `deliverables` 红线）

以下规则只约束作者编写的公开交办内容（`task_metadata.instruction`、`deliverables`、`task_name`），**原始业务卷宗完整保留，不删改附件**：

### 1. 零模拟与零虚构卷外事件

- 100% 立足所附真实案卷自然展开。**严禁**将同一卷宗人为切成“某日先收一批、某日再补一批”的虚拟双窗口，**严禁**编造卷外引号来函、补件或未发生的变故。
- **严禁出现以下模拟／测试设定词**：“模拟律师”“模拟场景”“模拟委托”“按模拟于某日接办”“本题模拟”“办理演练”“假定……”“题设前提”“材料取得窗口”“考察”“请注意”“重点是”“评分将检查……”。
- 核算截止日直接写明具体年月日（写入 `baseline_date` 并在业务语境中交代）或锚定在卷客观文书节点；卷内未记载后续清偿或送达状态的，作为真实证据缺口处理，**严禁写“假定截至某日无新增清偿”**。

### 2. 防剧透五禁令（把发现矛盾与选路留给作答者）

| 禁令 | 严禁泄露的内容 | 允许且应当写明的真实业务交办 |
| --- | --- | --- |
| **① 禁在文件名或标题中泄底** | 当救济程序、案由或请求权基础本身属于待裁决核心（如应走代位析产、债权人撤销权、执行异议之诉还是追加被执行人）时，不得在 `deliverables[].path` 或 `task_name` 直接点名胜出路径的文书名 | 仅交代客户要达成的结果与收件用途，用中性功能称谓命名（如 `债权追索路径论证与行动方案.docx`、`拟提交法院的权利救济主文书.docx`）；只有程序已定而待解问题更窄时才点名既定文种（如《上诉状.docx》） |
| **② 禁喂备选路径与排除结论** | 严禁在括号或诉求子项中提前点名替代请求权、除斥期间类型或明示“不得直接启用某诉请” | 只交代客户当前卡在什么问题、期望保住什么权益及既定底线 |
| **③ 禁提示跨时际修法与顺延** | 严禁提示“跨某年修法前后规则变化”“适用某年时间效力解释”“注意某法定节假日顺延”或直接点名清偿抵充等司法解释文号 | 要求依据在卷裁判、送达与履行材料核定生效日、救济届满期限、适用规范及分段本息 |
| **④ 禁点破在卷旧稿具体错点** | 交办复核在卷旧申请书、起诉状、协议草案时，严禁提前指出其错在管辖、主体信息错位、机关名称有误或漏算某项利息 | 交代旧稿原准备用在哪里，委托核查能否沿用并交回当前可直接使用的定稿或停用替代安排 |
| **⑤ 禁预告账据与查控异常** | 严禁提示“多渠道回执重复需去重”“某日存在退回款项”“面积／金额记载颠倒”或“查控时间晚于终本裁定” | 要求核对在卷全部收付、退费与查控记录，核定截至基准日尚可主张或应承担的净额并在工作簿与文书中落实 |

## 二、饱满业务交办与口吻适配（打破干瘪与四段同构）

### 1. 适配两类真实委托口吻（兼容 Work 双口吻规范）

- **普通委托人（自然人／企业经营者）**：以第一人称口述切入 `background` 与 `requests`，只讲亲历事实、现实困局、感受与期望结果；允许保留符合真实处境的不专业、不可行或越界诉求（用以检验作答者能否依法识别并纠偏），不预先解释证据性质、法律关系或规定专业文书体例。
- **专业委托方（资深合伙人、法务总监、办案机构）**：使用资深法律实务人士的正式工作交办口吻，直入程序死线、退件僵局、待审旧稿、交易拍板或对账打架，可交代专业用途与载体要求，但严禁提示考点或解法路线。

### 2. 保持饱满业务信息量，严禁缩水

`background` + `requests` + `hard_constraints` + `deliverables` 组合后须完整呈现真实复杂案件的业务语境，**绝不压缩成干瘪的几行提纲**，也不得使用“简要说明”“只需概述”“不必展开”等压缩作答深度的字眼：
- 写清当前卡住办理的现实处境、基于在卷文书的基准时点与触发委托的来件／旧稿；
- 写清已知接收人（合议庭、执行局、财务、采购、风控委、股东会等）拿到每份独立文件后**具体要拿去干什么**（待判断的受理机关与路径留给承办人）；
- 写清跨文件主体、金额、期限、附条件口径一致及授权纪律边界（不代签、不径行递交、不越权处分等随文嵌入对应业务处，不在结尾机械背诵负面清单）；
- 严禁放行纯文本交卷（绝不写“在回复中分件列出全文即可”“无须制作文件”），也不写“逐页转换为页面图像”“实际执行公式重算并读回”等测试防作弊黑话。

### 3. 打破固定模板与目录互抄

- **打破起手与结构同构**：不默认全批用“我方作为某某当事人，现以某年某月某日为基准日……”起笔；根据本案真实触发点灵活选择切入方式（客户当面问决定、退回旧稿改到哪、双岗位接手分流、围绕待审原句批注、时限逼近倒排等，详见 [书面表达与交办组件库](../assets/书面表达与交办组件库.md)）。
- **各字段各司其职，拒绝共享同一套小标题目录**：
  - `task_name`：聚焦本案最具辨识度的标的对象或核心待决动作；
  - `instruction`：按客户现实痛点、待决事项与收件用途组织；
  - `rubric`：按独立专业判断、原件依据与错办后果组织（不每条都以“在《某文件》中……”机械起手，不写“本条评价……”元话术）；
  - `reference_outputs`：按真实文种体例直接给收件人可用正文，**不默认每题都把《审签意见》放第一件**。

## 三、文书引用、格式洁净与保义终检

### 1. 分层文书引用规范

- **`input_files` 契约字段**：`attachment_id` 与 `name` 原样复制自 `delivery.json.input_files`（系统映射需要），`description` 写明该材料所含真实文书。
- **`instruction` 正文**：按客户知情范围自然点明触发委托的核心来件（如手头待审旧稿、刚收到的裁定／通知），**不按卷宗顺序报菜名式串列全部边缘凭证目录**（避免泄露边缘线索）；案号含 `(****)` 脱敏掩码时，改用不带星号的自然简称（如“某区法院民初第×××号判决”）；**严禁**声称随附材料为“调档扫描原件／手写原件”或要求鉴真笔迹印章，也**严禁**把完整在卷文书误称为“文字摘录／转录文本”。
- **`reference_outputs` 与 `rubric` 正文**：必须精确点明所附卷宗的具体原始文书名称及案号／日期／出具主体；**严禁**出现匿名哈希文件名（如 `材料-xxxx.docx`）、“合并卷宗”、本机路径或把内部序号 `附件1` 当作正式文书名。

### 2. 正文排版规范（适配 Work 五件套 DOCX/XLSX 渲染）

- `task_name`、`instruction` 各字段与 `rubric[].metadata.statement` 采用自然段与规范中文序号，不使用装饰性 `【】` 标签、不夹带代码围栏或 Python/终端脚本。
- `reference_outputs[].content` 采用真实正式法律文书层级（可供 Work 渲染器直接生成宋体正文、黑色标题的规范 `.docx`），严禁夹带代码围栏、脚本或内部制作说明。

### 3. 表达定稿四步保义终检

1. **遮头核验真实感**：遮住首句角色说明与案名，能否一眼看出客户卡在什么现实痛点、每份独立文件给谁办什么事？若像抽象说明书或考题，补实业务场景。
2. **漏交办与泄底双查**：单读 `instruction`＋`deliverables`，核对每项核心工作均有自然交办落点，同时逐句排查是否无意泄出待选路径、修法年份、顺延规则、旧稿具体错点或账据异常。
3. **强度零折损核对**：核对改写表达后，所有独立文件（`.docx`/`.xlsx`）、活公式动态复算、权威法源核验、最优合法口径与 `rubric` 判定边界均未弱化（“必须”未变“可考虑”、“且”未变“或”）。
4. **零残留扫描**：全量扫描 `task_name`、`instruction`、`deliverables`、`reference_outputs`（含全部 `sheets` 单元格）与 `rubric`——确认零模拟词、零评测黑话、零 AI／工具／候选视角残留、零 `(****)` 掩码、零“文字摘录”误称、零非法 `.pdf` 成果声明。
