# 五件套契约与交付规范（`work_legal_v1`）

**用途：**确保作者输出的 JSON 题包 100% 通过 `work_legal_v1` 代码校验，并在归档时无缝投影为 **Siriser 平台确认稿五件套**（`instruction.json`、`metadata.json`、`rubric.json`、`input_files/`、`golden_output/`）及后续 Harbor 衔接包。

> **格式铁律**：Work 业务成果（`deliverables`）**仅允许 `.docx` 和 `.xlsx`**，严禁声明 `.pdf`、`.md`、`.tsv` 或 `.txt`。

---

## 一、`work_legal_v1` 核心字段总览

按本次 `delivery.json` 提供的 schema 填写；**`question`、`reference_answer`、`answer_requirements` 及 rubric 的 `criterion/rule` 均由程序同源派生，作者不得另维护第二份**：

| 字段组 | 必填子字段与权威要求 | 五件套／下游去向 |
| --- | --- | --- |
| **任务识别** | `content_contract: "work_legal_v1"`；`task_name`（交办式自然短句，见第五节）；`task_type`（受控五选一：`F1 咨询研究`、`F2 审查审核`、`F3 文书起草`、`F4 方案设计`、`F5 数据核算`）；`header`（行业一二级、职业一二级填律师／法务岗位，不填当事人诉讼身份） | `metadata.json`、`rubric.json` 与锚点映射 |
| **`task_metadata.instruction`** | `background`（业务／案件背景与代理身份权限）；`requests`（非空不重复诉求数组）；`baseline_date`（`YYYY-MM-DD` 真实日期或无适用时点才填 `null`，禁拿开庭日／法条年份猜填）；`hard_constraints`（不重复的真实硬约束数组，逐条独立） | 经程序自动合成公开 `question` 并投影为 `instruction.json`（Harbor `instruction.md`） |
| **`task_metadata` 专业信息** | `occupation`、`scenario`（完整编号＋名称，与认领表一致）、`role_perspective`（单方立场）、`domain_l2`（二级标签或 `null`）、`capabilities`（2–4 项核心能力）、`professional_knowledge`、`vl_dependency`（布尔值，按任务是否须识读图像判断）、`source_note`（真实卷宗脱敏／原文来源与选题说明）、`generation_note`（AI／模型身份、生成边界与作者核验说明，**不进公开五件套**）、`tools`、`target_level`（`L2`–`L5`）、`level_basis`（`documents[]`、`necessary_steps[]`、`estimated_hours`、`explanation`） | `metadata.json`（`source_note` 进公开 `dataSource`；`generation_note` 留包外私有状态） |
| **`input_files`** | `{ attachment_id, name, description }[]`：**`attachment_id` 与 `name` 必须从 `delivery.json.input_files` 按顺序原样复制**；`description` 按本份材料正文如实填写用途与包含文书 | `input_files/` 映射与任务输入校验 |
| **`deliverables`** | `{ id, path, format, description, required }[]`：至少 **3 份**不同用途实质文书；`path` 为安全相对路径、≤200 字节、不含动态日期／时间戳／版本号、不重复无层级冲突；后缀与 `format` 仅限 `docx`/`xlsx` 且一致；`required: true` 必交项在 `instruction` 中清晰呼应 | `instruction.json`、`golden_output/` 与 Harbor `artifacts`（`/app/output/<path>`） |
| **`reference_outputs`** | `{ deliverable_id, content, sheets }[]`：与 `deliverables` **一一对应且全部非空**；`content` 为接收人可直接使用的完整正式业务正文；**凡 `format = "xlsx"` 必须提供非空 `sheets[]`**（`name` ≤31 字符不重复、`columns` 非空不重复、`rows` 每行长度等于列数且元素仅为字符串／有限数字／布尔值） | `golden_output/` 渲染为真实 legal 样式 `.docx`（正文宋体、标题黑色）与 `.xlsx`（含工作表＋“正文说明”表） |
| **`research_records`** | `{ id, query, source_url, source_title, version, findings, verification_status, supports }[]`：逐条如实记录作者本次实际检索、打开与核验结果，覆盖主成果与判据的每一条实际援引 | 保存于包外私有 `author_research_records`；如 `deliverables` 声明检索轨迹则同源对齐 |
| **`task_requirements`** | `{ input_mode: "text"|"image", output_mode: "text"|"file", tools: string[] }`：如实声明完成本题真实业务所需能力（交付可编辑文书／活公式表时填 `output_mode: "file"`）；不因当前纯文字 runner 删减必要法律工作，也不把作者工具机械填为候选义务 | 记录任务执行能力边界 |
| **`content_status`** | `{ status: "complete"|"draft", issues: string[] }`：按本次明确委托判定（见第四节）；**生成五件套交付前必须为 `complete` 且 `issues` 为空** | 五件套归档准入硬门槛 |
| **`rubric`** | 至少 30 项 `{ id, metadata }`，详见 [Work 评分方案与加压验题](03-Work评分方案与加压验题.md) | `rubric.json` 与 `评分要点.xlsx` |

## 二、F1–F5 任务类型、必含内容要素与载体设计

### 1. 五类任务类型参考组合（非固定全集，整体须 ≥3 份实质配套文书）

按本题核心工作与主交付物在 F1–F5 中择一，不为降重改类或自创类别：

| 任务类型 | 对应必选双锚点 | 典型配套成果参考（全部落地为独立 `.docx` / `.xlsx`） |
| --- | --- | --- |
| **`F1 咨询研究`** | Q3 + Q4 | 法律研究报告／法律意见书、类案／法源检索分析报告、实务处置建议或风险核查表 |
| **`F2 审查审核`** | Q2 + Q3 | 审查意见书或尽调报告、风险清单（`.xlsx`/`.docx`）、修订稿／修订说明或核心审查意见函 |
| **`F3 文书起草`** | Q1 + Q4 | 可直接提交或对外出具的文书正稿（如起诉状／答辩状／代理词／协议）、独立证据或附随材料清单、对内委托诉求处理说明／办案备忘录 |
| **`F4 方案设计`** | Q4 + Q6 | 整体方案或预案正文、法定动作与期限清单（`.xlsx`/`.docx`）、支撑依据与替代路径损益比较分析 |
| **`F5 数据核算`** | Q1 + Q5 | 结构化台账或活公式测算工作簿（`.xlsx`）、测算口径与证据认定说明（`.docx`）、分析结论与对外文书／预警清单 |

### 2. 五类核心成果必含要素

| 成果内容 | 必须包含的专业要素 |
| --- | --- |
| **风险清单** | 风险等级、风险描述、判定依据、修改或整改方案、是否必须修改（按风险由高到低排序） |
| **证据／附随材料清单** | 编号、名称、形式、证明内容、证明目的、在卷／待调取状态（按证明对象或请求权路径分组） |
| **法定动作清单** | 具体动作、执行主体、法定时限／起算依据、所需材料与触发条件 |
| **测算口径说明** | 基数口径、计算公式、数据来源凭证、假设／待核条件与舍入规则（保证可复算） |
| **法律分析** | 事实（可溯源文件）→ 规范（已核验法规或类案）→ 涵摄适用 → 明确结论（含不确定性条件与倾向建议） |

### 3. 检索报告 vs 检索轨迹的防重复规则

- **检索报告**：承载法源体系解释、新旧法过渡与类案比较及其对本案结论的影响（`.docx`）。
- **检索轨迹**：仅登记实际查询词、检索平台、命中要点、来源 URL 与版本核验记录（`.xlsx`，栏目格式参考 [检索轨迹填写示例](../assets/检索轨迹填写示例.tsv)）。
- **硬限制**：同一题 `deliverables` **至多声明 1 份**检索轨迹（且当交付链仅需作者 `research_records` 时可不重复列入 `deliverables`）；**严禁**复制轨迹表、工具过程或访问失败清单冒充第二份成果。

### 4. `.xlsx` 活公式与 `sheets` 落地规范

- 涉及逐笔收付、抵充、分段计息、财产分配、临界测算或后续补录复算时，在 `deliverables` 交办独立 `.xlsx` 工作簿，明确要求原始明细逐笔入表、派生列用活公式联动（待核留空与已知为零分离，默认待核留空零报错）。
- **不在 `instruction` 中写测试防作弊指令**（如“填入一笔假定变动试算后再恢复原状”），只在真实业务语境下要求“后续补录新回单或核实送达日后可自动联动更新余额与期限”。
- 在 `reference_outputs` 中，`.xlsx` 成果的 `sheets` 必须给出完整可核对的明细表与汇总表（含计算公式口径与核定数值），`content` 写全业务口径、原始凭据认定、差额处理及对对外文书的影响；五件套生成器会自动把 `sheets` 与 `content` 一并写入真实 `.xlsx`。

## 三、成稿质量、内外分件与受众纯净红线（代码级拦截）

### 1. 真实受众成稿与内外分件

- **按用途写足可用正稿**：诉状、答辩状、合同修订稿、函件须具备法定首尾与直接可签发／递交的正文，**严禁**以提纲、空标题或未来核查计划冒充成稿，对外正稿不夹带给起草人的“【请填写/请删除】”式指令。
- **严禁内外混装**：凡含官方网址出处核验、己方不利底牌、败诉风险评估、多路径净损益取舍或签发启用条件的对内决策说明，必须作为独立对内文件（如办案备忘录、审查意见、呈批说明）成件，**严禁**塞进提交法院或发给对方的对外清洁文书附注中。
- **不以固定标题开篇**：根据客户当下最先要办的事安排成果与开篇，不强求每题均以《审签意见》开篇。

### 2. 受众纯净硬拦截（`work-contract.ts` 自动检查）

`reference_outputs` 的全部 `content` 及 `sheets` 所有表名、列名、单元格**严禁**出现以下三类残留（命中即阻断五件套交付）：

| 禁用类别 | 典型禁词（全覆盖排查） | 正确存放位置 |
| --- | --- | --- |
| **AI 或真人制作身份** | `AI作者`、`AI生成`、`AI编制`、`模型生成`、`大模型撰写`、`作者为AI`、`非真人专家`、`真人专家确认/审核/认证` | `task_metadata.generation_note` |
| **内部工具与题包实现** | `AnySearch`、`ChatGPT`、`Codex`、`research_records`、`reference_outputs`、`Harbor`、`JSON内容稿`、`历史题包`、`历史评分`、`本次会话` | `generation_note` 或 `research_records` |
| **出题与评分视角** | `不要求候选`、`候选人无需/不必`、`作者网址`、`作者检索记录/轨迹`、`唯一答案键`、`参考答案`、`标准答案`、`Rubric`、`评分项/细则` | `rubric` 或内部自检（不落盘） |

- 业务成果仍须如实披露影响结论可靠性的**材料范围、原件未核、尚未实施事项和条件意见**，但一律使用正常法律业务语言（如“本意见基于委托方提供的现有副本材料出具，尚待核验原件及送达回证”），既不污染受众，也不冒充真人签署、实际立案或平台验收。

## 四、法源引用格式、真实检索与 `content_status` 判定

### 1. 法源引用硬格式（缺条文原文或摘要视为不完整）

| 法源类型 | 必须包含要素 |
| --- | --- |
| 法律、行政法规 | 全称 ＋ 中文数字条次（款、项及“之一／之二”不得省略） |
| 部门规章 | 全称 ＋ 发布机关令号（修订年份写在书名号外，如 2023 年修订《……》） |
| 司法解释 | 全称 ＋ 法释文号（如法释〔2020〕17 号） |
| 生效案例 | 案号（或入库编号）＋ 裁判要点 ＋ 官方来源 |
| 域外法 | 原文名称 ＋ 编号 ＋ 条次，首次附中文译名 |

**铁律**：援引不得只写条号，**必须附条文原文或规定摘要**，确保独立裁判无须打开外部链接即可核验规范是否支撑结论。

### 2. 权威来源红线

- **允许作为依据**：国家法律法规数据库、最高法／国务院／部委官网正文、中国裁判文书网／人民法院案例库等法院正式来源、北大法宝／威科先行正文页、域外官方数据库。
- **严禁作为依据**：微信公众号、律所推文、百科词条、问答社区、聚合资讯站（在答案中出现作为依据时，按维度 5 负向扣分）。
- **全覆盖**：主交付物与 Rubric 中每一条实际采用的法源／案例援引，均须在 `research_records` 中有对应真实核验记录（无轨迹即视为未核验）。

### 3. `content_status` 判定边界

| 本次委托与材料现状 | `content_status` 判定 |
| --- | --- |
| 委托要求基于现卷评价证据、出具条件性意见、核定可算区间及补证计划，现有材料足以完成全部必交成果 | `status: "complete"`, `issues: []`（原件待核与未来补证写入业务正文，不作草稿理由） |
| 必交成果要求确定性结论或实际办理，但缺少不可替代的关键输入使该部分无法合法完成 | `status: "draft"`, `issues` 精确指明具体必交成果、无法完成的部分及必要缺口（禁笼统写“需专业复核”） |
| 仅外部认领码、正式等级认证或线下办理状态待确认 | 单独如实记录于 `level_basis.explanation` / `generation_note`，不据此改为 `draft` |

## 五、任务命名与五件套／Harbor 衔接口径

### 1. 任务名称（`task_name`）

- 在题面与标准成果定稿后拟定：用一句真实交办工作的话点清业务对象、具体场景与交付动作。
- **四禁**：禁把工作标签直接拼串（“……的审查、核算与回复”）；禁批产对称句式（“[主体]的[A]与[B]”）；禁加“专项／全量／全套／闭环”空泛包装词；禁带 `(****)` 星号掩码或提前写出待求结论／待选救济路径。
- 参见 [书面表达与交办组件库](../assets/书面表达与交办组件库.md) 的多种自然命名方式。

### 2. 题目信息与 Harbor 元数据映射参考

Siriser 五件套（`metadata.json`）及后续 Harbor 元数据均从 `task_metadata`、`deliverables`、`rubric` 自动投影；填写 `task_metadata` 时须保证下列映射清晰无歧义（栏目组织可参考 [题目信息填写示例](../assets/题目信息填写示例.md)，不继承示例事实与结论）：
- `domain` 固定“法律”；`domain_l2` 对齐认领二级标签；`scenario` 对齐三级场景完整编号与名称；
- `target_level`（`L2`–`L5`）与 `level_basis`（逐份独立文书、必要步骤、专家耗时、说明）如实填写；
- `deliverables` 的 `path` 在 `instruction`、Harbor `artifacts`（`/app/output/<path>`）、`reference_outputs` 与 `rubric[].metadata.evaluated_files` 之间**逐字节完全一致**；
- 正式文件名与 Harbor 转换规则仅用于内容衔接，保存 `result.json` 不代表已完成平台上传、Docker/Oracle 验证或真人专家验收。
