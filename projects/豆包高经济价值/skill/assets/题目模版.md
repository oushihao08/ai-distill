# 题目包字段

按本次返回 schema 填写七项内容；下列花括号、Markdown标题和列表只用于说明字段，不原样进入业务文字。题面＝question，标准答案＝reference_answer。字段契约不固定业务文体或作答工具，业务文字采用[书面表达组合库](书面表达组合库.txt)中的办公写法。

## 表头

题目 ID：{本次 ID，仅用于题包关联，不写入业务正文}
一级／二级行业：{任务发生组织的主营行业及细分行业，按当前分类}
任务形式：{本次契约允许且有真实业务依赖的形式，不机械拆轮}
输入附件：{表头按实际分件脱敏文书文件名或登记原件名填写；题面、rubric、思路、标答业务正文直接点明所附分件脱敏卷宗的具体原始文书名称及案号／日期／出具主体或统称“所附卷宗”，严禁写“附件1”“附件 1”“合并卷宗”或 `材料-xxxx.docx` 等匿名哈希文件名}
L1 职业簇／L2 职业：{负责交付的律师／法务岗位，不填当事人的诉讼身份}

## 任务名称

{用最具区分度的单一核心事项、待决问题或关键文书用途命名；按最终题面确定，不照抄路径，不提前给待求结论，不堆全部文书名称，严禁整批写成“[主体／案名]的[四字动作]与[四字动作]”对称句式，严禁滥用“接管、核校、全套、闭环、专项”等词。}

## 任务类型

{按最终业务用途选本期适用的主要类型，不按附件名分类。}

先按设计方法完成任务盘点、[实质工作选择](../references/出题设计方法.md#按材料展开实质工作)、全部求解及复合判据，再为任务名称、prompt、rubric、作答思路、标准答案-文本分别组合表达。题名概括实际工作，prompt交办对象与可用成果，思路论证处理依据，标答完成正文，rubric验收具体结果。下列字段说明不是题面或答案的固定目录，不把内部盘点、工作分类、写法名称或自查清单作为新增返回字段；不得为采用某种组合反向调整题目内容、方向和难度。

## prompt

{按[场景规范](../references/材料方向场景与交付设计.md)、[设计方法](../references/出题设计方法.md)及[交付规范](../references/题目格式与交付.md)写真实律师卷宗交办：明确服务一方、基于所附真实脱敏卷宗终局节点的办理基准、权限、对象范围、每份交付成果的具体独立正式文件名及用途、必要依据要求。首句切入随本案触发点轮换（不默认拿当事人姓名起头，不堆砌“委托设定＋四连禁令”首段公式；严禁出现“按模拟于某日接办”“本题模拟”“模拟委托”“办理演练”“假定……”“题设前提”“材料取得窗口”等任何模拟话术或人工拆窗设定，越权边界随对应对外文书就近交代；引用材料直接点明具体原始卷宗文书名称，严禁写“附件1”“合并卷宗”或 `材料-xxxx.docx` 哈希名）。将设计方法确定的全部工作、处理深度、各独立命名正式文件及核验要求写入委托，不以概要或回复正文替代文件交付；不在题面喂给法定起算日、节假日顺延规则、计息折算基数或法定清偿抵充顺序，不提前给冲突位置、判断结论、分支清单或解法。}

{按[交付规范](../references/题目格式与交付.md#作答端检索依据与交叉核验)将完整执行与四项硬核交付要求按具体独立正式文件名融入对应文书与底稿段落（严禁照抄 Skill 内部缩略术语，严禁在末尾单挂统包式技术尾段）：深入论证竞争解释、联网打开权威法源原文核验、按题面指定独立文件名逐件交付完整可编辑正式文书（DOCX）、全由公式驱动的多分表工作簿（XLSX，含实际重算读回及围绕本案真实争议款项采信或关键时点分歧的业务情景联动验证，禁用“隔离核验副本改变一项关键输入”套话），并将主报告／意见书全文、全部正式对外文书与经横向或列宽适配的多栏核算附表全套导出为分页 PDF、逐页转为页面图像排查宽表横向劈裂／签章孤行／跨件金额出入并修改原稿重导核准；不加“先详细规划”起手式，不单列“文件交付回执”文种；改写后反查全部任务、文件能力与判据不变。}

{卷宗横跨多个程序阶段、含在卷遗留文稿或存在前后记录冲突时，优先采用[原卷跨阶段穿透与前手纠偏](../references/出题设计方法.md#原卷跨阶段穿透与前手纠偏)（多份在卷文书连锁重算、同案异源客观凭证消歧或前手在卷申请／合同纠偏定稿）；材料集中于单一程序阶段、流水穿透或章程决议联动改定时采用深度单案全套定稿。一切事实与凭证均须来自所附分件脱敏卷宗原件，严禁在题面内由出题人捏造卷外来函、虚构后续汇款／补充通知或把同一套卷宗人为拆成“两次材料取得窗口／保留双版本”。}

## 考点 rubric

{整体失效规则依评分规范筛选本题适用风险，落到具体对象、错误行为、核验依据和核心委托后果；多个情形写清独立触发关系及不触发边界。五个风险方向仅供作者审查，不作为固定条款复制到题包。}

{按[评分规范](../references/评分与难度验证.md#考点)划分复合专业结果，完整覆盖且不重复，既不把同源本息抵充拆成多条算式，也不把独立实质任务过度粗捆成 ≤3 条。逐项依据核心结论、决定性依据和成果可用性判断成立或不成立，非实质错漏不否定本项。等权换算百分制，不设固定条数。每题必须在最直接相关的一条 criterion 中写入案件化整体失效条件（仅出现一次，不固定塞在末条末尾），按本案自然行文写明全题归零后果（如全题按零分计、整题不予计分等，不逐字复读同一固定句尾），不另占得分项或分母。}

1、{具体专业事项及完整验收条件}
2、{下一项具体专业事项及完整验收条件}

{以上是阅读稿的普通编号，不是结构化字段。JSON 仍按 schema 返回，内部 id 保留 R1、R2 等；旧契约要求 max_score 时填1，其他契约按其实际字段返回，不额外添加 max_score；criterion 不重复序号、ID 或分值标签。}

{每项直接点明所验收的业务结论或成果能力（禁止写“本条评价……”），写清具体必要判断及联系、所附卷宗内决定性原始文书／记录内容（直接点明具体原始文书名称及案号／日期或统称“所附卷宗”，严禁写“附件1”“合并卷宗”、`材料-xxxx.docx` 哈希名或页码）与规则要旨、正确结论及对应独立命名成果要求；计算写口径与关键结果。合法替代、关键失败及共享前提存在时，就近交代实际边界，不逐项套同名栏目。段落、分项或计算明细按内容选择。}

{先检查数据与依据、专业处理、成果使用的覆盖，再按独立用途设项；不固定这三类为三个考点。相关 criterion 写明产物实证标准与失败影响（明确仅列文件名、口头自述已完成或填静态常数不成立）；共用文件或读回缺口不重复否定已可核验的内容结果，实际使用能力仍须有对应的复合验收。严禁把“评分端”“轨迹未传”“评测条件不满足”“不作为有效专业难度成绩”等内部评测系统术语写进 criterion。}

{涉及跨阶段原卷穿透与争议情景联动时，按[跨阶段原卷核改与联动试算的验收](../references/评分与难度验证.md#跨阶段原卷核改与联动试算的验收)覆盖跨文书核查的新增专业判断、公式联动及正式文书修订；具体结果、允许分支、上游错误归属及在卷旧稿与本次正式定稿的边界进入对应criterion。不得虚构卷外事件或设简单文件分。}

{评分者不读取 Skill、作答思路或默认标答；每条 criterion 须包含自足的完整判据。正文写具体成立要求及决定性失败影响，不重复“全部满足得分”之类尾句；整体失效条件写清具体行为、证据及全题零分后果，不固定标题或措辞，不增加schema未声明的字段。参考[复合示例](../references/评分与难度验证.md#关系型考点示例)，不继承示例事实。}

## 作答思路

{用日常专业书面说明完整展开本案决定性记录如何支持、限制或推翻主张，逐项说明规则与条件如何决定处理，细致区分对象、时点、证据效力和适用分支，并解释必要计算及竞争解释的取舍。写已完成的专业论证，不复述通用工作流程，不交Markdown正文、代码或生成脚本。}

{跨阶段卷宗穿透的论证解释后阶段在卷文书如何印证、限制或推翻前阶段记录，说明下游文书与核算为何据此调整，保留卷宗本身未决的真实证据缺口；不把卷宗目录摘抄或工具步骤当作推导。}

## 标准答案-文本

{严格以题面指定的各份成果独立正式文件名分件标示，逐件按对应真实法律文书或核算底稿体例全面完成委托，完整写出可直接提交或签署的正式文书正文（含法定标题、致送法院／收件主体、当事人基本情况、请求／结论、事实与理由、尾部及附项）、必要论证、核算与分支处理；首屏直接进入第一份独立命名的正式法律文书或法律意见书正文，严禁写成脱离正式文书载体的“无信头直入争议结论”或“出题人自撰审签结论正文”，也严禁整批机械照抄千篇一律的三行抬头模板。跨文件结论、金额、条件与实际条款前后一致；细致区分在卷已证事实、单方陈述与待核缺口，完整说明其对各独立成果使用的影响。业务正文不带Markdown标记或编程内容，不能只列文件名、“另拟文书”或以代码代替文件交付。}

{采用实质工作选择中的任务时，逐项落实到对应独立命名的正式成果中；受影响的正文、计算及关联文书一并校准一致，保留在卷原稿中仍成立的内容。题面要求可直接使用的正式文书或合同修订定稿时，不能以审查清单、回应提纲、审签结论综述或修改建议替代。}

{文件题的文本标答须按各成果独立正式文件名逐件写全正式可用文书全文、工作簿分表结构与字段口径、活公式写法、分项汇总及争议或异常调整项的逐笔处理；所附卷宗已明确且无争议的大批量同质原始流水按具体原始文书来源、笔数与分项小计归并引用，不逐行重抄进 `reference_answer`。普通出题由作者用计算脚本核验全部数据与公式闭环并直接输出 `result.json`，不在出题会话内制作配套办公文件或渲染图片；作答端运行能力缺口仅在会话回复中简述，不另写落盘文件，不把未来操作指令或未执行脚本塞入标答，不新增 schema 字段。}

{涉及跨阶段卷宗核改与争议情景联动时，按各独立命名成果完整交付核定后的正式文书全文与工作簿主表／情景试算表结构，明确在卷文书依据与适用边界。不能用局部替换片段代替需独立提交的完整正式文书，也不能让接收人自行拼稿或只交最终总额而省略中间勾稽。}

## 独立使用与组合规则

业务设计完成后必读[表述方法](../references/表述方法.md#独立使用与组合规则)和[书面表达组合库](书面表达组合库.txt)。任务名称、prompt、rubric、作答思路、标准答案-文本分别依据本题的触发事实、信息关系、接收人和成果用途选择并组合表达组件。以改写前内容核对全部业务工作、难点与0/1判分关系不变；选型编号和内部组合过程不进入题包。

## 已有题目的保义改写

仅授权润色时按[保义改写规则](../references/表述方法.md#已有题目的保义改写)，不借改写改变题面工作、rubric 或标答结论。

成稿覆盖核对：按[完整阶段材料要求](../references/出题设计方法.md#每项工作与各阶段材料完整交付)逐项核对本题已选工作的输入、处理结果、实际文件与验收。回复正文不替代需要独立使用的文件；所有阶段均保留必要成果及明确有效关系。按[实测验收](../references/评分与难度验证.md#执行复杂度与实测证据)记录难度、轮次、耗时，未测不写已保证。
