# 高经题目难度提升会议纪要

- 来源：国庆期间难度提升分享会口播整理
- 用途：从真实出题场景到构建难题的桥梁；流程和质检细节以各小组长为准
- 模型作答只看 prompt 和输入附件。作答思路、标答、考点不进模型输入。

## 前提

提升难度的根本是任务本身够难，不是故意刁难模型。

质检里看到的情况：模型觉得难的事，通常也是真实工作里难的事。故意 mock 一个场景去卡模型，往往反而不难。

把模型当成同事或实习生，按真实工作和科研里的交代方式给任务。人在真实任务里往往不知道正确路径，要从只言片语里摸索、拼信息。

不要把本纪要里的 tips 丢给模型去 mock 出题。质检经常一眼能看出构造题。

## 难度落在哪

题目结构里，影响难度的是 prompt 和输入材料。这是模型做题时会看的部分。

答案侧（标答、作答思路、考点）是模型作答之后，帮质检理解题目、搭起从 prompt 到考点的桥。标答本身与难度无关。

判分依据是考点。模型产物和标答可以有差距，尤其半开放题：标答是一种较好解法，考点不应把这种解法写成唯一解。收敛的计算/审计题，关键值应和标答对得上。

## Prompt

要从真实工作环境入手。有效知识必须已经蕴含在 prompt 或附件里。在这个前提下，可以隐去引导，对部分信息做模糊处理。

把握尺度：更强的模型，或靠多人协作，应能从现有材料完成任务。做不出来是模型能力问题。题目必须可作答；在可作答的基础上模型做不出来，才是难度高。

不要把思路前置在 prompt 里，不要告诉模型怎么做。附件内容可以细列在作答思路里，方便校验；prompt 里不需要罗列，让模型自己找。

只要把事情讲清楚、只让模型复现，以当前模型能力，大部分题仍在能力范围内。流程不能告诉模型。

尽可能扩大项目范围，覆盖完整项目周期和上下游协作，不要只考一个关口。各阶段信息必须共享并互相影响。小题之间要有流程衔接，不是对同一规则重复处理多份文件。

投资项目、经营改进项目、科研项目都可以这样铺。

诉求和交付物要讲明白：完成什么任务、交付什么东西。材料只要保证解题有效信息在其中。

## 附件

核心是保持接手任务时的脏属性和噪音。专家把问题整理成题、打包附件时，人类操作往往会把难度处理掉。要提高获取数据的难度。

批量 mock、构造出来的数据，文档里几乎全是有效信息，模型读出来就能用，难度不够。要回到真实工作场景。

矛盾必须可解。附件 A 和 B 冲突时，C 里应有可支持判断的条款，可以不那么显性，但不能只放两份自相矛盾、无法裁决的材料。按权威性判断适用哪份；注意时间跨度，不同时间点甚至要根据当前时间取计算数据。

有效信息分散在不同附件里，每个附件的功能不要一目了然。完成任务所需信息不会只在一个文件里。

可以加干扰项，尽量保留原生信息，不要纯粹堆冗余。

联网搜索能抬轮次。普通项目只用普通能搜到的信息。若有效口径必须靠联网得到，要在作答思路里写明确认搜得到，避免实际搜不到。需要接库、API、注册才能拿到的信息，和普通联网分开，按项目要求。

本项目不应有调用外部工具的实操（如 CAD 制图、单独搭环境）。大部分文件应可读。不确定问小组长。

必须提供真实附件和真实内容，只做脱敏。名称可脱敏。处理数据时不能改变附件之间的耦合关系。公有和私有文件比例无额外限制，以出题说明为准。

## 轮次

增加交付产物的数量和类型，从实际业务出发。一份产物同时需要审计或支撑文件，可以让模型同步分析。同一内容分别出 PDF、Word、Excel，内容无区别，是无意义叠加，不增加难度。

涉及不同规则的大量数据清洗和处理，以及让模型自己判断，都能抬轮次。

## 四个案例

### 1. 多证据冲突

哪个证据有效，不能只靠最新日期。

例子：正式制度 V3，和日期更晚但尚未生效的 V4；管理人员邮件对某条规则临时豁免，后又有邮件撤销豁免；Excel 总结最新生成，但底层用的是旧快照；签字时间较早但权限最高的文件；前台显示完成、底层依据却是草稿；后续被撤销的记录。

模型不能看到什么就用什么，要梳理证据、权限、生效时间、适用对象、当前状态。较有效的设计：最醒目、最像答案的材料可能是错的；真答案往往要综合几份不显眼的证据。

### 2. 把真正判断标准藏起来

告诉模型要做什么，不直接告诉这次决策真正该看什么。

例子：选供应商。材料大量讲质量、报价、规模、获奖、综合评分，甚至给出能力排行。真正卡点可能是谁能按期交付；中途邮件要求提前交付后，标准从「都能入选」变成「谁能提前按期交付」。交付能力不显式写在 prompt 或某一份显眼文件里，相关字段散在各文件后方。

模型容易沿着材料已搭好的评价框架，选出综合能力最强的对象，解决不了当前最关键的问题。考察的是：从总体任务恢复出当前瓶颈 → 真正判断标准 → 该读哪些证据 → 最终决策。不是给什么材料就分析什么指标。prompt 里如果已经说明材料怎么分析，难度完全不同。

### 3. 同一批对象同时命中多条规则，没有固定优先级

必须来自真实业务。仅为这个点去构造，会显得刻意，叠加后也容易有漏洞。

固定的 A 优先于 B、B 优先于 C，模型较好处理。更难的是：优先级随同时命中哪些条件而变化。两项同时命中是一种先后或覆盖关系；A 和 C 同时命中可能 C 优先；三项同时命中可能触发特殊条款。还有单独例外、特定时间或状态才生效的粒子、风险项要额外审计。

模型路径：当前状态 → 命中的规则组合 → 处理顺序 → 覆盖关系 → 例外。规则复杂，且要批量处理；不同附件的对象还可能交错适用，不是附件 A 一套、附件 B 一套。

### 4. 局部无解，必须维持到交付

不要把整道题做成无解。只在其中一个点上：规则不明确，人做的时候也会单拎出来，交付时再问领导或走特殊环节。

初期就要标成特殊处理、当前条件下无解，并维持到项目交付。孤立地问「有没有一个数同时大于 10 又小于 5」，模型知道没有；把同样的矛盾埋进复杂任务中间环节，模型很容易为了交差硬给出一个漂亮、合理但无效的结果。它应该意识到这一步原则上不该继续往下算。

## 使用这些 tips 时

不要把假陷阱做成真漏洞。从真实场景出发，用这些点回忆自己的工作，再出题。

## 答疑（与出题直接相关）

- 模型只看 prompt 和输入附件，不看做题思路和标答。标答是给人审计、给后续训练用的，是必填。prompt 要求交付产物时，标答附件应有对应产物；纯文字作答才可以只交文字。
- 标答不要用 AI 做。以前 AI 就能做出来的标答，现在也很难达标。公开文献或开源项目里的表格，模型有可能搜到。
- 判分按考点，通常 0-1、等权。专家自设权重、倒扣、一票否决，流程里不参考。建议 15 条以上、大约 20 条。写太少，一条占比过大；写一堆送分项，分数会被抬高；只写最难的点，又会让得分低于模型实际做对的比例。考点要客观反映作答，不要过度拟合自己的标答。质检可能对考点做调优。
- 文件脱敏不会被判成故意编题。
- 专家核对自己的标答，不核对模型产物。模型产物是项目侧抓来判难度用的。不想自测可以完全不用模型。
- 自测难度：让模型独立作答，带上标答和思路，直接问它自认做对多少。大部分做对，难度通常不够；缺口大，才更可能够。具体调哪个模型问小组长。
- 难度不够往往不进详细质检，也不会逐条解释为什么不够。难度初步够了，才会讨论哪里还能优化。
- 难度不够算不合格还是返修、轮次打标、豆包相关，按本项目问小组长。
- 出难题：把诉求和交付讲明白，上下文可以模糊，有效信息必须在材料里。以模型给不出合格答案为准，但题目必须可作答。
- 本纪要是通用答疑。出题说明、案例库、软件工程优秀案例、项目流程以小组长和正式出题文档为准。
