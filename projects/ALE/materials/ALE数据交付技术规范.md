# ALE 数据交付技术规范

需求沟通v1 · 2026-10-19

适用于 ALE 专业工作任务包及配套环境、评分和轨迹。本文用于技术对齐与试包质检；领域题量按第 1 节执行，资源预算及正式验收条款在签约前确认。样本符合规范可推进采购协商，不等于批量数据已接收。

## 1. 交付内容与计量

- 每题交完整题面、输入材料与初始状态、环境/工具及重置方法、可执行评分入口、逐项 rubric、真实参考成品及推导依据。ALE-native、Harbor 或等价可复现格式均可，不依赖供方私有 harness；自建工具、断言 handler、辅助库及评审适配器一并交付。推荐目录与文件约定见第 7 节。
- 每题交最终版本全部成功、失败和故障记录、难度标定、实际产物、逐项评分及成功轨迹防 hack 审核；另交至少一条 opus-5 或 gpt-5.6-sol 的真实完整成功轨迹，不能用 oracle/参考脚本日志代替，也不能替代第 4 节标定。
- 批次交 task_id/版本/领域/任务族/材料/环境/run 对应表、全量文件清单与 SHA256、来源及训练/商业使用授权、去重与覆盖统计。ZIP 内外都可校验，正文和大日志必须实交，不接受 LFS 指针、过期下载链接或占位文件。
- 按去重且合格的独立任务数计净量；任务数、独立材料包数、环境数和共享世界数分别统计。合法复用软件环境不扣题数，但只换名称、数字或种子的同构题不重复计数；公开原题、直接改写和历史重复交付不计新增原创净量，须披露上游和增量。
- 交软件与工具、操作系统、文件格式、语言和资源档位标签及覆盖表；题目领域与题量按以下要求交付，同一道题不得重复计入独立净量。

**题目领域划分方式按照ALE的 domain/sub_domain 划分**

单个 domain 数据需求（按去重且验收合格净量计）：computing_math 200 条，life_science 200 条，health_medicine 200 条，business_finance 200 条，engineering 200 条，visual_media 200 条，physical_science 100 条；其他 domain 每个最多 50 条。

每个 domain 内各 sub_domain 的题目分布均匀，随批次提供逐题领域标签和各 sub_domain 的数量统计。

## 2. 题目与评分质量

- 任务须保留真实专业工作的实质步骤，目标、输入、权限、信息截点和交付物清楚；必要材料可发现且足够。关键事实、对象、日期、单位、表格行列和计算口径一致，数值可重算、引用可定位，不以隐藏义务增加难度。
- 每条 criterion 写明题面依据、材料位置、交付物及观察位置、判断条件、权重、容差和关键门控。检查对象关联、计算及实际状态，不能因文件存在、出现同一数字或声称完成就给分；独立义务不得混绑、重复扣分或互相矛盾。
- 材料有意设置冲突时，须允许有依据的纠错及其下游影响；存在多种合理读法或等价工程实现时，声明接受条件。参考值与所有评分项一致，不用单一隐藏答案误罚有依据的替代结论。涉及专业判断的题目须有相应领域审核及依据。
- 分数统一声明量纲及归一化方式。确定性参考应取得声明满分；连续专业评分参考须达到 0.90 且全部关键项通过。模型成功按事前冻结的合格线与关键项共同判断，核心目标失败不能由大量次要分抵消；保留连续分，另记二值 success。

## 3. 环境、网络与原生产物

- 交可独立构建或恢复的环境、固定依赖和镜像 digest；Windows/GUI 题交可复现的 VM/快照、软件版本、安装授权与启动/重置方法。明确 CPU/GPU、内存、时间和权限要求；不能仅因主机 Python 版本不同或静态 import 未解析就判题失败，须在声明环境核实。
- 默认以离线可复现任务为准，每题声明 allow_internet 与访问范围；确需检索或业务 API 的，列允许服务、工具、凭据注入方式和合法快照。确定性判分本地离线运行；模型评审仅访问约定 judge API，依赖及模型资产预置，不在评分时临时下载或静默更换方法。
- agent 执行期间不可读隐藏真值、参考成品和私有评分资产；交构建、挂载、执行、收集、判分各阶段可见性。业务状态只通过授权工具改变，工具写入/读回与评分读取一致；自写日志或成功标记不能作可信完成证据。
- 环境可启动、健康检查、完成参考、读取产物、评分并复位；题目和 run 间不串状态。缺依赖、服务或网络故障显式报错，不能伪装成正常零分；agent 正常执行但漏交产物，按模型未完成处理。

参考软件检查规范，更多软件可以自行补充。

| 产物类型 | 须执行的实质检查 |
| --- | --- |
| CAD / 三维设计 | 重开原生工程/实体；核对单位、拓扑、关键尺寸、功能特征及可编辑性。 |
| Blender / 音视频 | 重开工程，检查绑定/材质/轨道与任务要求；重新渲染或导出核对。 |
| XLSX / Office | 检查指定对象、公式重算与缓存、修订/结构、跨文件勾稽及可读排版。 |
| Web / 应用操作 | 启动真实页面/服务并实际操作，核对持久状态、关键交互及约定视口。 |
| 科学计算 / 代码数据 | 从原输入独立复算，检查假设、样本划分、单位、误差、运行约束与全量对象。 |

截图、导出件可作辅助证据，不能替代题面要求的原生工程。无 GUI 或权限受限时须提供可执行的等效检查；原生产物要求本身不能因此删掉。

## 4. 难度标定

> 每个最终任务版本使用 GPT-6.1-Sol 或 Opus-5.5，reasoning effort = max，执行 8 次独立有效尝试，仅保留成功 1–3 次的任务。通过率为 12.5%、25% 或 37.5%；成功 0 次或 4–8 次不合格。

- 成功定义：全部必需项通过、实际专业产物或最终状态正确，并达到事前冻结的评分合格线，且完整轨迹及防 hack 审核通过。保留原始分数和逐项结果，另记二值 success；部分分不能代替整题成功。
- 事前固定模型实际版本、harness、提示词/工具、采样参数及时间/token 预算；8 次均从干净状态开始，不共享答案、上下文或产物，不得人工引导。
- 预先编号并交付全部 8 次；不得挑选有利结果或重跑正常失败。仅有证据的基础设施故障可排除并补足，原记录保留；超预算或未解出计失败。材料错误或题面歧义须先修复，不作为模型能力不足的证据。
- 题面、环境、参考解或评分发生影响结果的修订，须重新标定。逐题成功数及通过率可由 8 个 run_id、原始评分和审核结果复算；额外运行单列。不得为凑通过率或模型排名而调整评分、删失败记录或削减实质工作。

## 5. 轨迹完整性与防 hack

- 每条轨迹对应一次真实运行，包含任务及版本、模型及实际版本、run_id、消息顺序、工具调用 ID/参数/结果、接口已暴露的推理、最终回复、实际产物及逐项评分。不得伪造、拼接、截断或以压缩摘要替代原始记录；未暴露推理据实声明。大块工具输出另存完整正文并给可校验索引。
- 每条 run 须按逐次模型调用的原始 usage 累计 agent 输入、输出、总 token 量并统计运行轮数；缓存/推理 token 有则分项说明包含关系，不重复累计，缺失不填 0。一次模型响应计一轮，工具返回不计，同轮并行工具调用不额外加轮，工具调用数另计；judge 用量和基建故障/重试单列。按题目及模型，对成功/正常失败分别汇总样本数、均值、P50、P90 和最大值，注明分位数算法。
- 禁止经搜索、网页、Git 历史、包仓库或其他会话获取本题答案/私有评分资产；禁止泄露凭据、修改测试/评分器/reward、伪造对象或绕过授权工具直接改后端。正常专业检索须符合第 3 节网络范围。发现评分漏洞与模型实际利用须区分；直接修改私有状态不能证明模型可利用，利用结论须有允许工具下的实际可达证据。
- 每条申报成功轨迹均须有防 hack 审核，陈述、工具证据、成品/状态及分数一致；保存产物复评分须仍满足成功条件。随机 judge 按预先冻结规则复评/仲裁，保留全部结果，不挑最高分。
- 数据保持私有，每题关联数据集专属 canary；已确认的答案泄露、轨迹伪造及奖励投机为 0。缺失或异常须保留并披露，不能删去后改善通过率。

## 6. 全量质检、返修与接收

- 逐题登记、逐题检查、逐题给结论，不以几个典型 case 代替全量覆盖。每题先在正式环境验证正确参考基线，再测空提交/no-op、适用错误反例和正确替代答案。基线跑不通时先定位环境/材料/产物问题，不据此宣称退化已被拦住。只读源码或自报得分不算完成动态检查。
- 反例每次只改一个实质条件，保留其他正确内容，用未修改的正式评分器比较受影响项、总分和不应变化项。至少覆盖：空壳/表头、常量/伪造数据、保留关键词但否定结论、错误对象或漏组、未固定 ID 的数值改错、删关键对象、篡改输入、跨文件/状态矛盾及功能缺失；合法等价解不得误罚。
- 空提交/no-op 为 0；骨架、常量伪造及纯摘要缺核心工作者，归一化分数须 ≤0.20 且不能判成功；其他反例必须失去对应项分，破坏关键约束则整题失败。适用性按任务写明，不把所有缺陷统一套成同一分数上限。
- 每题保留基线/变体原文件、改动、公开依据、预期与实际逐项/总分及复现方法。judge 交模型、参数、完整 prompt 模板、实际填充内容与原始响应，支持接我方指定模型；产物中的指令不能改变评审规则。随机评分按冻结的复评/仲裁办法成对复测，全部结果留存，不挑最高分。
- 问题单写 task_id/版本、具体差异、文件/criterion 位置、对结果影响、需改/补内容和复验步骤。供方逐条回应并交修订与影响范围；题面、材料、环境、参考、评分、受影响轨迹及标定同步更新，不沿用旧版通过结论。
- 缺件是交付缺口，不等于已证实题目内容错误；未测、工具故障和正常模型失败分别记录。关键正确性、评分、隔离或必需证据存在未关闭问题的题不计合格净量；minor 仅限不影响理解、复跑与判分的问题。双方冻结哈希并书面确认后接收，供方自称 final 不触发接收。
- 技术合格后，按约定在固定、独立且不与采购训练数据重叠的评测集上比较训练前后效果。训练方案、评测协议、执行方、费用周期及涨分门槛须事前确认；技术合格不替代约定的训练效果验收，涨分也不豁免重大缺陷。

质检记录最小字段：check_id、task_id、任务/包/评分版本或哈希、检查范围、执行方式、expected、observed、status、证据路径。齐备检查发现缺件记 FAIL；依赖缺件而无法执行记 SKIP；工具/基建故障记 ERROR；完成且满足要求才 PASS。检查项通过数不等于整题通过数。

## 7. 推荐交付格式

推荐按“批次清单 + 逐题任务包 + 原始运行证据”交付。已有 ALE-native 或 Harbor 结构可保留，提供字段/路径映射即可；共享材料和环境只存一份，以版本、路径和哈希引用。

```text
batch/
  batch_manifest.json
  SHA256SUMS.txt
  trajectory_stats.csv
  tasks/<task_id>/
    task_card.json (or task.toml)
    instruction.md
    environment/
      Dockerfile, env.json, requirements.lock, input/, reset.sh
    tests/
      grade.py, rubric.json, reference/
    solution/
      solve.sh, artifacts/
    runs/<model>/<run_id>/
      run.json, trajectory.jsonl, artifacts/, grade.json
    review/<run_id>.json
  shared/
    materials/, environments/
```

| 文件 | 最小内容与格式 |
| --- | --- |
| 批次清单 | batch_manifest.json：批次/任务版本、任务清单、领域与任务族、材料/环境引用、文件路径及哈希；SHA256SUMS.txt 覆盖全部交付实物，排除校验文件自身。 |
| 任务与环境 | task_card.json 或 task.toml：task_id、版本、输入、产物合同、启动/复位/评分入口、资源与网络；env.json 声明镜像 digest 或 VM 快照、软件与依赖。 |
| rubric.json | 逐项 criterion_id、题面与来源位置、产物观察位置、权重、关键门控、期望值/容差/等价答案和实现映射；grade.py 为评分入口示例名。 |
| run 与 trajectory | run.json 绑定 task_id、run_id、任务/环境/评分/模型版本、参数预算、起止及终止状态；轨迹用完整 JSON/JSONL，保留原始字段，大返回另存正文并索引。run.json 同时记录 usage、model_turns 和 tool_calls，汇总须能由原始调用记录复算。 |
| 轨迹统计 | trajectory_stats.csv 每个 run 一行：task_id、run_id、模型、状态、input_tokens、output_tokens、total_tokens、model_turns、tool_calls；run.json 记录 usage 来源及缓存/推理子项，批次清单附分布汇总与字段覆盖率。 |
| grade 与 review | grade.json 交逐项 expected/observed/score、总分、success、错误及证据路径；review/\<run_id\>.json 绑定同次运行、产物哈希、审核结论与证据。 |

文本与结构化元数据使用 UTF-8；原生工程、数据和媒体保持原格式。原有轨迹 schema 可保留，须附字段映射；转换件与原始记录一并交付，不能因转换丢失推理、工具返回或产物关联。

目录名可映射，执行契约不可缺。镜像可通过可获取的固定 digest 或镜像归档交付；Windows/GUI 以可恢复的环境资产及说明替代 Dockerfile。目录中的 reference/solution/rubric 不得因此进入 agent 可见区，仍须证明第 3 节的实际隔离与收集流程。
